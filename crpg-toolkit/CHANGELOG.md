# Changelog

All notable changes to this package are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

Promoted from three games built on the toolkit (Barrow's End, ConsumerGame, Viking Raid), where each had been worked around or written twice. Everything below is additive and opt-in: no existing call site, test or authored asset changes behaviour. Design and review: `Docs/Plans/Toolkit-Promotion-Batch1.md`.

### Added
- Common actions and opportunity attacks (SRD5): Dash, Disengage, Dodge and combat Help as registered abilities, granted to every character by one universal feature (`FeatureDefinition.Universal` / `UniversalFeatures`, applied to character builds, NPC spawns, the registry and loaded sessions without refilling resources). `CommonActionRules` (Dodge and Help queries, lifecycle cleanup), `DashEffect` / `DodgeEffect` / `HelpAttackEffect`, temporary movement capacity on `ResourceState`, and `OpportunityAttackRule` (an eligible hostile spends its Reaction on one real melee attack; Disengage suppresses it; native segmented and instant movement both resolve it). `IOpportunityAttackRule` / `IAttackRollObserver` carry the hooks. 21 ability descriptions that were empty or lost on load were repaired.
- Perception, light and Hide (design `Docs/Design/Hide-And-Vision.md` in the game that asked for it): `IPerceptionQuery` (`SightOf` / `CanSee`, `Visibility` = Clear, LightlyObscured, HeavilyObscured, Unseen) with `LightLevel` / `ILightProvider`, `IFacingProvider`, `VisionProfile` (`Panoramic` is the SRD's all-round unlimited sight, `Watchful` a 120 degree cone) and `VisionGeometry`, all in `CRPG.Core`. SRD5 `Srd5PerceptionQuery` implements it (blind observer, invisible target, obstruction, optional cones, light at the target, darkvision as a `Sense:Darkvision` feature modifier in feet; elves and dwarves have it). It is an optional dependency of `AbilityResolutionService` (a target the caster cannot see fails a sight requirement), `OpportunityAttackRule`, `CommonActionRules` and `TacticalAiTurnDriver` (an AI only chooses enemies it can see); `DefaultAttackBonusRule.Perception` gives an attacker the target cannot see advantage and one who cannot see its target disadvantage. `StealthRules` + `HideEffect` + `ability-hide` + `condition-hidden`: one Dexterity (Stealth) check against each observer's passive Perception, kept until the hider is found; an attack, a hostile ability or a spell at another creature, damage (a house rule) or walking into plain sight gives the hider away (`MovementResolutionService.Moved` reports every frame of a walk). `IStealthService` is carried on `AbilityExecutionContext` (`AbilityResolutionService.Stealth`). `SurpriseRules` + `condition-surprised` (a creature that noticed none of the other side cannot act on its first turn). `WalkableCells` and `VisionField` in `CRPG.Navigation` cache the pointwise sight query over the walkable floor for overlays and AI. The `skill-stealth` asset, which had no name and no governing stat, is now Dexterity. `AbilityResolved` events now carry `Data["ability"]` and `Data["targets"]`.
- `WorldSpawnService` places a restored NPC on the nearest navmesh point (within 1.5 m) when its saved pose stands just off the mesh, so a creature saved mid-pose (seated on a bench) no longer fails to create its agent on load.
- `AbilityUsedLogEntry`: logged once per ability execution, before any roll or damage, naming the ability, the caster and every strike (one entry per creature, repeated for a spread ability's extra projectiles). A presentation reads it to start the cast effect and launch one projectile per strike, then the rolls that follow to know what hit. Nothing is logged for a rejected cast or when there is no combat log.
- Attack riders, and Sneak Attack as the first: `IAttackRiderRule` (with `AttackRiderQuery` and `AttackRider`) is asked by `AttackRollEffect` once per target that was hit, after the weapon's own damage; an offered rider is rolled and dealt through the same damage path (the weapon's hit-point resource and damage type, doubled dice on a critical hit) and announced with an `AttackRiderLogEntry` just before its damage. `AbilityExecutionContext.AttackRiderRule` / `.Ability` and `AbilityResolutionService.AttackRiderRule` carry it; `AbilityTag.Finesse` is appended. Null rule: nothing changes.
- `IAllyAdjacencyQuery` and `PositionalAllyAdjacencyQuery` (any conscious ally of the attacker within reach of the target, wherever the attacker stands), and SRD5 `SneakAttackRule` (the `feature-sneak-attack` holder, 1d6 per two levels rounded up, with advantage (flanking counts) or an ally beside the target, never with disadvantage, once per turn, restored on the rogue's turn and at the start and end of a fight; any weapon attack by default, `RequireFinesseOrRanged` for the strict SRD rule; never a spell).
- Multi-target abilities (Bless, Magic Missile, Prayer of Healing) can be given their targets one click at a time: `AbilityTargetingGate.IsMultiTarget`, `PickedTargets`, `Confirm()` and `PicksChanged`. Each click on a new creature is validated together with the picks so far and added; the pick that fills `MaxTargets` casts, and a click on a creature already picked (or `Confirm()`) casts with what is picked. A rejected pick is not added and the earlier ones stay; arming again or disarming clears them. Single-target, self and aimed abilities behave exactly as before.
- `TargetingDefinition.SpreadProjectiles` (default off): an ability that fires `MaxTargets` projectiles deals them round-robin over the creatures chosen, so one target takes every dart, two take two and one, three take one each, each rolled on its own. The target list a caller passes still may not repeat a creature. Set on the SRD5 Magic Missile asset, whose description no longer says stacking darts is unmodelled.
- `IPointerWorldFilter` and `PlayerCommandRouter.WorldFilter` (forwarded by `InputSystemCommandSource.WorldFilter`): an optional say over what a pointer can reach, for a building shown one floor at a time. `IsPickable(collider)`: a click passes through a collider the filter declines (the nearest ACCEPTED hit decides; physics, navigation and doors are unaffected); `IsSelectable(id, position)`: a drag box skips a character the filter declines. Null by default and then identical to before (one nearest raycast, every selectable on screen).
- Location maps, for a hub town that needs more than a picture (design `Docs/Design/Location-Map-System.md` in the game that asked for it), all additive: `MapGlyphShape` on `MapLandmark.Shape` / `MapMarkerSnapshot` (diamond stays the default; square, circle, ring, triangle, hexagon, star, cross and pin are drawn by `MapGlyphElement` with Painter2D, so a kind of place no longer relies on colour alone); `MapMarkerKind.Pin` + `MapMarkerSnapshot.ForPin` (numbered, drawn with its number); `MapView.SetOverlay` / `LocationMapHud.SetOverlay` / `ClearOverlay` (an optional layer over the image and under the markers on the image's own rectangle: a fog-of-war mask; survives re-`Initialize`); `LocationMapHud.AreaClicked` raising a `MapClick` (world XZ, button 0/1, the landmark or pin key under the pointer; a press moving less than `MapViewStyle.ClickDragThreshold` is a click, the right button never pans); and the editor baker `CRPG.Editor.LocationMapBaker` (north-up orthographic render framed to an exact world rectangle through the project's pipeline, the guide image with a metre grid, an idempotent `LocationMapDefinition` asset) with `MapStylise` / `MapStyle` (a parchment tone and Sobel-inked edges as a pure pixel pass).
- `UtilityAIDecisionProvider`: optional `scoreFloor` constructor parameter. A candidate must score strictly above it, so `scoreFloor: 0f` treats a zero score as a veto (a downed target is never attacked just because it was the only legal one left) and a fully vetoed turn returns no decision. The default (negative infinity) keeps the original behaviour, in which a behaviour with no considerations still acts.
- `GameEvent.AfterHeal` (appended last), published by `HealEffect` after its combat-log entry, with `Data["Amount"]` the amount actually restored.
- SRD5 `DeathSaveService`: optional `reviveOnHeal` flag (default false). A heal that brings a character from 0 hit points above 0 ends its death saves, removes every Unconscious condition and publishes `CreatureStabilized`. A healthy creature that is unconscious for another reason is not woken, and characters outside `usesDeathSaves` are untouched.
- `PartyExplorationController`: optional `facingSource` (an `ISelectableSource`). When given, a move order's facing is derived from the centre of the ordered members to the destination (the router always sends world forward, so a wedge formation used to point along +Z), and `LastOrderFacing` exposes the last derived direction.
- `CRPG.Presentation.CombatCueEventBinding`: the presentation-neutral event-to-cue mapping (hit, down, died, recovered, plus an optional `onContext` that sees who struck). `SpriteCueEventBinding` is now a thin wrapper over it; its public API is unchanged.
- `TacticalEncounterController.Defeat` (instance, and a static overload for callers that run combat on a bare `CombatEncounterService`): the same teardown a real `CreatureDied` gets, for rulesets without death. `CreatureDied` now routes through it.
- `CRPG.AI.PerCombatantDecisionProvider`: routes each combatant's turn to the provider of its own behaviour set, so one encounter can mix enemy types.
- `CRPG.Gameplay.PartyCommandFilter`: wraps an `IPlayerCommandSource` to filter Select to the current party's members and arbitrate input (`CombatMoveOverride`, `MovesLocked`; locked wins).
- `TacticalPlayerMoveAdapter`: optional `canMove`, `adjustDestination` (+ `MoveRefused` event) and `provokesReactions` (false = no opportunity attacks against player movement). New `NavMeshDestinationAdjuster` snaps a click onto the NavMesh and keeps it clear of other combatants so the move can arrive.
- `CRPG.Editor.Npc.INpcAppearanceEditor`: an extension point on the `NpcDefinition` inspector so a project can supply its own appearance creator (a 3D character builder, a sprite paper doll). The toolkit only knows `NpcDefinition.Appearance` holds (slot, option) ids; implementations are found with `TypeCache`, asked `Handles(npc)` (a new NPC with no visual prefab included), and their element is added after the raw Appearance foldout (which stays: it is the data). The inspector rebuilds its extensions when `visualPrefab` changes, disposes an `IDisposable` element (a preview render utility), and wraps both calls in try/catch so a faulty creator never breaks the inspector. Viking Raid's Viking NPC creator (`VikingRaid.Appearance`) is the first implementation.
- `CRPG.Editor.Location` location tools (design `Docs/Plans/Toolkit-LocationTools.md`), for placing and checking the NPC spawn points of a `LocationContent` in the editor, no runtime change:
  - `LocationPlacement`: `AddSpawn` creates the anchor (under the common parent of the existing anchors, else an `NPCs` root beside the location) and the list entry as ONE Undo step and returns a generated unique `SpawnId` (the definition's id without `npc-`, then `-2`, `-3`; never the party's reserved `hero-` prefix) or the typed one; `RemoveSpawn` can delete the anchor unless another entry shares it. Ids are only ever generated, never renamed.
  - `LocationValidator.Validate(location, nav, others, origins)` over `INavMeshService` (a fake in tests, `NavMeshService` in the editor; null skips the walkability rules). Errors, from what the runtime really does: empty or duplicate `SpawnId` (this location and the other open ones: a duplicate silently takes over the first NPC's saved record), no definition or no visual prefab, no anchor (the `LocationInitializer` throws), an anchor that is a prefab asset or in another scene, an empty or duplicate store or loot id (they would share one persisted state). Warnings: off the walkable surface, unreachable from an arrival point, anchors under 0.8 m apart, outside the camera bounds, a store or loot adapter missing, a `hero-` id.
  - A UI Toolkit `PropertyDrawer` for `NpcSpawnPoint` (status dot, Select / Frame / Snap; the default list around it is untouched, so the 2D scenes that carry an empty `LocationContent` keep their inspector), Scene-view gizmos (a marker that keeps a constant size on screen, with ground ring, facing arrow, beacon and a labelled plate per spawn point, visible through walls and pulsing for a new placement) and the `Place NPC` global `EditorTool` (places into the selected object's location, else its scene's, else the first open one; pick a definition, a ghost follows the mouse over the first physics hit that snaps onto the walkable surface, click places, Shift keeps placing, R turns, Esc leaves).
  - `LocationNpcAccess` + `NpcQuickPanel`: from a placed NPC to what is edited next. Clicking an NPC's beacon in the Scene view selects its anchor and a panel offers Open NPC (the `NpcDefinition` inspector), Frame, Remove and the dialogue (assign a `DialogueDefinition`, create a `dlg-<npc>` asset beside the NPC, open the dialogue graph); the spawn point inspector row has NPC and Dialogue buttons. This authors the link only: the toolkit does not yet turn `NpcDefinition.DialogueId` into a conversation for a spawned NPC.
  - Menu `CRPG Toolkit/Location/Validate Open Locations` (the scene's `SceneTravelDestination`s are the arrival points) and `Place NPC Tool`. `CRPG.Editor.Validation.ValidationResult` gains an optional `Context` object.
  - Viking Raid: `Viking Raid/Village/Validate Location` (arrival point `CRPG/PartyStart`).
- NPC services (design and as-built notes `Docs/Plans/Toolkit-NpcServices.md`): what a townsperson does besides talk, all opt-in and configured in the editor. **Stores:** `NpcSpawnPoint.Store` (`NpcStoreSpec`: id defaulting to the spawn id, `StoreListingSeed`s, buy/sell multipliers); `NpcStores.Ensure` creates the shop in the session (idempotent by id, so depleted stock survives location unloads and, with `SaveService.RestoreStores` run after it, a save/load); `LocationInitializer.Prepare` / `RebindStoresAndLoot` create NPC shops too; `NpcDialogues.AttachAll` binds it to the NPC's adapter and warns about a missing currency id. **Inn:** `BranchNode.Source = PartyItemCount` (an item and a quantity; `Evaluate` now takes the `DialogueContext`), `SpendItemAction`, a default generic `RestService` in `NpcDialogues.Wire` (react to `GameEvent.LongRest` for anything else a rest should do; `RestService` is sealed). **Quests:** `QuestTracker` (per session: `Start(questKey)`, `RefreshAll`, `Tick`, records `quest-started:<id>` / `quest-completed:<id>` in the Timeline), `NpcDialogueOptions.Quests`, `QuestValidator`. **Recruiting:** `NpcRecruitment` (`Queue(spawnId)` waits for the conversation to END, then the NPC's own character joins the party and its townsperson parts are stripped; the game's callback registers the motor), `NpcDialogueOptions.RequestRecruitSpawn(spawnId, key)`, `WorldSpawnService.SetFaction`, `NpcRoutineRunner.Detach`; `NpcDialogues.AttachAll` and `NpcRoutines.AttachAll` skip party members. **Fixes found on the way:** an Open Store action reached in the MIDDLE of a conversation never opened the shop (only a graph that started with it worked): `DialogueView.Driven` + `ConversationController`; the store screen offered the party's gold for sale (a 0-value coin sold for 0 and deleted it); `StoreView.Initialize(presenter, plainStyle)`; a null store in `ConversationController` is skipped with a warning; `PartyInventoryState.CountShared` / `TryRemoveShared` (all or nothing, across stacks); `GiveItemAction.Item`, `StartQuestAction.QuestKey`, `RecruitToPartyAction.CompanionKey` are readable. **Editor:** a Store field on the spawn row (reset on `AddSpawn`), validator rules for shops (null/free/sold-out items, duplicate ids including store talk points, an unreachable shop), a branch/spend/give action with no item, a Start Quest key with no quest asset, and `BranchNodeView` fields.
- NPC dialogue (design and as-built notes `Docs/Plans/Toolkit-NpcDialogue.md`): a spawned NPC can be talked to. `NpcSpawnPoint.Dialogue` is the dialogue this NPC says in this place (else its `NpcDefinition.DialogueId` resolved through the ruleset); `NpcDialogues.AttachAll(content, spawner, session, options)` (idempotent for the components, re-wires the session dependencies on every call; call it like `NpcRoutines.AttachAll`) adds a `WorldInteractable` (the NPC's own transform as the anchor) and a `TalkInteractionAdapter`; the only required option is a `PanelSettings`. Clicking a talkable NPC is an Interact (new opt-in `WorldInteractable.TakesClickOverSelection`; a character is otherwise always a Select), the approach completes in range (`CompleteApproachInRange`), the NPC holds still (the routine suspension) and turns to the speaker, and everything is released however the conversation ends. `WorldInteractable.Configure` is valid after `Awake` (the missing-anchor error is reported from `Start`). `TalkInteractionAdapter`: public `Dialogue` / `PanelSettings` / `PlainStyle`, `ConversationStarted` / `ConversationEnded` events on every ending, and a conversation that fails to start no longer leaves the NPC (or, via `ConversationController`, the modal pointer lease) locked. `DialogueView.Initialize(presenter, plainStyle)`: a self-contained dark panel for games with no USS skin (the default look is unchanged). Routines wait `ResumeDelaySeconds` after a suspension. Editor: a Dialogue field in the spawn row, the quick panel and Dialogue button author the spawn point's dialogue (`LocationNpcAccess` spawn-level), a new spawn point no longer inherits the previous NPC's dialogue, validator rules for dialogue (empty, graph errors, store action, no collider, DialogueId only), and `DialogueValidator` catches a null node entry and an action node with no action. `LocationValidator.Validate`'s `deepRoutineChecks` parameter is now `deepChecks`. Any assembly that reads `NpcSpawnPoint.Dialogue` needs a `CRPG.Dialogue` reference.
- NPC ambient routines (design and as-built notes `Docs/Plans/Toolkit-NpcRoutines.md`): what an NPC does between orders, configured per spawn point. `NpcSpawnPoint.Routine` (`NpcRoutineSpec`, default `Stand`: every existing scene, save and game is unchanged) is `Wander` (random reachable points in a circle, pauses between legs) or `WorkLoop` (a loop of `WorkStop`s: walk, face the stop, play an animation cue, optionally pick up or put down a `CarriedPropDefinition` held in a humanoid bone). The behaviour is `AmbientRoutineMachine`, plain C# over ports (`IMovable`, `INavMeshService`, animation, facing, hands) and tested without a NavMesh; `NpcRoutineRunner` is the thin Unity adapter and `NpcRoutines.AttachAll(content, spawner)` (idempotent: call it after a location's NPCs exist, after `LocationInitializer.Prepare` and after a load) attaches runners. Arrival is trusted only for the machine's own move request, a stalled leg is abandoned, an unreachable stop is retried then skipped, every action ends on a timer. `GameSession.Ambient` (`AmbientSuspension`) lets any system pause an NPC's routine; `InteractionController` uses it from the moment a request targeting that NPC is accepted until it ends. New `FacingPriority.Ambient` tier, `CharacterPlayableAnimator.TryGetCue` / `HasStanceLocomotion`. Editor: the spawn row's routine section (kind, area, stops, Add stop), per-NPC routine gizmos, validator rules (empty loops, pick-up without a prop or without a drop, stops in another scene or shared with another NPC, unreachable stops, cues missing from the animation profile, non-NavMesh bodies), and `LocationPlacement.AddStop`; a new spawn point no longer inherits the previous NPC's routine. NavMesh-driven NPCs only.


## [0.1.0] - 2026-09-06

### Added
- Initial package scaffolding: assembly layout for `Runtime/`, `Rules/`, `Editor/`, `Integrations/`, `Tests/`, `Samples~/`.
- Phase 1 foundation: `DefinitionId`, `IRulesDatabase` (+ `RulesDatabase` default implementation), `RuleQuery<T>`/`NumericRuleQuery`, modifier pipeline, dice service, structured combat log base types.
- Phase 2 (Actors) start: `StatDefinition`, `ResourceDefinition`, `ConditionDefinition`, and the runtime `CharacterState` (`StatBlock`, `ResourceState`, `ConditionInstance`) — equipment intentionally deferred to the Inventory assembly.
- Phase 3 (Party) start: `PartyState` (membership, click/shift-click/drag-box selection, active-vs-selected, linked groups for splitting the party) and formation solving (`IFormationSolver` + `Cluster`/`Line`/`Column`/`Wedge` implementations, `PartyMoveOrder`) — NavMesh/Navigation wiring intentionally deferred.
- Phase 3 (Exploration/Navigation/Camera): `INavMeshService`/`NavMeshService` (verified against a real baked NavMesh — see Verified below) and `IMovable`/`NavMeshCharacterMotor`; the reference isometric-ish camera (`CRPGCameraSettings`, `CameraRigState`, `IsometricCameraRig`, CameraRoot→YawPivot→PitchPivot→Camera); `IPlayerCommandSource`/`SelectCommand`/`MoveCommand` in `CRPG.Core` as the input-decoupling seam from spec §2; `PartyMovementService` and `PartyExplorationController` in `CRPG.Exploration` tying commands → party selection/movement. Combat movement (feet conversion, remaining-movement budget) intentionally deferred to the Combat phase.
- Phase 6 (Inventory/Equipment): `ItemDefinition`/`EquipmentSlotDefinition` (authored; slots are data so a ruleset can add its own without code changes) and the runtime `ItemInstance`/`ItemLocation`; a single `PartyInventoryState` (no per-character backpacks) with `EquipmentService` (validated equip/unequip, displaces whatever occupied a slot back to shared inventory) and `LootService` (Take/Take All); `EncumbranceMode` + `IEncumbranceCalculator` with `Disabled`/`PartyCombined`/`PerCharacter` implementations. Items grant abilities via a bare `DefinitionId` (`GrantedAbilityId`) rather than the engine needing Potion/Scroll/Bomb subsystems — that hook activates once Abilities exists.
- Phase 3/13/14/15/17 (Abilities & effect pipeline, completing the original spec's core-model list): `GameEvent`/`GameEventContext`/`IGameEventBus` (trigger framework) in `CRPG.Core`; `FeatureDefinition` (the universal race/class/feat/item building block) and `FeatureModifier`/`FeatureModifierCollector` in `CRPG.Actors`, wired into `CharacterState.Features` and into `ConditionDefinition` (conditions now actually carry modifiers, closing a gap left open in Phase 2); `ICharacterRegistry`/`CharacterRegistry` so ability/rule code can resolve a `RuntimeEntityId` to a live `CharacterState` without knowing how characters are stored. In `CRPG.Abilities`: `AbilityDefinition` (tags, costs, targeting, a polymorphic `[SerializeReference]` effect list), `TargetingDefinition`/`TargetMode`/`TargetRelation` (min/max target counts enforce spec's "forced target selection"; a tag-based `TargetFilter` is deferred — needs creature tagging that doesn't exist until SRD content), `AbilityCost`, and ten `AbilityEffect`s built only on systems that already exist: `Damage`/`Heal` (roll dice, spend/restore a designated resource — no damage-type/resistance pipeline yet, that's Combat-phase), `ApplyCondition`/`RemoveCondition`, `SpendResource`/`RestoreResource`, `GrantFeature`/`RemoveFeature`, and the two composition effects `Sequence` and `Conditional`. `AbilityResolutionService` implements spec §17's pipeline from Confirm onward (CanUse check → consume resources → apply effects → publish `AbilityStarted`/`AbilityResolved` events); the earlier interactive steps (Begin Targeting, incremental validation while picking) are exposed as separate `CanUse`/`IsValidTargetSelection` calls for a UI layer to use, not built into `Execute` itself. Move/Teleport/Push/Pull, Make Attack/Saving Throw/Ability Check, Summon/Create Area, and Set World Flag are explicitly deferred — they need Navigation-in-Abilities, Combat's roll-vs-DC resolution, spawning, and WorldState respectively, none of which exist yet.

- Phase 4 (Combat, spec §27-30): `Combatant`/`CombatEncounter` (initiative-sorted turn order, round tracking, mid-encounter removal); `IInitiativeRule`/`DefaultInitiativeRule` (rolls 1d20 plus whatever a ruleset tags with the `"Initiative"` query key via the existing `FeatureModifierCollector` — no hardcoded Dexterity); `TurnResourceSet` (restores whichever ResourceDefinitions a ruleset uses as Action/Bonus Action/Reaction/Movement to full at the start of a turn); `CombatEncounterService` orchestrating start/end-turn/end-combat and publishing `CombatStarted`/`TurnStarted`/`TurnEnded`/`CombatEnded`; the reaction system (`ReactionOpportunity`, `IReactionDecisionProvider` + `AlwaysDecline`/`FirstEligible` reference implementations, `ReactionService` filtering candidates by the `Reaction` tag and `CanUse`, deferring to `AbilityResolutionService.Execute` for actual cost/effect resolution). New structured log entries completing spec §35's list: `DamageLogEntry`, `ConditionLogEntry`, `DeathLogEntry`, `TurnLogEntry`. `AbilityExecutionContext` now carries an `IGameEventBus`; `DamageEffect` publishes `BeforeDamage` (with the rolled amount in `Data["Amount"]`, so a future resistance/vulnerability handler can rewrite it without `DamageEffect` knowing about damage types), `AfterDamage`, and `CreatureDroppedToZeroHP`; `ApplyConditionEffect`/`RemoveConditionEffect` publish `ConditionApplied`/`ConditionRemoved`. Deliberately not built: true suspend/resume of an interrupted action while a reaction resolves (needs an async attack/turn pipeline that doesn't exist yet — `ReactionService` covers "find eligible reactions, decide, execute" for that pipeline to call into later), and what zero HP actually means (unconscious vs. dead vs. removed) — left as a ruleset decision, not hardcoded into `CombatEncounter`.

- Phase 5 (Character Creation, spec §8-10): the generic choice-requirement system — `ChoiceType`, `ChoiceRequirement` (a stable id, candidate `Options`, an optional `FilterTag` for dynamically-resolved pools, a required `Count`), now carried by `FeatureDefinition.Choices`. `RaceDefinition`/`BackgroundDefinition` (flat feature grants — subraces aren't a separate type, they're just a `SelectFeature` choice offering candidate feature options) and `LeveledFeatureDefinition`/`ClassLevelGrant`/`ClassDefinition`/`SubclassDefinition` (level-gated feature grants, `ClassDefinition` adding hit die/primary stats/saving throw proficiencies) and `SkillDefinition`. `CharacterBuildPlan` (pending vs. resolved choices — resolving one can surface more, e.g. a chosen subrace introducing its own spell choice) and `CharacterBuildService` (`RefreshPendingChoices` walks race/class/subclass/background plus resolved `SelectFeature` choices to find more `ChoiceRequirement`s; `Build` throws while any are pending, otherwise produces a real `CharacterState` with stats/features/resources/proficiencies applied — `SelectSkill`/`SelectProficiency`/`SelectLanguage` choices map onto `CharacterState.GrantProficiency`, while `SelectSpell`/`SelectEquipment`/`SelectAbilityScore`/etc. are recorded on the plan but not yet auto-applied, pending the known-spell-list/starting-kit/level-up systems they need). Ability score generation (`IAbilityScoreGenerationMethod`): `StandardArray`, `RandomRolls` (4d6 drop lowest), `PointBuy` (real 5e cost table, budget-validated), `ManualEntry`. `FeatDefinition` and dedicated `LanguageDefinition`/`DamageTypeDefinition`/`CreatureTypeDefinition`/`TerrainDefinition` types are deliberately not built yet — nothing in the immediate Fighter 1-3 content needs them, and `ChoiceRequirement.Options` works with bare `DefinitionId`s regardless of whether a concrete definition type exists yet for what they'll eventually resolve to.

- Phase 7 (first real SRD5 content): a minimal "Human Fighter, levels 1-3" slice authored as 35 real `.asset` files under `Rules/SRD5e2014/Content/` — `race-human` (+1 all six stats), `class-fighter` (d10 hit die, STR/CON saves, level 1: Fighting Style choice between Defense/Archery + Second Wind + a 2-of-8 skill choice, level 2: Action Surge), `subclass-champion` (level 3: Improved Critical, authored as a `CriticalRange` modifier even though no attack-resolution system consumes it yet), `background-soldier`. `Second Wind` and `Action Surge` are real, working `AbilityDefinition`s built entirely from existing systems (`HealEffect` for Second Wind's 1d10+3; `RestoreResourceEffect` granting back an Action for Action Surge) — no new engine code needed. Authored via a one-time reflection-based Editor script (`TestProject/Assets/Editor/FighterSampleContentAuthor.cs`, dogfood-only, not shipped) rather than by hand in the Inspector. Deliberately not built: the SRD5 derived-stat math layer (ability modifiers, AC formula, attack bonus, save DCs) and 4 of 6 Fighting Styles (Dueling/Protection/Two-Weapon/Great Weapon Fighting need reaction abilities or dice-reroll effects not yet built) — see spec's own "Derived-stat rule engine" as the next real ruleset-code undertaking.
- `Timeline`/`ITimeline` in `CRPG.Core`, **replacing spec §48's WorldState design entirely** (a deliberate deviation from the spec, decided in this session): rather than a mutable dictionary of current flags, the single source of truth for world/story state is now an ordered, append-only log of `TimelineEvent`s (`Record(key, TimelineValue, amount, source)`), queried either for current-value semantics (`HasOccurred`, `GetLatest`) or history semantics flat WorldState couldn't express (`Sum`/`CountOccurrences` for reputation-style tallies, `OccurredBefore`/`OccurredAfter` for ordering-sensitive branching). `TimelineValue` mirrors WorldState's planned Bool/Int/Float/String/Entity kinds (as `Flag`/`Number`/`Text`/`EntityRef`). Every scalar query is backed by an incrementally-maintained projection (latest/sum/count/first-sequence per key) rather than scanning the log, since the user expects heavy query bursts at load time and right after dialogue resolves; only the rarer `AllEvents(key)` does a filtered scan. Deliberately plain C# (no `[SerializeField]`/`[Serializable]`) — this is runtime infrastructure like `GameEventBus`, not an authored asset type like `AbilityDefinition`, so it doesn't need Inspector-serialization treatment. Kept decoupled from `IGameEventBus` by design (transient reactive triggers vs. deliberate narrative record-keeping); nothing stops code from doing both when a moment is both mechanically and narratively significant. Dialogue's own node graph (a `Record Event` node type, `Branch`/`Condition` nodes gaining Timeline queries) is not built yet — this lands the query engine those nodes will call into.

- Dialogue system (`CRPG.Dialogue`, spec §36-40), the last core-model phase and — per the user — the most important one ("the literal interface into the story"): a node-graph `DialogueDefinition` (a `DefinitionAsset`) holding a `[SerializeReference] List<DialogueNode>`, each node identified by a stable string `NodeId` rather than a direct object reference (same rationale as `ChoiceRequirement`'s `DefinitionId` options — keeps `[SerializeReference]` graphs simple, no cycle/reference-serialization concerns). Six node types: `LineNode` (speaker + text, `Advance()`), `ChoiceNode`/`ChoiceOption` (`ChooseOption(index)`), `BranchNode` (evaluates directly against `ITimeline` — `HasOccurred`/`NotOccurred`/`SumAtLeast`/`SumAtMost`/`CountAtLeast`/`OccurredBefore`, using the Timeline query surface built in the prior phase exactly as designed), `CheckNode` (a deliberate merge of spec's separate Skill Check and Ability Check nodes into one, since the underlying mechanic — roll a d20, add whatever a query key resolves to, compare to a DC — is identical regardless of what the key is called), `ActionNode` (`[SerializeReference] DialogueAction`, with `RecordEventAction` writing to the Timeline and `GiveItemAction` adding to `PartyInventoryState` as the two built-in actions), and `EndNode`. `DialogueRunner` walks the graph and auto-"settles" through any run of `Branch`/`Action` nodes (no player input needed) until it lands on a Line, Choice, Check, or End — so callers never need to special-case "skip past the invisible plumbing nodes." `DialogueCheckResolver` implements four checker-selection policies via `CheckPerformer`: `ActiveCharacter`, `BestPartyMember` (gathers each party member's modifiers for the check's query key through the existing `FeatureModifierCollector` and picks the highest — same pattern as initiative and ability-score bonuses, no new resolution mechanism needed), `SpecificSpeaker` (the conversation's NPC rolls, using its own `CharacterState` if it has one), and `EntireParty` (every current party member rolls independently; succeeds if at least half do — the 5e "group check" convention, framed as roll-aggregation logic rather than a 5e-specific rule so it stays in the ruleset-agnostic engine). `PerformCheck()` returns a `DialogueCheckOutcome` (`Success` + every `RollResult`, since `EntireParty` rolls more than once) rather than a single `RollResult`. `ChoiceOption` can optionally be gated by the same Timeline condition `BranchNode` uses (extracted into a shared `TimelineConditionEvaluator`) — `DialogueRunner.GetVisibleOptions()` filters to currently-visible options and `ChooseOption` throws if the caller picks a gated, currently-hidden one. Deliberately still deferred: `StartQuest`/`OpenStore` action kinds (need Quests/Store systems that don't exist yet). Verified with 22 EditMode tests total for Dialogue (142/142 package-wide), including a full `Line → Choice → Check → Action → End` integration test matching the spec's own "[Persuasion DC 15] Let us pass" example.

- Utility AI -- an Infinite Axis Utility System (IAUS) -- for NPC combat turns (`CRPG.AI`, new assembly; spec §49), plus a complementary Influence Map for spatial hazard/terrain reasoning (`CRPG.Core/Spatial/`). `Consideration` (an `InputKey` string + inline `AnimationCurve` + `Weight`, evaluated and combined via `UtilityMath.CombineScores` -- multiply every score together so a 0 vetoes the whole Decision, then apply IAUS's standard compensation factor so stacking several good-but-imperfect scores doesn't decay toward zero from the multiply alone) is nested authored data on a `BehaviorDefinition` (a Behavior = "use this ability," referencing both the `AbilityDefinition` and its own considerations by `DefinitionId`, same cross-reference convention as everywhere else in the toolkit), bundled into a `BehaviorSetDefinition` per creature archetype ("Goblin Warrior" = [MeleeAttack, Retreat]). `UtilityAIDecisionProvider : ITurnDecisionProvider` is the Brain -- not an asset, just the code that evaluates a Behavior Set each turn (mirrors `IReactionDecisionProvider`'s shape) -- enumerating every Behavior × valid-target Decision (reusing the ability's own `Targeting` for candidate/range filtering, scoped to `MaxTargets == 1` for this pass), scoring each, and returning the winner as a `TurnDecision`; a full `UtilityDecisionLogEntry` trace (every Decision considered, its score, which won) reuses the existing `ICombatLog` structured-logging pattern -- the actual tune-a-curve/replay/read-the-trace debugging loop this class of AI needs, rather than a bespoke tool. `ConsiderationInputRegistry` resolves an `InputKey` to a raw float the same way `FeatureModifier.QueryKey` resolves a rule query -- built-ins (`Distance`, `Self`/`TargetResourcePercent:<id>`, `RandomChance`, `InfluenceMap:<layer>:Self`/`Target`) cover only what's derivable from already-generic state; a ruleset/game registers its own. `InfluenceMap`/`InfluenceSource` (battlefield-scoped runtime state, not a `DefinitionAsset` -- like `LootContainerState`/`CombatEncounter`) let a named layer ("Danger", "DifficultTerrain") accumulate falloff-weighted contributions from hazard sources, sampled by the two new Consideration inputs above; sources can be hand-placed by whoever sets up an encounter or created automatically by a new `CreateInfluenceSourceEffect : AbilityEffect` when a spell resolves (Fireball leaves fire, Web leaves difficult terrain). `InfluenceMap`/`InfluenceSource`/`IPositionProvider` live in `CRPG.Core`, not `CRPG.AI` -- both `CRPG.Abilities` (for the new effect) and `CRPG.AI` (for the Consideration inputs) need them, and `CRPG.AI` already depends on `CRPG.Abilities`, so putting them in `CRPG.AI` would create a circular assembly reference. `AbilityExecutionContext`/`AbilityResolutionService` gained two new optional fields/constructor params (`Positions`, `InfluenceMap`) to carry this through to effects that need them -- backward compatible, existing call sites unaffected; found and fixed a related latent bug while there, `ConditionalEffect`'s filtered sub-context was silently dropping `EventBus` (now threads all of `EventBus`/`Positions`/`InfluenceMap` through). Deliberately deferred: AoE/multi-target Decision scoring (needs cluster-placement heuristics), movement/positioning Behaviors (no in-turn move budget wired in `CombatEncounterService` yet -- the map itself has no movement dependency, so this is a clean fast-follow), Team/Faction concepts in `CRPG.Combat` (the Brain takes enemy/ally candidate lists externally instead), shared/reusable curve assets (curves stay inline on each Consideration, using Unity's built-in `AnimationCurve` Inspector widget for free visual editing), and async decision timing (stays synchronous -- no combat UI exists yet to pace a "thinking delay" against). `InfluenceSource` has no built-in duration/auto-expiry: `ConditionInstance.RemainingDuration` already has the identical gap (nothing anywhere ticks it down), so this doesn't quietly half-solve it just for influence zones -- a source persists until something explicitly calls `RemoveSource`. Verified with 22 new EditMode tests (206/206 total), including a source's falloff-vs-distance math, a 0-scoring Consideration correctly vetoing a Decision, and an `InfluenceMap` Consideration correctly flipping which target wins.

### Fixed (retrofit)
- `DiceExpression` was a `readonly struct` with get-only auto-properties and no `[SerializeField]` backing fields -- it worked as a runtime-constructed value (all of Phase 1's tests passed) but was silently **not actually authorable in the Inspector**, since Unity's serializer can't write into readonly fields or bare properties. Converted to a plain `struct` with real `[SerializeField]` fields (same pattern as `DefinitionId`), needed now that ability damage/healing amounts are dice expressions designers type into the Inspector. Public API and behavior unchanged; full suite re-verified green after the change.
- `CharacterBuildService.Build` never actually applied ability-score bonus modifiers (e.g. Human's +1 to all six stats) — the mechanism (FeatureModifier keyed by the stat's own DefinitionId, gathered via `FeatureModifierCollector`) had been designed but the code was never written. Found via the Fighter demo (STR stayed at 16 instead of 17); fixed by adding the gather-and-apply step after feature granting. Full package suite re-verified green (102/102) after the fix, not just the demo.
- `CampDemo.unity`'s `UIDocument.panelSettings` was silently null in the saved scene (`fileID: 0`) even though `BuildCampDemoScene` assigned it before saving — same root cause as the earlier `AssetDatabase.CreateAsset`/`SetDirty` bug: `CreateAsset` + `SaveAssets` on a *just-created* `PanelSettings` asset can invalidate the in-memory reference used immediately afterward. Fixed by reloading the asset from disk via `AssetDatabase.LoadAssetAtPath` after saving it, before assigning it to the `UIDocument`. Separately, the newly-created `PanelSettings` also had no theme assigned (a `PanelSettings` with no theme renders nothing) — the script now auto-assigns Unity's built-in default runtime theme by its known guid, only when one isn't already set (so it won't clobber a manually-chosen theme). Found because the user hit "nothing displaying," diagnosed it live, and fixed it manually in-editor first; this closes the gap in the *authoring script* so regenerating the scene doesn't reintroduce it.
- **The fix above was incomplete** -- discovered while building the Store demo scene, which reused the exact same (by-then-extracted) `GetOrCreateDemoPanelSettings` helper and still produced a scene with `UIDocument.panelSettings: {fileID: 0}`. The user's earlier live in-editor fix had only ever patched the *saved scene*, never the authoring script itself, so the underlying bug was still there waiting to bite the next scene. Root cause was different from (and in addition to) the one above: `EditorSceneManager.NewScene(...)` unloads objects not referenced by any active scene/root, which silently turns an already-loaded asset reference into a fake-null "missing object" even with no intervening `CreateAsset`/`SaveAssets` call -- so loading/creating the `PanelSettings` *before* `NewScene` was itself unsafe, regardless of the reload-after-save fix. Fixed by moving `GetOrCreateDemoPanelSettings` to run *after* `NewScene`, immediately before the reference is used. Reran `BuildCampDemoScene` after the fix and confirmed it now reproduces the same valid `panelSettings` reference the user had set by hand, closing the gap at the actual root this time; `BuildStoreDemoScene` was verified the same way from a clean run. 157/157 tests still passing (this bug was never in package code, only the dogfood scene-authoring script).
