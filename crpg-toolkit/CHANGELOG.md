# Changelog

All notable changes to this package are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## [0.1.0] - 2026-09-06

### Added
- Initial package scaffolding: assembly layout for `Runtime/`, `Rules/`, `Editor/`, `Integrations/`, `Tests/`, `Samples~/`.
- Phase 1 foundation: `DefinitionId`, `IRulesDatabase` (+ `RulesDatabase` default implementation), `RuleQuery<T>`/`NumericRuleQuery`, modifier pipeline, dice service, structured combat log base types.
- Phase 2 (Actors) start: `StatDefinition`, `ResourceDefinition`, `ConditionDefinition`, and the runtime `CharacterState` (`StatBlock`, `ResourceState`, `ConditionInstance`) — equipment intentionally deferred to the Inventory assembly.
- Phase 3 (Party) start: `PartyState` (membership, click/shift-click/drag-box selection, active-vs-selected, linked groups for splitting the party) and formation solving (`IFormationSolver` + `Cluster`/`Line`/`Column`/`Wedge` implementations, `PartyMoveOrder`) — NavMesh/Navigation wiring intentionally deferred.
- Phase 3 (Exploration/Navigation/Camera): `INavMeshService`/`NavMeshService` (verified against a real baked NavMesh — see Verified below) and `IMovable`/`NavMeshCharacterMotor`; the reference isometric-ish camera (`CRPGCameraSettings`, `CameraRigState`, `IsometricCameraRig`, CameraRoot→YawPivot→PitchPivot→Camera); `IPlayerCommandSource`/`SelectCommand`/`MoveCommand` in `CRPG.Core` as the input-decoupling seam from spec §2; `PartyMovementService` and `PartyExplorationController` in `CRPG.Exploration` tying commands → party selection/movement. Combat movement (feet conversion, remaining-movement budget) intentionally deferred to the Combat phase.
- Phase 6 (Inventory/Equipment): `ItemDefinition`/`EquipmentSlotDefinition` (authored; slots are data so a ruleset can add its own without code changes) and the runtime `ItemInstance`/`ItemLocation`; a single `PartyInventoryState` (no per-character backpacks) with `EquipmentService` (validated equip/unequip, displaces whatever occupied a slot back to shared inventory) and `LootService` (Take/Take All); `EncumbranceMode` + `IEncumbranceCalculator` with `Disabled`/`PartyCombined`/`PerCharacter` implementations. Items grant abilities via a bare `DefinitionId` (`GrantedAbilityId`) rather than the engine needing Potion/Scroll/Bomb subsystems — that hook activates once Abilities exists.
- Phase 3/13/14/15/17 (Abilities & effect pipeline, completing the original spec's core-model list): `GameEvent`/`GameEventContext`/`IGameEventBus` (trigger framework) in `CRPG.Core`; `FeatureDefinition` (the universal race/class/feat/item building block) and `FeatureModifier`/`FeatureModifierCollector` in `CRPG.Actors`, wired into `CharacterState.Features` and into `ConditionDefinition` (conditions now actually carry modifiers, closing a gap left open in Phase 2); `ICharacterRegistry`/`CharacterRegistry` so ability/rule code can resolve a `RuntimeEntityId` to a live `CharacterState` without knowing how characters are stored. In `CRPG.Abilities`: `AbilityDefinition` (tags, costs, targeting, a polymorphic `[SerializeReference]` effect list), `TargetingDefinition`/`TargetMode`/`TargetRelation` (min/max target counts enforce spec's "forced target selection"; a tag-based `TargetFilter` is deferred — needs creature tagging that doesn't exist until SRD content), `AbilityCost`, and ten `AbilityEffect`s built only on systems that already exist: `Damage`/`Heal` (roll dice, spend/restore a designated resource — no damage-type/resistance pipeline yet, that's Combat-phase), `ApplyCondition`/`RemoveCondition`, `SpendResource`/`RestoreResource`, `GrantFeature`/`RemoveFeature`, and the two composition effects `Sequence` and `Conditional`. `AbilityResolutionService` implements spec §17's pipeline from Confirm onward (CanUse check → consume resources → apply effects → publish `AbilityStarted`/`AbilityResolved` events); the earlier interactive steps (Begin Targeting, incremental validation while picking) are exposed as separate `CanUse`/`IsValidTargetSelection` calls for a UI layer to use, not built into `Execute` itself. Move/Teleport/Push/Pull, Make Attack/Saving Throw/Ability Check, Summon/Create Area, and Set World Flag are explicitly deferred — they need Navigation-in-Abilities, Combat's roll-vs-DC resolution, spawning, and WorldState respectively, none of which exist yet.

- Phase 4 (Combat, spec §27-30): `Combatant`/`CombatEncounter` (initiative-sorted turn order, round tracking, mid-encounter removal); `IInitiativeRule`/`DefaultInitiativeRule` (rolls 1d20 plus whatever a ruleset tags with the `"Initiative"` query key via the existing `FeatureModifierCollector` — no hardcoded Dexterity); `TurnResourceSet` (restores whichever ResourceDefinitions a ruleset uses as Action/Bonus Action/Reaction/Movement to full at the start of a turn); `CombatEncounterService` orchestrating start/end-turn/end-combat and publishing `CombatStarted`/`TurnStarted`/`TurnEnded`/`CombatEnded`; the reaction system (`ReactionOpportunity`, `IReactionDecisionProvider` + `AlwaysDecline`/`FirstEligible` reference implementations, `ReactionService` filtering candidates by the `Reaction` tag and `CanUse`, deferring to `AbilityResolutionService.Execute` for actual cost/effect resolution). New structured log entries completing spec §35's list: `DamageLogEntry`, `ConditionLogEntry`, `DeathLogEntry`, `TurnLogEntry`. `AbilityExecutionContext` now carries an `IGameEventBus`; `DamageEffect` publishes `BeforeDamage` (with the rolled amount in `Data["Amount"]`, so a future resistance/vulnerability handler can rewrite it without `DamageEffect` knowing about damage types), `AfterDamage`, and `CreatureDroppedToZeroHP`; `ApplyConditionEffect`/`RemoveConditionEffect` publish `ConditionApplied`/`ConditionRemoved`. Deliberately not built: true suspend/resume of an interrupted action while a reaction resolves (needs an async attack/turn pipeline that doesn't exist yet — `ReactionService` covers "find eligible reactions, decide, execute" for that pipeline to call into later), and what zero HP actually means (unconscious vs. dead vs. removed) — left as a ruleset decision, not hardcoded into `CombatEncounter`.

- Phase 5 (Character Creation, spec §8-10): the generic choice-requirement system — `ChoiceType`, `ChoiceRequirement` (a stable id, candidate `Options`, an optional `FilterTag` for dynamically-resolved pools, a required `Count`), now carried by `FeatureDefinition.Choices`. `RaceDefinition`/`BackgroundDefinition` (flat feature grants — subraces aren't a separate type, they're just a `SelectFeature` choice offering candidate feature options) and `LeveledFeatureDefinition`/`ClassLevelGrant`/`ClassDefinition`/`SubclassDefinition` (level-gated feature grants, `ClassDefinition` adding hit die/primary stats/saving throw proficiencies) and `SkillDefinition`. `CharacterBuildPlan` (pending vs. resolved choices — resolving one can surface more, e.g. a chosen subrace introducing its own spell choice) and `CharacterBuildService` (`RefreshPendingChoices` walks race/class/subclass/background plus resolved `SelectFeature` choices to find more `ChoiceRequirement`s; `Build` throws while any are pending, otherwise produces a real `CharacterState` with stats/features/resources/proficiencies applied — `SelectSkill`/`SelectProficiency`/`SelectLanguage` choices map onto `CharacterState.GrantProficiency`, while `SelectSpell`/`SelectEquipment`/`SelectAbilityScore`/etc. are recorded on the plan but not yet auto-applied, pending the known-spell-list/starting-kit/level-up systems they need). Ability score generation (`IAbilityScoreGenerationMethod`): `StandardArray`, `RandomRolls` (4d6 drop lowest), `PointBuy` (real 5e cost table, budget-validated), `ManualEntry`. `FeatDefinition` and dedicated `LanguageDefinition`/`DamageTypeDefinition`/`CreatureTypeDefinition`/`TerrainDefinition` types are deliberately not built yet — nothing in the immediate Fighter 1-3 content needs them, and `ChoiceRequirement.Options` works with bare `DefinitionId`s regardless of whether a concrete definition type exists yet for what they'll eventually resolve to.

- Phase 7 (first real SRD5 content): a minimal "Human Fighter, levels 1-3" slice authored as 35 real `.asset` files under `Rules/SRD5e2014/Content/` — `race-human` (+1 all six stats), `class-fighter` (d10 hit die, STR/CON saves, level 1: Fighting Style choice between Defense/Archery + Second Wind + a 2-of-8 skill choice, level 2: Action Surge), `subclass-champion` (level 3: Improved Critical, authored as a `CriticalRange` modifier even though no attack-resolution system consumes it yet), `background-soldier`. `Second Wind` and `Action Surge` are real, working `AbilityDefinition`s built entirely from existing systems (`HealEffect` for Second Wind's 1d10+3; `RestoreResourceEffect` granting back an Action for Action Surge) — no new engine code needed. Authored via a one-time reflection-based Editor script (`TestProject/Assets/Editor/FighterSampleContentAuthor.cs`, dogfood-only, not shipped) rather than by hand in the Inspector. Deliberately not built: the SRD5 derived-stat math layer (ability modifiers, AC formula, attack bonus, save DCs) and 4 of 6 Fighting Styles (Dueling/Protection/Two-Weapon/Great Weapon Fighting need reaction abilities or dice-reroll effects not yet built) — see spec's own "Derived-stat rule engine" as the next real ruleset-code undertaking.
- `Timeline`/`ITimeline` in `CRPG.Core`, **replacing spec §48's WorldState design entirely** (a deliberate deviation from the spec, decided in this session): rather than a mutable dictionary of current flags, the single source of truth for world/story state is now an ordered, append-only log of `TimelineEvent`s (`Record(key, TimelineValue, amount, source)`), queried either for current-value semantics (`HasOccurred`, `GetLatest`) or history semantics flat WorldState couldn't express (`Sum`/`CountOccurrences` for reputation-style tallies, `OccurredBefore`/`OccurredAfter` for ordering-sensitive branching). `TimelineValue` mirrors WorldState's planned Bool/Int/Float/String/Entity kinds (as `Flag`/`Number`/`Text`/`EntityRef`). Every scalar query is backed by an incrementally-maintained projection (latest/sum/count/first-sequence per key) rather than scanning the log, since the user expects heavy query bursts at load time and right after dialogue resolves; only the rarer `AllEvents(key)` does a filtered scan. Deliberately plain C# (no `[SerializeField]`/`[Serializable]`) — this is runtime infrastructure like `GameEventBus`, not an authored asset type like `AbilityDefinition`, so it doesn't need Inspector-serialization treatment. Kept decoupled from `IGameEventBus` by design (transient reactive triggers vs. deliberate narrative record-keeping); nothing stops code from doing both when a moment is both mechanically and narratively significant. Dialogue's own node graph (a `Record Event` node type, `Branch`/`Condition` nodes gaining Timeline queries) is not built yet — this lands the query engine those nodes will call into.
- A `FighterDemoBootstrap` MonoBehaviour + test scene (`TestProject/Assets/Scenes/FighterDemo.unity`, dogfood-only) proving the whole pipeline end to end at runtime: registers the authored content into a `RulesDatabase`, drives `CharacterBuildPlan`/`CharacterBuildService` (auto-resolving every remaining choice generically — no special-cased "this is the fighting style choice" logic), and displays the built character's stats/features/proficiencies on screen. The visual character model (`Superhero_Male_FullBody` from the dogfooding asset pack) is placed directly in the saved scene, visible immediately without pressing Play. Verified with an actual rendered screenshot, not just logs — see Verified below.
- Rest/Camp system, decided in a design conversation with the user (2026-09-07): Short Rest is callable from anywhere with no gating; Long Rest only happens from behind a Camp menu; both are **party-scoped** (one action rests everyone, not per-character). `RestTrigger` (`None`/`ShortRest`/`LongRest`/`Both`) added to `ResourceDefinition` — the one piece of restoration policy the engine owns generically, since "restores on a rest" is common enough across rulesets to deserve a real field. `RestService` (`CRPG.Actors`) restores every resource on each given party member whose trigger matches, then publishes exactly one `ShortRest`/`LongRest` event for the whole party (not per-member — "the party rested" is one narrative beat). Second Wind and Action Surge (authored in the Fighter content pass) are now correctly tagged `Both`/`Both`, and Hit Points is tagged `LongRest` — closing a gap where their "restores on a short or long rest" description was previously just text, not implemented.
- Camp screen (`CRPG.UI`), the first real UI in the project, kept deliberately minimal per the user's "KISS" direction — a functional placeholder (party list + equipped slots + HP + one Rest button), not a full paper-doll art layout, with the Presenter/View split (spec §2) built properly from day one so a polished view can replace `CampView` later without touching logic: `CampPresenter` (pure C#, no UI Toolkit dependency — `GetPartyMembers()`/`ConfirmLongRest()`) and `CampView` (a `UIDocument`-based MonoBehaviour, built procedurally in code rather than hand-authored `.uxml`/`.uss`, to avoid blind-authoring risk). New `PartyMemberSummary`/`EquippedSlotSummary` DTOs decouple the view from raw `CharacterState`/`EquipmentService` internals. Also added 2 `EquipmentSlotDefinition`s (Main Hand, Armor) and 2 `ItemDefinition`s (Longsword, Chain Shirt) to the Fighter sample content so the screen has real equipped gear to display, and a `CampDemoBootstrap` + scene (`TestProject/Assets/Scenes/CampDemo.unity`, dogfood-only) building a 3-member party from the existing Fighter content to exercise it.
- Dialogue system (`CRPG.Dialogue`, spec §36-40), the last core-model phase and — per the user — the most important one ("the literal interface into the story"): a node-graph `DialogueDefinition` (a `DefinitionAsset`) holding a `[SerializeReference] List<DialogueNode>`, each node identified by a stable string `NodeId` rather than a direct object reference (same rationale as `ChoiceRequirement`'s `DefinitionId` options — keeps `[SerializeReference]` graphs simple, no cycle/reference-serialization concerns). Six node types: `LineNode` (speaker + text, `Advance()`), `ChoiceNode`/`ChoiceOption` (`ChooseOption(index)`), `BranchNode` (evaluates directly against `ITimeline` — `HasOccurred`/`NotOccurred`/`SumAtLeast`/`SumAtMost`/`CountAtLeast`/`OccurredBefore`, using the Timeline query surface built in the prior phase exactly as designed), `CheckNode` (a deliberate merge of spec's separate Skill Check and Ability Check nodes into one, since the underlying mechanic — roll a d20, add whatever a query key resolves to, compare to a DC — is identical regardless of what the key is called), `ActionNode` (`[SerializeReference] DialogueAction`, with `RecordEventAction` writing to the Timeline and `GiveItemAction` adding to `PartyInventoryState` as the two built-in actions), and `EndNode`. `DialogueRunner` walks the graph and auto-"settles" through any run of `Branch`/`Action` nodes (no player input needed) until it lands on a Line, Choice, Check, or End — so callers never need to special-case "skip past the invisible plumbing nodes." `DialogueCheckResolver` implements four checker-selection policies via `CheckPerformer`: `ActiveCharacter`, `BestPartyMember` (gathers each party member's modifiers for the check's query key through the existing `FeatureModifierCollector` and picks the highest — same pattern as initiative and ability-score bonuses, no new resolution mechanism needed), `SpecificSpeaker` (the conversation's NPC rolls, using its own `CharacterState` if it has one), and `EntireParty` (every current party member rolls independently; succeeds if at least half do — the 5e "group check" convention, framed as roll-aggregation logic rather than a 5e-specific rule so it stays in the ruleset-agnostic engine). `PerformCheck()` returns a `DialogueCheckOutcome` (`Success` + every `RollResult`, since `EntireParty` rolls more than once) rather than a single `RollResult`. `ChoiceOption` can optionally be gated by the same Timeline condition `BranchNode` uses (extracted into a shared `TimelineConditionEvaluator`) — `DialogueRunner.GetVisibleOptions()` filters to currently-visible options and `ChooseOption` throws if the caller picks a gated, currently-hidden one. Deliberately still deferred: `StartQuest`/`OpenStore` action kinds (need Quests/Store systems that don't exist yet). Verified with 22 EditMode tests total for Dialogue (142/142 package-wide), including a full `Line → Choice → Check → Action → End` integration test matching the spec's own "[Persuasion DC 15] Let us pass" example.

- Store system (`CRPG.Inventory`/`CRPG.UI`, spec's shop design from an earlier session): currency is not a new mechanism -- it's a regular stackable `ItemDefinition` (e.g. "Gold Piece") living in the party's shared inventory like anything else. `ItemDefinition` gained a `BaseValue` field (what one unit is worth in whatever item a `StoreService` is configured to treat as currency). `StoreInventoryState` (a plain runtime object like `LootContainerState`, not an authored asset -- a shop's stock is world/save state, not reusable data) holds `StoreListing`s (`ItemId` + `Quantity`, negative meaning unlimited -- the KISS default, since it needs no restocking-timer mechanic at all). `StoreService` implements `TryBuy`/`TrySell` (bool-returning, no side effects on failure -- insufficient funds/out-of-stock/not-owned all just return false) plus `GetBuyPrice`/`GetSellPrice`/`GetCurrencyTotal`, mirroring `EquipmentService`/`LootService`'s validated-command style. `StorePresenter`/`StoreView` follow the same Presenter/View split as `CampPresenter`/`CampView` -- a minimal functional buy/sell screen, not a polished shop layout. Dialogue's deferred `OpenStore` action kind is now built: `DialogueContext` gained an optional `Store` (the NPC's shop, if any) and a `StoreOpenRequested` flag; `OpenStoreAction` needs no authored fields of its own -- it just calls `context.RequestOpenStore()`, and the host polls the flag after driving the runner the same way it already checks `CurrentNode`/`IsComplete`. Only `StartQuest` remains as a deferred Dialogue action kind, pending Quests. Verified with 15 new EditMode tests (157/157 total) plus a `StoreDemo.unity` dogfood scene (a merchant selling Healing Potions/Longswords/Chain Shirts against a starting purse of Gold Pieces).

- Quest framework (`CRPG.Quests`, spec §47): `QuestDefinition` (a `DefinitionAsset` with a display name/description and a list of `QuestObjectiveDefinition`s -- id, display name, `QuestObjectiveType` (`ReachLocation`/`TalkTo`/`Kill`/`Collect`/`Interact`/`SetFlag`/`Custom`, kept for authoring/display only), a Timeline `TrackingKey`, and a `TargetCount`). Every objective type resolves identically at runtime -- `QuestService.RefreshProgress` just checks `ITimeline.CountOccurrences(TrackingKey) >= TargetCount` -- so the type never branches completion logic; whatever produces a countable moment (a kill, a pickup, a conversation, a future Interaction/Navigation trigger) only needs to call `Timeline.Record` with the matching key, proven directly by `QuestDialogueIntegrationTests`: a "Talk To" objective completes from a Dialogue `RecordEventAction` with zero Quests-side knowledge of Dialogue (`CRPG.Quests` references only `CRPG.Core`/`CRPG.Rules`). `QuestService.StartQuest`/`RefreshProgress` publish `QuestStarted`/`QuestObjectiveCompleted` (once per objective, not on every refresh)/`QuestCompleted` through the existing `IGameEventBus`, optional like `RestService`'s event bus param. Quests complete only once *every* objective does (AND semantics, no optional/alternative objectives -- KISS). "Objectives listen for gameplay events rather than polling Update" (spec) is satisfied at the integration level: `RefreshProgress` is meant to be called in reaction to whatever just happened, not on a timer. `QuestLog` (party-scoped, like the shared inventory) and `QuestLogPresenter`/`QuestObjectiveSummary`/`QuestSummary` (`CRPG.UI`) exist as a pure data layer for a future journal screen, authored ahead of that consumer the same way Champion's Improved Critical was authored ahead of attack resolution -- no `QuestLogView` yet, and no dogfood scene for this phase (nothing about bookkeeping progress needs a visual to prove out the way Camp/Store's screens did). Verified with 10 new EditMode tests (167/167 total).

- Save system (`CRPG.Saving`, spec §51), completing the user's Store → Quests → Save sequence: `SaveData` (a plain `[Serializable]` root: `SaveHeader` + `PartySaveData` + `List<CharacterSaveData>` + inventory items + Timeline events + quests), serialized with `UnityEngine.JsonUtility` (`SaveService.ToJson`/`FromJson`) -- no new package dependency. Every DTO flattens the Dictionary/HashSet-shaped runtime state (`PartyState`, `CharacterState`, `PartyInventoryState`, `Timeline`, `QuestLog`) into plain Lists, since `JsonUtility` can't serialize either, and every definition reference is stored as its stable `DefinitionId`/`RuntimeEntityId` string rather than an object reference, per spec. `SaveService.Capture`/`Restore` are stateless static conversions (not a constructed service -- there's no long-lived collaborator to hold, just a transformation over whatever state is passed in); `Restore` is documented to expect fresh, empty containers, since e.g. `PartyState` has no "clear" operation. Two small additions to already-shipped `CRPG.Core` types made this possible without reflection: `RuntimeEntityId.FromString` (reconstructing a saved id, mirroring `DefinitionId`'s existing public constructor) and `Timeline.LoadEvent` (re-adds a `TimelineEvent` with its *original* `Sequence`/`Timestamp` preserved, unlike `Record` which always assigns both fresh -- backed by a new `TimelineEvent` constructor overload taking an explicit timestamp, with `Record`/`LoadEvent` now sharing one projection-update method so they can't drift). WorldState/SceneState/CombatState from spec's save-contents list are handled per the session's own established substitutions and scope: WorldState is Timeline (already the case everywhere else); SceneState and CombatState are deliberately not included -- there's no scene-persistence or combat-encounter-serialization system built to produce them, and spec itself marks CombatState "if supported." `ISaveMigration` (operates on raw JSON text, not `SaveData` objects, since an older save's schema may not even deserialize cleanly into today's DTOs) plus a `SaveMigrationRunner` that repeatedly applies whichever registered migration matches a save's current `FormatVersion` -- proven with a synthetic version-0-to-1 migration test, since no real prior format version exists yet to migrate from. Verified with 9 new EditMode tests (176/176 total), including a full `Capture → ToJson → FromJson → Restore` round trip.

- Dialogue player-facing UI (`DialoguePresenter`/`DialogueView`, `CRPG.UI/Dialogue/`), closing a gap found while planning the first real content demo: `CRPG.Dialogue` had been backend-only since it was built, exercised solely by EditMode tests, with no way to actually see or play a conversation the way Camp/Store got real screens. `DialoguePresenter` wraps a `DialogueRunner` (current speaker/line, visible choices with their original `Options` index so `ChooseOption` still gets the right one once any are Timeline-gated, check label/DC, `Advance`/`ChooseOption`/`PerformCheck`); `DialogueView` is a procedural `UIDocument` screen (speaker + text, a Continue/choice-buttons/Roll area depending on node type, closes on `IsComplete`) that rebuilds its interactive area as a fresh `VisualElement` every refresh rather than clearing/repopulating the same one in place -- the exact fix already learned from `StoreView`'s row-count bug applied proactively this time. Verified with 6 new EditMode tests.
- `SetStorePriceMultiplierAction` (`CRPG.Dialogue`), a small new `DialogueAction`: changes `DialogueContext.Store`'s price multipliers from within a conversation (e.g. a merchant's prices improving once a Timeline flag a `BranchNode` already checked is true) rather than via a `GameEventBus` subscription -- `GameEvent.QuestCompleted` carries no "which quest" data today, so a background subscriber can't tell quests apart anyway, and tying the price change to the exact dialogue line that notices it is more narratively honest besides. Required making `StoreInventoryState.BuyPriceMultiplier`/`SellPriceMultiplier` settable (previously constructor-only) so a shop's prices can react to world state after it already exists. A no-op if the NPC has no store. Verified with 3 new EditMode tests.
- First content demo built on top of the whole stack: a small "Oakhaven" town/cave/goblins slice (dogfood-only, `TestProject/Assets/Editor/OakhavenContentAuthor.cs` + `.../Scripts/OakhavenDemoBootstrap.cs` and friends), adapted from a user-supplied GDD after a full engine-capability and third-party-asset audit surfaced what the GDD assumed that doesn't exist yet (no attack-roll-vs-AC math, no combat UI/enemy AI, no goblin/hobgoblin/witch-doctor models, no premade buildings or cave tileset). Per the user's explicit scope choices: cave "encounters" are resolved as Dialogue `CheckNode`s (skill rolls vs a DC with branching Timeline consequences), not tactical combat; goblins are static-pose "Puglin" recolors used purely as set dressing; the town and cave are a rough scripted primitive blockout, not concept-art fidelity. Exercises Dialogue (5 new `DialogueDefinition`s, full branching per the GDD's Eldor/Griff scripts), Quests (`The Lost Heir`/`The Goblin Menace`), the Timeline-gated store price change, Save-compatible runtime state, and Exploration/Navigation end to end (a from-scratch `IPlayerCommandSource` implementation, `com.unity.ai.navigation`'s `NavMeshSurface` for baking -- the classic `UnityEditor.AI.NavMeshBuilder.BuildNavMesh()` API left the scene's `NavMeshData` reference empty once that package was installed, confirmed by direct in-Editor inspection after the fix). A small standalone `FeatureDefinition` grants flat "Skill:Athletics"/"Skill:Intimidation" bonuses for this demo's checks, since skill proficiency still doesn't translate into a numeric bonus anywhere in the engine (the SRD5 derived-stat layer remains unbuilt) -- added to the player character directly, not to the shared Fighter sample content. 185/185 tests passing (9 new: `DialoguePresenter` + `SetStorePriceMultiplierAction`/multiplier-setter coverage).
- Two dogfood-only Play-mode bugs found and fixed while the user tested the Oakhaven scene: (1) none of the `DialogueTriggerZone`/`TeleportTriggerZone` volumes ever fired -- Unity never raises `OnTriggerEnter`/`OnTriggerExit` between two colliders unless at least one side has a `Rigidbody`, and the player had a `NavMeshAgent` + collider but no `Rigidbody` (`NavMeshAgent` moves the transform directly and doesn't add one); fixed by giving the player a kinematic, no-gravity `Rigidbody` (kinematic so it doesn't fight the agent's own movement with physics forces). (2) Clicking a `DialogueView` button also fired a world-space move command underneath it, since there's no `EventSystem` in the scene and runtime UI Toolkit panels don't route through one on their own; fixed by having `MouseClickCommandSource` ask every open `UIDocument`'s panel directly (`panel.Pick(RuntimePanelUtils.ScreenToPanel(...))`) whether the click landed on UI before treating it as a world click. Both are TestProject-only fixes, no package code involved; 185/185 unaffected.

- Utility AI -- an Infinite Axis Utility System (IAUS) -- for NPC combat turns (`CRPG.AI`, new assembly; spec §49), plus a complementary Influence Map for spatial hazard/terrain reasoning (`CRPG.Core/Spatial/`). `Consideration` (an `InputKey` string + inline `AnimationCurve` + `Weight`, evaluated and combined via `UtilityMath.CombineScores` -- multiply every score together so a 0 vetoes the whole Decision, then apply IAUS's standard compensation factor so stacking several good-but-imperfect scores doesn't decay toward zero from the multiply alone) is nested authored data on a `BehaviorDefinition` (a Behavior = "use this ability," referencing both the `AbilityDefinition` and its own considerations by `DefinitionId`, same cross-reference convention as everywhere else in the toolkit), bundled into a `BehaviorSetDefinition` per creature archetype ("Goblin Warrior" = [MeleeAttack, Retreat]). `UtilityAIDecisionProvider : ITurnDecisionProvider` is the Brain -- not an asset, just the code that evaluates a Behavior Set each turn (mirrors `IReactionDecisionProvider`'s shape) -- enumerating every Behavior × valid-target Decision (reusing the ability's own `Targeting` for candidate/range filtering, scoped to `MaxTargets == 1` for this pass), scoring each, and returning the winner as a `TurnDecision`; a full `UtilityDecisionLogEntry` trace (every Decision considered, its score, which won) reuses the existing `ICombatLog` structured-logging pattern -- the actual tune-a-curve/replay/read-the-trace debugging loop this class of AI needs, rather than a bespoke tool. `ConsiderationInputRegistry` resolves an `InputKey` to a raw float the same way `FeatureModifier.QueryKey` resolves a rule query -- built-ins (`Distance`, `Self`/`TargetResourcePercent:<id>`, `RandomChance`, `InfluenceMap:<layer>:Self`/`Target`) cover only what's derivable from already-generic state; a ruleset/game registers its own. `InfluenceMap`/`InfluenceSource` (battlefield-scoped runtime state, not a `DefinitionAsset` -- like `LootContainerState`/`CombatEncounter`) let a named layer ("Danger", "DifficultTerrain") accumulate falloff-weighted contributions from hazard sources, sampled by the two new Consideration inputs above; sources can be hand-placed by whoever sets up an encounter or created automatically by a new `CreateInfluenceSourceEffect : AbilityEffect` when a spell resolves (Fireball leaves fire, Web leaves difficult terrain). `InfluenceMap`/`InfluenceSource`/`IPositionProvider` live in `CRPG.Core`, not `CRPG.AI` -- both `CRPG.Abilities` (for the new effect) and `CRPG.AI` (for the Consideration inputs) need them, and `CRPG.AI` already depends on `CRPG.Abilities`, so putting them in `CRPG.AI` would create a circular assembly reference. `AbilityExecutionContext`/`AbilityResolutionService` gained two new optional fields/constructor params (`Positions`, `InfluenceMap`) to carry this through to effects that need them -- backward compatible, existing call sites unaffected; found and fixed a related latent bug while there, `ConditionalEffect`'s filtered sub-context was silently dropping `EventBus` (now threads all of `EventBus`/`Positions`/`InfluenceMap` through). Deliberately deferred: AoE/multi-target Decision scoring (needs cluster-placement heuristics), movement/positioning Behaviors (no in-turn move budget wired in `CombatEncounterService` yet -- the map itself has no movement dependency, so this is a clean fast-follow), Team/Faction concepts in `CRPG.Combat` (the Brain takes enemy/ally candidate lists externally instead), shared/reusable curve assets (curves stay inline on each Consideration, using Unity's built-in `AnimationCurve` Inspector widget for free visual editing), and async decision timing (stays synchronous -- no combat UI exists yet to pace a "thinking delay" against). `InfluenceSource` has no built-in duration/auto-expiry: `ConditionInstance.RemainingDuration` already has the identical gap (nothing anywhere ticks it down), so this doesn't quietly half-solve it just for influence zones -- a source persists until something explicitly calls `RemoveSource`. ### Fixed (retrofit)
- `DiceExpression` was a `readonly struct` with get-only auto-properties and no `[SerializeField]` backing fields -- it worked as a runtime-constructed value (all of Phase 1's tests passed) but was silently **not actually authorable in the Inspector**, since Unity's serializer can't write into readonly fields or bare properties. Converted to a plain `struct` with real `[SerializeField]` fields (same pattern as `DefinitionId`), needed now that ability damage/healing amounts are dice expressions designers type into the Inspector. Public API and behavior unchanged; full suite re-verified green after the change.
- `CharacterBuildService.Build` never actually applied ability-score bonus modifiers (e.g. Human's +1 to all six stats) — the mechanism (FeatureModifier keyed by the stat's own DefinitionId, gathered via `FeatureModifierCollector`) had been designed but the code was never written. Found via the Fighter demo (STR stayed at 16 instead of 17); fixed by adding the gather-and-apply step after feature granting. Full package suite re-verified green (102/102) after the fix, not just the demo.
- `CampDemo.unity`'s `UIDocument.panelSettings` was silently null in the saved scene (`fileID: 0`) even though `BuildCampDemoScene` assigned it before saving — same root cause as the earlier `AssetDatabase.CreateAsset`/`SetDirty` bug: `CreateAsset` + `SaveAssets` on a *just-created* `PanelSettings` asset can invalidate the in-memory reference used immediately afterward. Fixed by reloading the asset from disk via `AssetDatabase.LoadAssetAtPath` after saving it, before assigning it to the `UIDocument`. Separately, the newly-created `PanelSettings` also had no theme assigned (a `PanelSettings` with no theme renders nothing) — the script now auto-assigns Unity's built-in default runtime theme by its known guid, only when one isn't already set (so it won't clobber a manually-chosen theme). Found because the user hit "nothing displaying," diagnosed it live, and fixed it manually in-editor first; this closes the gap in the *authoring script* so regenerating the scene doesn't reintroduce it.
- **The fix above was incomplete** -- discovered while building the Store demo scene, which reused the exact same (by-then-extracted) `GetOrCreateDemoPanelSettings` helper and still produced a scene with `UIDocument.panelSettings: {fileID: 0}`. The user's earlier live in-editor fix had only ever patched the *saved scene*, never the authoring script itself, so the underlying bug was still there waiting to bite the next scene. Root cause was different from (and in addition to) the one above: `EditorSceneManager.NewScene(...)` unloads objects not referenced by any active scene/root, which silently turns an already-loaded asset reference into a fake-null "missing object" even with no intervening `CreateAsset`/`SaveAssets` call -- so loading/creating the `PanelSettings` *before* `NewScene` was itself unsafe, regardless of the reload-after-save fix. Fixed by moving `GetOrCreateDemoPanelSettings` to run *after* `NewScene`, immediately before the reference is used. Reran `BuildCampDemoScene` after the fix and confirmed it now reproduces the same valid `panelSettings` reference the user had set by hand, closing the gap at the actual root this time; `BuildStoreDemoScene` was verified the same way from a clean run. 157/157 tests still passing (this bug was never in package code, only the dogfood scene-authoring script).
