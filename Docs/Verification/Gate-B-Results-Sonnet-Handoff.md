# Production Foundation — Gate B Results (Adventure Slice)

Date: 2026-09-13. Recorded by Sonnet 5 as part of Task 3.6 (`Docs/Plans/Production-Foundation-Implementation.md`), per Gate B's acceptance text: "four-character party, click/drag selection, bounded camera, walk to talk/loot/store, one branching dialogue, one quest, scene travel, save/exit/load. A game implementer supplies content and reference views but writes no replacement framework services." A point-in-time record of what was actually run and what its result was, including open gaps — not a claim that every bullet has been exercised end-to-end by a human with working input, which it has not.

## Context: three real, live-found-and-fixed defects this session

Live hands-on testing (Editor Play mode and a standalone build) by the user surfaced defects no automated test caught, because none of them are expressible as a pure-logic unit/PlayMode test — each needed a human actually clicking things:

1. **UI Toolkit Event Debugger showed zero mouse events reaching any HUD element.** Root-caused to two independent, compounding bugs: (a) `AdventureSliceSceneAuthor.AuthorCoreScene`'s `PanelSettings` reference became a Unity "fake null" across two intervening `NewScene()`+`NavMeshSurface.BuildNavMesh()` cycles (Interior, Overworld) — fixed by re-loading the asset fresh immediately before use instead of trusting a reference held across the whole multi-scene authoring pipeline; (b) `TestProject/ProjectSettings/ProjectSettings.asset` had `activeInputHandler: 0` (Legacy Input Manager only), so the New-Input-System-based `InputSystemCommandSource` never received real device events at all — the user changed this to `2` (Both) via the Editor UI. Both were required; either alone left clicking completely non-functional.
2. **Consolidated four per-panel `UIDocument`s into one shared `HudRoot`.** Not required to fix the above (each panel's own root was already explicitly anchored via `HudPanelLayout.AnchorToCorner`, not left full-screen), but a real architectural correction: four independent full-screen roots have no defined relative `sortingOrder` and each is independently pickable-everywhere by default. `Runtime/UI/HudRoot.cs` (new) owns the single `UIDocument`, sets its root to `PickingMode.Ignore`, and hands each panel an anchored child region via `CreateRegion`. `PartyView`/`InventoryView`/`QuestLogView`/`SaveView` no longer own a `UIDocument`; `Initialize` now takes an externally-supplied `VisualElement` container.
3. **"Load" visibly walked the party to the saved position instead of placing them there instantly.** Matches a NavMeshAgent quirk this same codebase had already worked around once (`AdventureSliceBootstrap.PlaceInitialParty`'s own explicit post-activation `Warp` call): an agent that goes through Instantiate → synchronous OnEnable → `SetActive(false)` → later `SetActive(true)` does not reliably resync its *internal* nav-mesh position from `transform.position` alone. `SessionLoadCoordinator.Commit` now explicitly `Warp`s every restored instance's `NavMeshAgent` to its own transform position after reactivating it.
4. **"Load failed: content validation failed."** 100% reproducible, not intermittent: `LocationInitializer.Prepare` seeds the Overworld's merchant store the moment that scene loads, so *any* save taken in Overworld captures a store listing referencing the Potion `ItemDefinition` — but `AdventureSliceBootstrap.BootCoroutine` never registered `Potion` (or the Merchant `NpcDefinition`) into the `RulesDatabase` used for save/load content validation. Fixed by adding `otherItems`/`npcDefinitions` fields to the bootstrap, registered alongside the existing `hitPointsResource`/`currencyItem`/dialogues/quests.

All four fixes were re-verified against the full package suite (568 EditMode + 156 PlayMode, all green) and, for (3)/(4), against a live re-authored scene and a real Save→move→Load cycle the user confirmed worked correctly ("save and load both work").

## Known open gap — not yet root-caused, tabled at the user's request

**Clicking the Save/Load panel was reported to also issue a world movement command** (the party moved as if the click had landed on the ground). This was investigated live and NOT reproduced by any of the following automated checks against the actual running scene:
- `UIToolkitPointerCapture`'s static `registered` set correctly contains the `HudRoot` document.
- `panel.Pick()` correctly resolves every one of the panel's 8 buttons when queried at that button's own screen-space center.
- Driving the real `PlayerCommandRouter.HandlePointerDown`/`HandlePointerUp` (the actual production suppression code path, not a reimplementation of it) at each of the four HUD regions' own centers correctly suppressed Move/Select; a negative-control click at empty screen center correctly did NOT suppress.

Since the mechanism checks out at every point tested, the discrepancy is most likely something about the *specific* pixel the user actually clicked (an edge/gutter area, or a coordinate-space mismatch specific to their Game View window size — untested here, which ran at 1920×1080) rather than a structural suppression failure. Tabled per the user's explicit instruction ("let's table that bug for now"); next step if resumed is the UI Toolkit Debugger's Picking panel at the exact click point, per the user's own prior successful use of that tool for the original event-routing diagnosis.
