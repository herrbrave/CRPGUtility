# Production Foundation — Gate A Results (Character Laboratory)

Date: 2026-09-11. Recorded by Sonnet 5 as part of Task 2.5 (`Docs/Plans/Production-Foundation-Implementation.md`), per Docs/Design/Production-Foundation.md sec.8's Gate A acceptance text: "two different real Humanoid art sources; one compatible modular outfit family; rigid equipment; locomotion/facing/interruption/death; bind/unbind/scene reload; inspect visuals in PlayMode." A point-in-time record of what was actually run and what its result was — including failures and gaps, not only successes, per the implementation plan's explicit instruction ("record failed compatibility cases as well as successful fixtures").

## Critical visual defect found by the user, root-caused, and fixed (same day, after the correction pass)

The user opened this project and actually looked at the character -- the one inspection step no automated test or live-binding check in this whole initiative had ever substituted for -- and found it collapsed into a "dead spider" pose: spine on the ground, legs curled, no visible animation. This directly falsifies the correction pass's own claim above that R3/R4/R7 made animation "correct" -- those fixes were all real and are still valid, but none of them, nor anything else in this project, had ever checked the ACTUAL RENDERED POSE against real content. This section documents the investigation, root cause, and fix.

**Investigation.** A game-view screenshot confirmed the collapse exactly as described. Isolated `AnimationClipPlayable` tests (manual `SetTime`/`Evaluate` against the same clip and character, outside the production driver) consistently showed NO change from the model's own bind pose -- i.e. they did not reproduce the bug, which was the first real clue. Only Unity's own CONTINUOUS graph evaluation (`graph.Play()`, evaluated automatically every engine frame) reproduced it, and it was a single fixed wrong pose, not a drifting/animating one -- ruling out a mixer-weight or crossfade bug (the driver's own diagnostics were, in fact, completely clean throughout: exactly one port, full weight, correct clip identity). `Animator.Rebind()` on the live broken character corrected the pose instantly -- but only for a single frame, reverting to the same wrong pose within about a second even with the character's own animator component fully disabled, proving Unity's own automatic graph evaluation (not this project's code) was recomputing the wrong result every frame. Removing the model's Avatar entirely produced a normal, stable, correctly-animating pose.

**Root cause**: both real Humanoid fixtures (`BaseHumanMaleCharacter`, `BaseHumanFemaleCharacter`) had their source FBX configured with a **Humanoid** Animation Type/Avatar (done in Task 1.3, with the stated intent of "so it can later share animation clips... via Humanoid retargeting"). That intent was never actually implemented or true: `CharacterAnimationAuthor`'s clips are imported as **Generic** (raw bone-path curves), and `PlayableCharacterAnimationDriver` plays them via a raw `AnimationClipPlayable -> Animator` output with **no retargeting step of any kind** -- cross-body sharing has only ever worked because both third-party FBX packs happen to use an identical UE4-mannequin-style bone-path hierarchy (`Armature/root/pelvis/...`), not because of Humanoid muscle retargeting. Feeding Generic curve data through a raw Playables output into a **Humanoid**-avatar'd Animator does not just fail to retarget -- Unity's own internal per-frame Humanoid pipeline actively reinterprets/corrupts it, and that corruption is invisible to any check that only inspects driver/graph state (weights, active port, bound-ness) rather than the actual resulting transforms.

**Fix**: both fixtures' source FBX files reconfigured to `Animation Type: Generic` with a Generic (not Humanoid) Avatar; `BaseHumanMaleCharacterAuthor.ConfigureGenericRig()` renamed/corrected from its old `ConfigureHumanoidRig()` for reproducibility; `CharacterRigValidator.ValidateModel` now **Errors** (not silently passes) if a model's avatar is Humanoid, with the full empirical reasoning in its own remarks; `GateAFixtureTests` gained a bone-name-independent, world-space rendered-bounds sanity check (`AssertReasonablyUprightPose`) against BOTH real fixtures specifically so a future regression of this class is caught by CI, not only by a human looking. Re-verified: fresh EditMode (449/443+6) and PlayMode (91/91, including the two new pose-sanity tests) runs, plus a clean live Play-mode screenshot from the actual corrected prefab (not a patched instance) showing a normal standing/idle pose.

**§1's "proving cross-skeleton Humanoid retargeting" claim, corrected**: it is bone-PATH matching between two packs that happen to share identical hierarchy naming, not Humanoid muscle-space retargeting -- Humanoid avatars are now explicitly NOT used anywhere in this pipeline. The two-Humanoid-art-source claim in §1 (two different, real, differently-proportioned bodies playing the same clip set) is otherwise unaffected and still holds.

**Not yet investigated**: both screenshots above show the character floating slightly above the ground plane (feet not quite touching). This appears to be a separate, minor issue (likely the CapsuleCollider/NavMeshAgent's configured height/base offset vs. the model's own origin, not a fixture-level rig bug) -- flagged honestly as unverified/unfixed rather than silently ignored, not blocking, but worth a look during the user's own visual review.

## Second visual defect found by the user, root-caused, and fixed (same day, immediately after the dead-spider fix)

Right after the dead-spider fix, the user reported: pressing Walk split the character into two overlapping bodies, one left behind idling while "the other" ran to a spot on the right and only appeared to move backward; Turn/Equip/Unequip appeared to do nothing but log.

**Investigation.** Live inspection of the actual saved `CharacterLab.unity` hierarchy (not a guess) showed `PreviewAnchor` held **two** `BaseHumanMaleCharacter` children, exactly overlapping at the origin. Their component lists differed: the first (index 0) was missing `FacingController` entirely; the second (index 1) had it. `CharacterLabHarness.Start()`'s fallback rebind picks `GetChild(0)` -- the stale one. A live game-view capture mid-Walk visually confirmed two overlapping bodies, and the untouched "idle" duplicate was even seen briefly animating on its own, because Unity's NavMeshAgent local-avoidance nudged it out of the driven character's way as it started moving, which independently crossed that duplicate's own moving-speed threshold.

**Root cause**: `CharacterLabHarness.SpawnCharacter`'s cleanup guard was `if (current != null) DestroyImmediate(current)`. `current` is an intentionally non-serialized runtime field (correct for holding a live component reference) -- but that also means a C# domain reload (i.e. any script recompile, and this session's correction/dead-spider fixes triggered many) silently resets it to `null` without touching the actual staged GameObject still sitting under the anchor. The next `SpawnCharacter` call (via the CharacterSetupWindow Preview button, including the dead-spider fix's own re-staging step) then saw `current == null`, skipped the destroy, and instantiated a second character on top of the first -- one of them now a stale copy predating a later prefab change (the FacingController wiring added in the R2 correction-pass work), so only the "wrong" duplicate ever actually got driven by input, and it was missing the component that makes Turn and moving-while-facing work correctly.

**Fix**: `SpawnCharacter` no longer trusts the cached `current` reference to decide what to remove -- it now destroys every existing child of the anchor unconditionally before instantiating the new one, since the anchor is only ever meant to hold one staged preview character. The scene was re-staged through the same `ICharacterPreviewAnchor` mechanism (not hand-patched) and re-saved, leaving exactly one character with the full, correct component set.

**Re-verified live**: fresh EditMode (449/443+6 same pre-existing) and PlayMode (91/91) runs after the fix; live Play-mode session confirmed a single character, Walk arriving cleanly at the target while correctly rotating to face its direction of travel (`forward` tracked `velocity` direction; final pose faced along +X, matching a target at `(3,0,0)`), and Turn now logging "requested facing away from current forward" instead of "No FacingController on this wrapper." Equip/Unequip's "nothing happens but logs" behavior was confirmed as-designed, not a bug: `CharacterLabSceneAuthor` never assigns `equipItemForTesting`, and the harness's own log text says so explicitly ("No 'Equip Item For Testing' assigned in the Inspector").

## Third visual defect found by the user ("moonwalking"), root-caused, and fixed (same day)

After the two fixes above, the user reported the character still "walks backwards during movement... like they're moonwalking," and confirmed on request that this meant genuinely reversed apparent travel, not a foot-sliding quality.

**Investigation, ruling out several real hypotheses with direct measurement before finding the actual cause**: read the `Armature|Walk_Loop` clip's own curves directly -- confirmed zero net root/Armature translation (a pure in-place cycle, no baked root motion to conflict with NavMeshAgent-driven translation). Reflectively read `PlayableCharacterAnimationDriver`'s live `Playable.GetSpeed()` on the active port during a real Walk -- confirmed `+1.0` (forward playback, never negative). Polled the playable's own clip-time against real wall-clock time across several samples during a deliberately slowed test walk -- confirmed the clip's internal time only ever increases, advancing at exactly the driver's documented speed-clamp ratio (0.5x at the test's artificially slow speed; the math and clamp both work exactly as designed). None of these -- the most likely "reversed animation" explanations -- were the cause.

**Root cause, found by directly reproducing the control sequence**: `Turn()` (key 3) requests a manual facing direction at `FacingPriority.Interaction`, which outranks the automatic `FacingPriority.Motion` request `FacingController` normally applies while moving (turning the character to face its direction of travel). Previously only `StopWalking()`/Idle (key 1) released this override; `Walk()` did not. Reproduced live: triggering Turn then Walk with no Idle in between, the character arrived exactly at its destination (`pos=(3,0.08,0)`, confirming translation was completely correct) but its final `forward` was `(0,0,-1)` -- exactly where Turn had left it, never rotating to face where it was actually going for the whole walk. Turn-then-Walk is an entirely natural order to explore a numbered control list in, so this reproduces easily, not an edge case.

**Fix**: `CharacterLabHarness.Walk()` now also clears the `FacingPriority.Interaction` override before requesting movement, mirroring what `StopWalking()` already did -- starting a new walk is just as much a "the manual turn no longer applies" signal as stopping is.

**Re-verified live**: repeated the exact Turn-then-Walk sequence after the fix -- character now arrives with `forward=(1,0,0)`, correctly matching its direction of travel, confirmed by both live state and a game-view screenshot. Fresh EditMode (449/443+6, unchanged) and PlayMode (91/91) runs, no regressions.

### Follow-up: the same symptom persisted for a PLAIN Walk (no Turn involved)

The user reported the walk direction still appeared backward "during the move phase" even without pressing Turn. Rather than guess again, ruled out further hypotheses with direct measurement before finding the real cause this time too.

**Investigation**: `Time.timeScale` set very low (0.01-0.03) to spread a sub-second default walk across many real-time-spaced screenshots (a plain sleep-based capture loop wasn't fine-grained enough -- the default walk to `(3,0,0)` completes in well under a second). The resulting sequence showed the character's TRUE starting behavior clearly for the first time: at spawn (identity rotation, forward `(0,0,1)`) the default `WalkTarget` sits 90 degrees away at `(3,0,0)`. NavMeshAgent begins translating toward it immediately (velocity is not gated by facing), while `FacingController` only reaches the correct orientation after its own turn completes. That turn (90 degrees at the configured 360deg/s) takes about 0.25s -- roughly a THIRD of the entire ~0.86s default walk. For that whole leading fraction, screenshots showed the character facing directly at the camera (its spawn orientation) walking an animated gait that reads as "approaching the viewer" while the body visibly slides sideways toward the target -- exactly the "moonwalking"/backward impression reported, and for a much larger share of the walk than a longer real-gameplay move would ever show.

This is NOT a bug in `FacingController` or the movement system -- both were re-confirmed correct yet again (clip plays forward at the right speed, NavMeshAgent moves at exactly its configured velocity toward the real target, the turn itself completes in the geometrically-correct amount of time for its configured angular speed). It is this specific demo's spawn-vs-target geometry making an ordinarily brief turn-catch-up transient dominate a walk that is barely longer than the turn itself.

**Fix**: `CharacterLabHarness.SpawnCharacter` now spawns the character already facing its `walkTarget` (when assigned) instead of a fixed world identity rotation, eliminating the mismatch for the demo's first, most-scrutinized walk. Turn (key 3) remains available to deliberately exercise facing-priority behavior.

**Re-verified live**: re-staged the real scene through the fix (single character, `forward` now starts at `(1,0,0)`, already matching the target); a fresh slow-motion capture sequence of the default Walk showed the character correctly facing its direction of travel from the very first frame through arrival, no camera-facing transient at any point. Fresh EditMode (449/443+6, unchanged) and PlayMode (91/91) runs, no regressions.

## Correction pass addendum (same day)

A second, independent review (`Docs/Verification/Phase-2-Review.md`) found nine real integration defects in the Task 2.4/2.5 work this document originally certified as passing/partial -- six High severity, three Medium. Every finding was independently re-verified against the actual source (not taken on trust) before fixing. All nine are now fixed, tested, and reconfirmed via a fresh live EditMode (449 total, 443 pass + the same 6 pre-existing intentional-red) and PlayMode (90/90 pass) run, plus a real Play-mode session in the actual saved CharacterLab scene for the harness fix specifically (not just a unit test). Summary of what was wrong and what changed:

- **R1 (wrapper updates were destructive)**: `CharacterWrapperBuilder` always rebuilt a completely fresh hierarchy and saved over the existing prefab -- preserving the asset's GUID but silently discarding any consumer-added component/child/reference. Now genuinely edits in place via `PrefabUtility.LoadPrefabContents`, patching only the tool-owned components and the Model child specifically; everything else survives untouched, including external subobject references. New test proves this through two real content changes, not a no-op re-save. (Found and fixed along the way: `GetComponent<T>() ?? AddComponent<T>()` is unsafe for Unity Object types -- confirmed via a live `MissingComponentException` -- fixed with an explicit `== null` check pattern.)
- **R2 (the saved laboratory couldn't resume its staged character)**: `CharacterLabHarness`'s runtime references are correctly non-serialized, but `Start()` never rediscovered the staged character under the serialized anchor after a scene reload, so every control silently no-opped. Fixed, and re-verified live: opened the real saved scene, entered actual Play mode via the Editor, and confirmed the harness rediscovered the character and successfully bound it (`agentBound=True`) and that a control (Walk) worked. Also fixed in the same pass: equip testing only ever registered the bare item, never its visual profile/bone map (added explicit Inspector fields for them); the harness leaked a `GameSession` on character replacement (now disposed); a manual Turn request was never released (now cleared by Idle/Stop).
- **R3/R4 (action/terminal state didn't correctly hand baseline animation back)**: `RefreshBaseline`'s "already playing this" cache didn't know the mask (action/terminal) had just lifted, so the graph could stay stuck on an action's last frame indefinitely even once state correctly reported inactive; separately, rebinding to a new Animator (a Model swap) stranded an in-flight action with no surviving completion route, permanently masking baseline forever. Both fixed -- baseline is now force-replayed on the exact tick a mask lifts, and a rebind now cancels a stranded action exactly once (or, for a terminal pose, replays its remembered cue on the new graph) rather than leaving it unresolved. Six new PlayMode tests reproduce and fix both, including a pre-bind request and a terminal-then-rebind case.
- **R5 (real equipment replacement defeated known-good-visual retention)**: `EquipmentService.Equip` publishes `ItemUnequipped` for a displaced occupant BEFORE `ItemEquipped` for its replacement -- the binder was destroying the old visual on the first event, before the replacement was ever validated. The original test only ever published a direct `ItemEquipped` with no preceding unequip, so it never caught this. Fixed with a pending-removal window (a same-slot re-equip reclaims it; a genuine unequip flushes it in `LateUpdate`); new tests go through the real `EquipmentService`, not hand-built events.
- **R6 (skinned binding could still half-bind)**: validation only proved the map's OWN entries resolved, not that they covered every bone a renderer actually references -- an uncovered bone silently stayed pointed at the garment's own copy. Also: `RigBindingMap.RigFamilyId` was defined but never actually checked (a redundant, unchecked `EquipmentVisualProfile.RigFamilyId` created a false impression of safety -- removed); duplicate sibling paths in a real hierarchy silently picked whichever was visited last. All fixed: full renderer-bone coverage is now required (reject the whole binding otherwise), the map's own `RigFamilyId` is what's actually checked, and an ambiguous path is now omitted from lookup entirely rather than arbitrarily resolved.
- **R7 (interruption wasn't actually normalized)**: the 2-port design kept only the single dominant outgoing port during a rapid interrupt and discarded the rest, so combined weight could dip well below 1 and an equal-weight interruption lost half the visible pose outright. Redesigned around a bounded (4-port) shared fade-out group whose start weights are captured fresh at each interruption -- provably exactly normalized at every instant (see the class's own remarks for the proof), not just eventually recovering. New tests assert exact normalization, an equal-weight interruption preserving both contributors, and the documented bounded-collapse behavior once the port cap is actually hit.
- **R8 (validation accepted cues with nothing playable)**: `TryGetCue` only proves a matching id exists, not that it has a real, non-zero-length clip -- a profile could satisfy the mandatory-cue check while building a wrapper that shows nothing. Now checks Clip null/zero-length for both mandatory and optional cues, and flags duplicate cue ids in a profile (a new `CharacterAnimationProfile.Cues` enumeration was added to support this).
- **R9 (synchronous callbacks could violate terminal/action invariants)**: `EnterTerminal` cancelled the in-flight action (synchronously invoking its callback) BEFORE setting `isTerminal`, so a callback that reentrantly requested a new action during that window was wrongly accepted, leaving both terminal and action-active true simultaneously -- reproduced live. `RequestAction` had the mirror bug: it assigned the new token AFTER invoking the previous callback, so a reentrant request's own assignment got silently clobbered once the outer call resumed. Both fixed by committing new state before invoking any callback that could re-enter; new tests cover both reentrancy paths directly.

**Deliberately not folded into this pass** (the review's own "additional integration concerns," framed as open architecture questions rather than contained bugs): a Model-swap timing window where the old/new Model hierarchies briefly coexist during equipment bone-map rebuilding; `CharacterPlayableAnimator` still reading a raw `NavMeshAgent` instead of `MotionSnapshot`; `CharacterSetupWindow`'s Preview needing a hardcoded TestProject scene path; and no single owner tearing down movement/subscriptions/views/session together on despawn. Flagged for a future task, not silently dropped.

**Gate A status, updated**: the review's critique of the ORIGINAL Gate-A-Results document's own claims was correct in one place -- "an unauthored death cue freezes the last baseline pose" was asserted from the harness's log text, not verified against `RequestTerminal`'s actual behavior. It has now been directly verified via `CharacterAnimatorBaselineRecoveryTests`: `RequestTerminal` really does stop baseline replacement (masks it via `IsTerminal`), so the graph genuinely holds its last pose rather than merely appearing to by coincidence. The gate's remaining open items (§2, §3, §5's scene-reload note, §7) are unchanged by this correction pass and still require the user's own rig/animation-feel review before Task 3.1.

## 1. Two different real Humanoid art sources

- **Source 1**: `Superhero_Male_FullBody.fbx` (Universal Base Characters[Standard], CC0) → `Assets/Resources/NPCs/BaseHumanMaleCharacter.prefab`. Authored via the pre-existing `BaseHumanMaleCharacterAuthor.cs` one-off script (predates this task); this task added `FacingController` to its build (a real, previously-unwired gap discovered while writing `CharacterWrapperBuilder` — see below) and re-ran it live.
- **Source 2**: `Superhero_Female_FullBody.fbx` (same pack, same license) → `Assets/Resources/NPCs/BaseHumanFemaleCharacter.prefab`. Built this task via `CharacterWrapperBuilder`/`CharacterRigValidator` — the new general-purpose tooling this task delivers — not a new hand-written one-off script, i.e. this is the tool's first real dogfooding use. `CharacterRigValidator.Validate` against its spec: **0 errors**, 1 warning (no rig family declared — expected, opt-in per Task 2.4, no `CharacterRigDefinition` asset exists yet for either source).
- **Shared animation content across both**: `CharacterAnimationProfile_HumanMale.asset` (authored against source 1's skeleton) was reused unmodified for source 2. `Tests/Runtime/GateAFixtureTests.cs`'s `TheSecondHumanoidFixtureBindsAndPlaysBaselineLocomotionWithoutError` (new, passing) instantiates the real source-2 prefab, confirms its Avatar is genuinely Humanoid (`isHuman == true`, not merely non-null), and ticks several real frames of baseline (idle) playback with no exception and a still-bound presentation graph — i.e. Humanoid retargeting of the same clip set onto a differently-shaped skeleton is demonstrated, not just claimed.

## 2. One compatible modular outfit family — partial pass

The Peasant modular outfit (Task 2.4: `EquipmentVisualProfile`/`RigBindingMap`-based, 4 pieces) is fully verified against **source 1 only**. A live smoke check (Task 2.4) equipped the real Tunic+Boots items onto the real `BaseHumanMaleCharacter` instance and confirmed all 65/65 bones resolved with zero nulls on both renderers.

**Gap**: the asset pack also ships `Female_Peasant_{Arms,Body,Feet,Legs}.fbx` pieces, but no `ItemDefinition`/`EquipmentVisualProfile`/`RigBindingMap` content was authored for them this task, and the outfit was therefore never equipped onto source 2. Marked **partial** rather than **pass** for that reason — the BINDING MECHANISM is proven cross-skeleton-capable in principle (Task 2.4's synthetic tests exercise arbitrary rig-family mismatches deliberately), but "one compatible modular outfit family" working on a SECOND real body was not itself exercised. A natural follow-up, not attempted here to keep this task's scope to what Task 2.5 actually asked for.

## 3. Rigid equipment — mechanism proven, no real content

Task 2.4 built and tested the Rigid attachment path (named-socket resolution, missing-socket graceful rejection) entirely against synthetic fixtures — no real weapon/rigid-equipment `ItemDefinition` exists anywhere in the project. `CharacterRigValidator`'s `RequiredSocketIds` check (new this task) can flag a missing socket on real content once any is authored, but there is currently nothing to validate. Recorded honestly as a real gap: the MACHINERY is real and tested; there is no real rigid-equipment fixture to look at in PlayMode yet.

## 4. Locomotion / facing / interruption / death

- **Locomotion**: `Tests/Runtime/CharacterMotionTests.cs` (Task 2.1) bakes a real NavMesh per test (real obstacle detour, real disconnected-island partial-path case) — not mocked.
- **Facing**: `FacingController` (Task 2.1) tested in isolation since Task 2.1, but **was never actually wired onto either real character prefab until this task** — discovered while writing `CharacterWrapperBuilder` (it omitted `FacingController` at first, matching `BaseHumanMaleCharacterAuthor`'s own long-standing omission). Fixed in both: `CharacterWrapperBuilder.BuildCharacterRoot` now always adds it, and `BaseHumanMaleCharacterAuthor.cs` was updated and re-run live so the pre-existing fixture matches. Confirmed present via `CharacterWrapperBuilderTests.BuildOrUpdateCreatesAPrefabWithTheExpectedComponents`.
- **Interruption**: Task 2.3's attack→hit→death-during-crossfade coverage, including the real Unity Playables weight-reset bug found and fixed that task.
- **Death**: `CharacterPresentationState.EnterTerminal`/`Recover` tested since Task 2.2 (state-level: rejects further move/action/stance requests, exactly once cancellation). **Gap, recorded honestly**: no `anim-death` clip is authored in the shipped `CharacterAnimationProfile_HumanMale.asset` fixture (`CharacterAnimationAuthor.cs`'s `Cues` array has only idle/moving/attack-idle/attack-melee) — entering terminal state today freezes at the last baseline pose rather than showing a distinct death pose. The STATE transition is real and tested; the VISUAL is not authored. `CharacterLabHarness`'s own Death control logs this caveat directly so a reviewer isn't confused by it.

## 5. Bind / unbind / scene reload

- **Bind/unbind**: extensively covered since Task 1.1 across `CharacterBindingTests.cs`, `CharacterWrapperTests.cs`, `EquipmentVisualBindingTests.cs`, `GameSessionDestructionTests.cs` — identical-tuple no-op, different-tuple throw, full teardown on `Unbind`, `OnDestroy`-driven unbind (including the documented headless-EditMode `OnDestroy` limitation worked around via PlayMode tests).
- **Scene reload specifically**: **not independently verified**. Every existing test exercises destroy/recreate of individual GameObjects within one already-loaded scene (`DestroyImmediate`, `Object.Destroy`), which drives the same `OnDestroy`/`Unbind` code path a scene unload would — but no test actually unloads and reloads a whole Unity `Scene` (e.g. `SceneManager.LoadScene`) to confirm no static/singleton state leaks across that boundary specifically. Flagged as an unverified claim rather than assumed equivalent; the engine has no known singletons that would make this likely to fail (`GameSession`/`RulesDatabase`/etc. are all constructed fresh, not static), but "likely fine" is not the same as verified.

## 6. Inspect visuals in PlayMode

Delivered as tooling, not as a completed human review: `CharacterSetupWindow`'s Preview button stages any configured character into the new `Assets/Scenes/CharacterLab.unity` (ground + baked NavMesh + light + camera, authored via `CharacterLabSceneAuthor.cs`), and `CharacterLabHarness` (implementing the package's new `ICharacterPreviewAnchor` interface — the package itself holds no reference to this TestProject-only script) exposes keyboard controls (1–9) to cycle Idle/Walk/Turn/Action/Interrupt/Death/Recover/Equip/Unequip with on-screen labeling, once Play starts.

Verified mechanically this session (via live `eval_file` calls against the actual open Editor, not assumed): the `ICharacterPreviewAnchor` discovery correctly finds the harness by interface (not a package→TestProject type reference), and `SpawnCharacter` correctly instantiates a real wrapper prefab (`BaseHumanMaleCharacter`) under the scene's `PreviewAnchor` Transform. The scene currently has that instance staged, left in place intentionally as a working example.

**What this task cannot do**: actually judge whether the rig/animation *looks* good. That is exactly what the plan's own "USER REVIEW GATE: approve rig and animation feel before broad UI/combat work" calls for — a human pressing Play in `CharacterLab.unity` and looking. Not claimed as done here.
