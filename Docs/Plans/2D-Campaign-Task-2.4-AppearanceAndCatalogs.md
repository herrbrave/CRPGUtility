# Task 2.4 Detailed Plan: Appearance storage, catalogs, and applying appearance to the view

> Status: BUILT (2026-09-19); plan v2 approved by the user, results at the end. (Was: DRAFT v2, post-Opus review.) Child of `Docs/Plans/2D-Campaign-Phase2-SpritePresentation.md` (Task 2.4 = D6, findings 1, 4; Opus S3/S4).
> Tasks 2.1-2.3 are committed (`ccfc6d7`, `bff5550`, `818546c`). The phase doc's "2.4a" (storage and spawn) and "2.4b" (catalogs and content) are one plan built in two stages.
> The "Review record" at the end lists every Opus finding and its disposition.

## Goal

A character's *appearance* (which body, hair, outfit... it was created with) becomes real, saved data, and a sprite character's view shows it:
- `CharacterState` carries an appearance map (`layer slot -> option id`); it round-trips through save/load; an authored NPC can declare one; a built player character can carry one from its build plan.
- A catalog asset per layer slot says what each option id looks like (sprite + tint); a source resolves `(slot, option)` for the view.
- The view applies the appearance at bind on every spawn/restore path; an unknown option degrades to an empty layer with a report, never a throw.
- The campaign project gets its real catalogs (generated from the sliced Kenney sheets + the custom skeleton bodies), ready for the Phase 4 creator and Phase 6 content.

Non-goals: the creator UI (Phase 4); live mid-game appearance-change events (out of scope per D6); curated display names, contact sheets for curation, and the missing monster art (necromancer, rats) - **a content pass with you after this task** (the contact-sheet generator moved there, see deviations).

## Deviations from the Phase 2 doc (flagged)

- **`ApplyAppearance` is replace-only and the render state does not retain option ids.** 2.2 moved it here after Opus showed a merge shape was wrong for restore. `ApplyAppearance(map, source)` makes the layer appearance *exactly* the map (absent slots are cleared; an unknown option leaves its slot empty and reports). "What option is on this slot" is answered by `CharacterState.Appearance`, the authoritative data, so retention on the render state is cut as unneeded.
- **Save format 2 -> 3 with an identity `V2ToV3Migration`** - and the real reason (the review sharpened it): without a bump, a v3-content save is indistinguishable from v2, so a **pre-2.4 build loads it, silently drops `Appearance`, and its next autosave writes the loss back to disk**. With the bump, `SaveFileStore` refuses cleanly (`UnsupportedNewerVersion`, `SaveFileStore.cs:188-189`; the slot UI already shows it, `SaveSlotCatalog.cs:53-58`) and the data survives. It is also what `COMPATIBILITY.md` prescribes, and v1 -> v2 was equally additive. Blast radius verified: one test line (`SaveServiceTests.cs:271`).
- **Separate `SpriteAppearanceBinder`** rather than folding into `SpriteEquipmentBinder` (different data source, no subscription, applied once). It duplicates the ~10-line "hold the compositor, re-resolve when destroyed" pattern instead of refactoring committed 2.3 code.
- **`CharacterBuildPlan` gains an appearance map** (Opus S5): the NPC side is symmetric (`NpcDefinition` -> `NpcSpawnService`); without a plan field a created protagonist would have no path to an appearance at all.
- **Contact-sheet generation/curation deferred to the scheduled content pass** (Opus M10): it is neither "make appearance real" nor needed by anything in Phase 2, and both obvious implementations are known-broken in this project (see risks). 2.4b ships catalogs + validator + the resolution/stability tests.
- **`CharacterState.SetAppearance` never throws** (Opus M5): an invalid slot or option is ignored, matching `GrantFeature`/`AddResource`/`LearnAbility`; `ClearAppearance(slot)` is the only remover.
- **Option ids include the sheet** (Opus S8): `<slot>-<sheet>-<col>-<row>`, e.g. `body-kenney-0-0`, `body-be-0-0` (the custom skeleton sheet), because `layer-body` draws from two sheets whose coordinates collide.

## Verified facts this design rests on

- `CharacterState` is plain `DefinitionId` data (`CharacterState.cs`); `CurrentAnimationCueId` (`:97`) is the precedent for presentation data on it (transient, unsaved - appearance is durable, so it is saved). Its mutators validate nothing (`:103-173`).
- Save: `SaveService.CaptureCharacters/RestoreCharacters` copy each field explicitly (`SaveService.cs:126-205`); `CharacterSaveData` has `[Serializable]` list fields with `= new()` initializers (`:44-71`); absent list fields keep their initializer (the repo already relies on it: `ConcentrationAffectedTargets`, `SaveService.cs:199`). `SaveData.CurrentFormatVersion = 2` (`SaveData.cs:18`); `SaveFileStore` defaults `{ V1ToV2Migration }` (`:99`); a save newer than current is refused **before** migrating with `UnsupportedNewerVersion` (`:188-189`); `NoMigrationPath` is only for a version at or below current with no chain (`:202-206`). No production code builds a `SaveFileStore` with a custom migration list; nothing else enumerates `CharacterSaveData` fields.
- Restore-before-bind is structural on every path: `SessionLoadCoordinator.BuildPhase` restores (`:435`) before `BindRestoredView` (`:471`), which throws for an unregistered character (`WorldSpawnService.cs:204-205`); `SpawnNpc` registers (`:161`) before `BindView` (`:170`). `session.Characters` is a `CharacterRegistry : ICharacterRegistry`; `CRPG.Presentation` references `Core, Actors, Inventory`.
- `RulesDatabase.All<T>()` is `definitionsById.Values.OfType<T>()` (`RulesDatabase.cs:57`) - Dictionary enumeration order, not a contract.
- Appearance and equipment are separate stores in `SpriteLayerState`; hides live only on equipment sets; `ClearAllAppearance` touches only appearance (`SpriteLayerState.cs:87-89, 164-176, 258`). Each of `SetAppearance/ClearAppearance/ClearAllAppearance` bumps `version` independently (`:150-176`).
- `NpcDefinition` has a custom inspector that lists property names explicitly (`Editor/Npc/NpcDefinitionEditor.cs:16-34`), so a new field is invisible until added there.
- **Sprite references and re-slicing:** `BarrowsEndSetup.SliceSheet` sets `spriteID = GUID.Generate()` for every rect on every run (`BarrowsEndSetup.cs:87`); Unity derives each sprite sub-asset's `internalID` (the `fileID` stored in every serialized reference) from that id (see the live meta). Re-slicing therefore turns every stored Sprite reference to "Missing (Sprite)" while sprite **names** stay stable.
- BarrowsEnd's test asmdef references only the test-runner assemblies and has `includePlatforms: []` (`BarrowsEnd/Assets/Tests/PlayMode/BarrowsEnd.PlayModeTests.asmdef`); `testables` makes `-runTests` also run the toolkit's suite unless `-assemblyNames` is given (Task 2.0 harness facts). The sliced textures are not readable (`isReadable: 0`).

## Design

### Stage A - storage, resolver, application (2.4a)

**1. `CharacterState.Appearance`** (`CRPG.Actors`): `IReadOnlyDictionary<DefinitionId, DefinitionId>` (layer slot -> option id); `SetAppearance(slot, option)` (invalid slot or option: ignored, no throw), `ClearAppearance(slot)`, `ClearAllAppearance()`. No change event.

**2. Save:** `[Serializable] AppearanceSaveEntry { string Slot; string Option; }`, `CharacterSaveData.Appearance = new()`; `SaveService` captures each character's entries sorted by slot id (per-character order deterministic; character order stays the existing `HashSet` order) and restores via `SetAppearance`, skipping empty entries. `SaveData.CurrentFormatVersion = 3`; `Migrations/V2ToV3Migration` is **deliberately an identity transform** (unlike `V1ToV2`'s `Level` fixup, an absent appearance list correctly defaults to empty) that sets `Header.FormatVersion = 3`; its doc comment says so and notes the pre-existing `ReadFormatVersion` asymmetry (no `Header` reads as current then fails `Corrupt`; a `Header` with no `FormatVersion` reads 0 -> `NoMigrationPath`). `SaveFileStore` defaults become `{ V1ToV2Migration, V2ToV3Migration }`. `ContentValidator` is **not** extended: an option id that no longer resolves must degrade at the view, not refuse the save (pinned by a test). `COMPATIBILITY.md` gets the v3 line and two corrections (`SaveService.CurrentFormatVersion` -> `SaveData.CurrentFormatVersion`, and the "version-0-to-1 example" reference -> the real v1 -> v2 migration).

**3. `NpcDefinition` + `CharacterBuildPlan`:** `[Serializable] AppearanceEntry { DefinitionId layerSlot; DefinitionId option; }` in `CRPG.Actors`; `NpcDefinition.appearance` (read-only `Appearance`), copied by `NpcSpawnService.Spawn`. `CharacterBuildPlan.Appearance` (a slot -> option map with `SetAppearance/ClearAppearance`), copied by `CharacterBuildService.Build`. **`NpcDefinitionEditor` gets an "Appearance" section** (`root.Add(Section("Appearance", "appearance"))`) plus a drift-guard test (every serialized field on `NpcDefinition` is drawn by some section - the 2.3 pattern).

**4. `SpriteLayerState.ApplyAppearance(IReadOnlyDictionary<DefinitionId, DefinitionId> slotToOption, ISpriteOptionSource source)`** and `ISpriteOptionSource { bool TryGetOption(DefinitionId slot, DefinitionId option, out SpriteOption result) }`. Semantics: the appearance layer becomes *exactly* the map; a slot absent from the map is cleared; an unknown option -> that slot empty + reported; an unknown slot (not in the state) -> reported, skipped; a null map clears all; a null source treats every option as unknown (reported once per call). **Implementation constraint (Opus S4):** resolve the whole target into a scratch array first, then write only the slots whose sprite/tint actually differ (exact component compare), so `Version` bumps only on a real change - a naive clear-all-then-set would bump every call.

**5. `SpriteLayerCatalog : DefinitionAsset`** (`[CreateAssetMenu]`): `layerSlot`, `displayName` (creator category name), `List<SpriteOptionEntry { DefinitionId optionId; string displayName; Sprite sprite; Color tint = white }>` (public constructor); `LayerSlot`, `DisplayName`, `Options`, `TryGetOption`. One catalog per layer slot; option ids unique within a catalog.

**6. `SpriteCatalogSource : ISpriteOptionSource`:** built from an `IRulesDatabase`, indexed by layer slot at construction. **Two catalogs claiming one slot: the one with the smaller ordinal `Id.Value` wins**, one warning names both (deterministic, the same rule 2.2 adopted after rejecting dictionary-order tie-breaks; tested with both registration orders). Lifetime: one per `SpriteAppearanceBinder.Initialize` (a definition sweep per spawn, accepted and documented; it also means content registered later is seen by the next spawn); `Rebuild()` for tests.

**7. `SpriteAppearanceBinder`** (MonoBehaviour, `[DefaultExecutionOrder(-10)]`): `Initialize(character, ICharacterRegistry characters, IRulesDatabase rules)`, `Refresh()`, `Unbind()`, `SetTarget(SpriteLayerState)`; same shape as the equipment binder (invalid args warn once and stay unbound, identical re-init no-op, different tuple throws, holds the compositor and re-applies in `LateUpdate` when the resolved state changes after a model swap, one warning when there is no target). No event subscription: applied at `Initialize` and on `Refresh()`. **Contract for callers (documented on the class and the plan field): a composition root sets `CharacterState.Appearance` before the view is bound, or calls `Refresh()` after changing it.** `Unbind` does *not* clear appearance (the binder does not own it, unlike equipment). A character missing from the registry: one warning, nothing applied.

**8. `WorldSpawnService.BindView`:** one more line after the two existing binder lines: `instance.GetComponentInChildren<SpriteAppearanceBinder>(true)?.Initialize(entityId, session.Characters, session.RulesDatabase);`. The order relative to the equipment binder is irrelevant (both are independent writes to different stores of one pure state, rendered in the compositor's `LateUpdate`; the equipment binder never reads appearance).

### Stage B - catalogs and content (2.4b)

**9. Validator** (`Editor/Validation/SpriteLayerCatalogValidator`, pure, same `ValidationResult` shape, wired into `PackageValidatorWindow`): **Error** - invalid `layerSlot`; an option with no id or no sprite; a duplicate option id in one catalog. **Warning** - a slot outside the default compositor set; a fully transparent tint; an empty catalog. `ValidateSet` flags two catalogs on one slot.

**10. Slicer fix (must land first - Opus B1):** `BarrowsEndSetup.SliceSheet` reads the existing rects/`ISpriteNameFileIdDataProvider` pairs and **reuses the existing `spriteID` for every name that already exists**, generating a new id only for new names. From then on stored Sprite references (catalogs now, equipment profiles/prefabs later) survive a re-slice. (The one existing consumer, the LookSpike scene, is already bound to the current ids and is unaffected.)

**11. Campaign catalogs** (`BarrowsEnd/Assets/Editor/BarrowsEndCatalogAuthor.cs`, `Barrows End/Content/Author Sprite Catalogs`): one catalog per layer slot from the verified column blocks: `layer-body` (Kenney bodies cols 0-1 rows 0-3 **plus** the two custom skeleton bodies), `layer-feet` (cols 3-4), `layer-clothes` (6-17), `layer-hair` (19-26), `layer-helmet` (28-31), `layer-shield` (33-40), `layer-weapon` (42-53). Option ids `<slot>-<sheet>-<col>-<row>` (sheet keys `kenney`, `be`); display names are the id for now. **Ids are permanent save contracts** (a stored id that vanishes degrades old saves to an empty layer), so curation may only change display names, never ids; stated in the author's header comment. Idempotent: loads existing catalog assets by path and updates in place (keeps asset GUIDs); sprites are looked up by sliced-sprite **name** (stable across re-slices).
**12. BarrowsEnd EditMode test project** (`BarrowsEnd/Assets/Tests/Editor/BarrowsEnd.EditModeTests.asmdef`, `includePlatforms: ["Editor"]`, references `CRPG.Core`, `CRPG.Presentation`, `CRPG.Editor` and the test runners), run with `-assemblyNames BarrowsEnd.EditModeTests` (the toolkit suite otherwise runs too); it gets its own baseline. Tests: (a) every option of every generated catalog resolves through `SpriteCatalogSource` to a non-null sprite; (b) the validator is clean on the generated catalogs; (c) **re-slice survival:** record each catalog sprite's `TryGetGUIDAndLocalFileIdentifier`, run `SliceAll` again, assert every catalog entry still holds the same non-null sprite; (d) option ids are unique per catalog and match the `<slot>-<sheet>-<col>-<row>` shape.

## Risks / open questions

1. **Option ids are permanent contracts** (sheet-scoped, curation may not rename them).
2. **Registering catalogs** in the game's `RulesDatabase` is the consumer's bootstrap job like every other definition; the BarrowsEnd tests register them explicitly; the real bootstrap arrives with Phase 3/6.
3. **2.5 dependency:** `SpriteAppearanceBinder` never appears on a wrapper-built prefab unless the builder adds it - 2.5 must add it (with the compositor, sorter, billboard, driver and `SpriteEquipmentBinder`) to sprite wrappers only, and must not add the 3D binder to them.
4. **Content gap (not code):** necromancer (robe + hood layers on an existing body) is nearly free from these catalogs; rats/bats and custom accents need Aseprite; curation of ~450 sprites needs your eyes. The contact-sheet generator for that pass must use pure CPU blitting from a `File.ReadAllBytes`/`LoadImage` temp texture (the textures are not readable, `ScreenCapture` hangs in batch mode, and a headless edit-mode `Camera.Render()` mixes sprite textures), with a fixed grid and a sidecar CSV (cell -> option id -> coordinates) instead of burned-in labels, written **outside `Assets/`** (e.g. `BarrowsEnd/ContactSheets/`) to avoid `.meta` churn.
5. **`SpriteAppearanceBinder` vs `SpriteEquipmentBinder` duplication** of the compositor-resolution pattern; a shared helper is a tidy-up if a third binder appears.

**Correction to the review (an Opus finding disproved empirically):** B1 claimed a re-slice would turn every stored Sprite reference into "Missing (Sprite)" because Unity derives the fileID from the slicer's `spriteID`. Tested directly: with the slicer forced to `GUID.Generate()` everything, the sheet `.meta` files changed (new `spriteID`s) but each sprite's `internalID` stayed identical (Unity derives it from the sprite *name*), and every catalog reference still resolved to the same sprite. So references were never at risk in this Unity version. The slicer still reuses ids by name because otherwise every re-slice rewrites all sheet metas; a test pins that (byte-identical metas across a re-slice) and a second test pins that references survive. The plan's "must land first" urgency was overstated.
