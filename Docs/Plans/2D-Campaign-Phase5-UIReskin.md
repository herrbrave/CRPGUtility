# 2D Campaign Phase 5: UI re-skin (HUD, paper doll, creator + title) - plan v7 (5.0 + 5.1 + 5.2 committed; skin pass for the doll next, then Task 5.3)

Master plan: `2D-Campaign-Implementation.md` (Phase 5). Source handoff: `BarrowsEnd/Docs/Handoff/Barrows-End-GUI-Handoff.md` (wireframes A HUD, B creator, C paper doll; assets `uipack_rpg_sheet.png` + `KenPixel.ttf`). Prior phase: `2D-Campaign-Phase4-CharacterCreator.md` (closed, Gate D passed).

## What the master plan got wrong (verified against source, 2026-09-22)

The master plan calls Phase 5 a "re-skin" of existing views "near-verbatim". Reading the code:

1. **BarrowsEnd has no HUD at all.** In `BarrowsEnd/Assets` nothing references `HudRoot`, `PartyView`, `InventoryView`, `AbilityBarView`, `TurnOrderView` or `CampView`. The only in-game UI is `ShellPanel` (status, message, summary line, Save/Load, Zoom), the creator and the title. So 5.1 and 5.2 are "wire the toolkit views into the shell, then skin them", not "re-skin".
2. **No look exists to re-skin.** Every toolkit view builds itself in code with inline styles (`style.backgroundColor = new Color(0,0,0,0.5f)`, hard-coded font sizes, `Color.yellow` borders). The repo contains **zero** USS/UXML files; the only stylesheet is Unity's default runtime theme (`.tss`). Inline styles beat USS, so a stylesheet cannot restyle these views as they stand. The creator is the one exception and the precedent: stable `name`s and `creator-*` classes, plus a `usePlaceholderStyle` flag that stops the inline look, plus a `styleSheets` list.
3. **There is nothing to show in the action bar or turn order.** BarrowsEnd has no combat or encounters until Phase 6. `AbilityBarView`/`TurnOrderView` can be skinned and shown in a dev scene, but not in the game.
4. **The handoff's slot set does not match the ruleset.** Wireframe C wants Head / Body / L-weapon / R-weapon / Feet. The BarrowsEnd ruleset has `slot-head`, `slot-armor`, `slot-mainhand`, `slot-offhand`, `slot-clothing`; there is no feet slot (locked decision: paper doll uses the ruleset's slots, no Feet). **Correction (Opus review):** `InventoryPresenter`/`InventoryItemSummary` already expose the slot *id* (`RequiredSlot`, populated regardless of equip state, and an equipped item's slot always equals it because `Equip` rejects a mismatch) - no presenter change is needed for 5.2.
5. **The handoff's secondary resource (mana pill) has no data.** Characters carry only `resource-hp`. The HUD shows an HP bar; a second bar renders only if a character has another resource.
6. The handoff's "WSL / Ollama / Hermes" testing bullets do not apply to this project (already flagged 2026-09-18).

## Locked design (high level)

**One skin, defined once, applied by stylesheet.** The look lives in a single BarrowsEnd stylesheet; toolkit views supply structure and stable class names only.

```
Kenney UI pack (originals, never edited)
        | copy
BarrowsEnd/Assets/Art/UI/Source/          <- read-only sources + LICENSE (NOT under Assets/Art/Source -- see D1a)
        | UiSkinBuilder (Editor tool, deterministic, idempotent)
BarrowsEnd/Assets/Art/UI/Parts/*.png      <- one PNG per part, Point filter, no mips, uncompressed
        | url() by path
BarrowsEnd/Assets/UI/Skin/barrowsend-skin.uss   <- tokens (:root vars) + component classes
BarrowsEnd/Assets/UI/Skin/BarrowsEndTheme.tss   <- @import default theme; @import skin
        | PanelSettings.themeStyleSheet  (one author, one asset per sorting layer)
every UIDocument (HUD, title, creator, paper doll) picks the skin up with no per-view attach
```

**Decisions and rejected alternatives (record so they are not re-litigated):**

- **D1 Per-part PNGs, not a sliced sprite sheet.** A per-part PNG is referenced from USS by a portable path (`url("/Assets/Art/UI/Parts/panel_brown.png")`, project-relative, not the Editor-internal `project://database/...?fileID=...&guid=...` form) with the slice set explicitly in USS (`-unity-slice-left: 8` ...); the alternative (a sliced sprite referenced by guid/fileID) is actually the rename-robust one but is opaque to read and diff, which is the real reason it's rejected. If the pack ships individual PNGs, copy those by name and skip cutting; otherwise `UiSkinBuilder` cuts them from the sheet using Kenney's XML (CPU blit from `LoadImage`, the 4.0 contact-sheet precedent, because the sheet is imported non-readable). Rejected: Sprite Editor slicing by hand (not reproducible), one big `Image` per part (no USS states).
- **D1a Source path moved out of the existing slicer's scan root (Opus review, blocker).** `BarrowsEndSetup.SliceAll` (`Assets/Editor/Content/BarrowsEndSetup.cs`) recursively scans `Assets/Art/Source` and force-converts every `Texture2D` there into a 16px-grid multi-sprite sheet. The original plan's `Assets/Art/Source/UI/` sits inside that scan root, so the first run of `Barrows End/Setup/Slice Kenney Sheets` would silently wreck every UI PNG's import settings (junk sprite rects on a `buttonLong_brown` that isn't a 16px grid at all) days after the fact. Fixed path: **`BarrowsEnd/Assets/Art/UI/Source/`**, outside that tree. A content test asserts nothing under it is Sprite-typed.
- **D2 Skin through the theme, not per-view attach.** `BarrowsEndTheme.tss` imports the default theme first and the skin second, so the skin wins ties without per-view code, and the creator/title/HUD share it. Rejected: `root.styleSheets.Add` in every view (the creator's current route; fine for one screen, error-prone for five). **This is S4's exact question and it is genuinely open** (whether a `.tss` can `@import` a `.uss`, and whether import order decides precedence, could not be confirmed by reading source): if S4 finds it does not work, D2 collapses to the rejected per-view-attach route and every "one author, no per-view code" claim below falls with it. S4 runs before anything is built on D2.
- **D3 Tokens as USS variables, components as selector lists.** Colours, spacing and font sizes are `:root { --be-... }` variables. USS has no mixins, so a component look is declared once on a *selector list* that mixes the skin's own primitives with the class names toolkit views already emit (`.be-panel, .party-card, .inventory-root { ... }`). BarrowsEnd-built elements (gallery, title) use the `be-*` primitives directly.
- **D4 Toolkit views keep structure inline, move look to USS, and gain one switch.** Each re-skinned toolkit view gets `usePlaceholderStyle` (default true, so every existing test and sample is unchanged) following the creator's precedent; BarrowsEnd sets it false. Sizing/positioning that USS should not own (whole-pixel preview, absolute HUD anchoring) stays inline. **Open sizing question (Opus review):** the creator itself doesn't fully follow this today - `CharacterCreatorScreen` sets `button.style.width/height` on every row and footer button *unconditionally*, not gated by the flag (`CharacterCreatorScreen.cs:250-269`), and Kenney's buttons have their own natural sizes (190x49 long, 45x49 square, 22x21 arrow) that don't match the creator's 36x32/110x36 boxes. 5.0's `PartyView` proof won't surface this (a party card has no natural part size), so **5.3 must decide explicitly**: either `usePlaceholderStyle = false` also drops inline sizes for skinned controls (sized by the part instead), or the skin's `-unity-slice-*` stretches to fit the existing inline box. Recorded here so 5.3 doesn't have to rediscover it.
- **D5 Pixel-exact by construction.** Reuse the creator's panel settings recipe: `ConstantPixelSize` scale 1, the runtime theme assigned, all five dynamic-atlas filters, Point-filtered part PNGs, plus `-unity-slice-scale: 1` explicit on every sliced rule (its default could not be confirmed from source; don't rely on it). Integer UI scale (2x on large displays) is an open question, not a 5.0 deliverable (locked: 1x for now, per user decision).
- **D6 Two panel settings, one author, new assets only in 5.0.** HUD screens at sortingOrder 0 and modal screens (title/creator/paper doll) at 10 come from one `UiPanelSettingsAuthor.Author(path, sortingOrder, ThemeStyleSheet theme, PanelScaleMode scaleMode)` that sets every field explicitly each run (the creator author's idempotent pattern). **Correction (Opus review, blocker):** the shipped `gate-panel-settings.asset` is `ScaleWithScreenSize` at 1200x800 today, and `PhaseTwoGateSceneAuthor` sets nothing else on it - unconditionally delegating it to the unified author (as v1 said) would re-skin and resize the *shipped* shell inside 5.0, contradicting "nothing shipped changes." **5.0 only authors the two new assets** (HUD, modal-new); `BarrowsEndCreatorAuthor`/`PhaseTwoGateSceneAuthor` keep their current settings untouched until 5.1 (gate) and 5.3 (creator/title) deliberately switch them over, called out as a look change when it happens.
- **D7 Class-name contract is text plus behaviour.** Views emit stable `name`s and semantic classes; a content test scans the skin USS for every class the toolkit views emit, and a PlayMode test proves the rule actually resolves and actually *differs state to state on the same element* (a rule that only differs from an unskinned control fails to catch a deleted `:disabled` rule - see the Tests section), so a typo or a rule beaten by an inline style is caught.

### Step 2: `UiSkinBuilder` (Editor tool, menu `Barrows End/UI/Build Skin Parts`)

- Input: a small manifest (`Assets/UI/Skin/SkinParts.json`) listing every part the skin uses: `{ "name": "panel_brown", "source": "<pack PNG file name>", "slice": [l,t,r,b] }`. **Since the pack ships 87 already-cut PNGs (Step 0), most entries are a straight copy; a bar is the one composite case** (`bar_back`, `bar_green`, `bar_red`, `bar_blue`: left/mid/right sources sliced 9/0/9/0 at 36x18 total covers every target width without repeating the mid tile - simpler than generating a wide bitmap, so composite generation is dropped in favour of just slicing the 3-part PNG directly). Not every pack part is used; the manifest is the shopping list (target set below).
- Output: `Assets/Art/UI/Parts/<name>.png` plus importer settings forced on every run: Texture Type Default, `filterMode = Point`, no mipmaps, `textureCompression = None`, `sRGBTexture = true`, `wrapMode = Clamp`, `alphaIsTransparency = true`, `isReadable = false` (the project's own precedent for forcing these, `BarrowsEndSetup.SliceSheet`, is real and works).
- Deterministic: same manifest -> byte-identical PNGs (a straight copy is trivially stable). Idempotent in effect, not mechanically no-op: `File.WriteAllBytes` + `SaveAndReimport` always touch mtime/re-import (the existing slicer does the same), so the tool compares output bytes and skips the write/reimport when unchanged, rather than claiming a byte-for-byte re-run leaves zero git churn.
- The slice values are also emitted into a generated `skin-slices.uss` fragment (`.be-part--panel-brown { -unity-slice-left: 8; -unity-slice-scale: 1; ... }`), so the slice numbers live in exactly one place (the manifest) and the hand-written skin never repeats them.
- Refuses (throws): a source part missing from the pack, a slice larger than the part's actual decorated border (see S1's real oracle - not "half the part", which is no guard at all on a 100px panel), a duplicate name.

**Target part set (verify each name against the XML at intake; this is the wireframes' shopping list):** panels: wood/brown (large, the paper-doll background), beige/tan (preview panel, stat block), grey/stone (options panel), inset (slots, rows); buttons: long and square in brown/grey/beige with pressed variants; round buttons (`buttonRound_*` + `iconCheck`/`iconCross`/`iconCircle` overlays, `cursorHand`); arrows: left/right (beige, silver); bars: back plus green/red/blue/yellow fills (composited); scrollbar (composed from `barBack_vertical*` + a `buttonSquare` handle); item slot (a `panelInset_*` square); empty-slot watermark (`cursorSword_*` or a `Game icons` sword, chosen in this step); no rivet parts exist. The green check / red X / eye of the handoff become tinted or colour-matched `iconCheck`/`iconCross` on round buttons; an "eye" icon has no pack part (drop or take from `Game icons`).

### Source facts checked before writing this plan (verify-first, not assumed)

1. **`ShellPanel.Summarize(CharacterState, IRulesDatabase)` is a static method three EditMode tests call directly** (`ShellStartFlowContentTests.cs:119,136,140`), independent of the `ShellPanel` MonoBehaviour/UIDocument. It must keep existing (signature and behaviour unchanged) even though the *widget* it currently lives on is being replaced - tests are not touched for this reason alone.
2. **`GateSessionServices.HitPoints` is a bare `DefinitionId` ("resource-hp"), not a `ResourceDefinition` asset.** `PartyPresenter`'s constructor wants a real `ResourceDefinition` (it reads `.Id` off it, only to compare against a `DefinitionId` again) - so the HUD needs `session.RulesDatabase.TryResolve<ResourceDefinition>(GateSessionServices.HitPoints, out var hpResource)` once at build time. This must succeed for the ruleset actually shipped (verified in a test, not assumed).
3. **`PartyPresenter.Rebind`'s missing `hitPointsResource`/`memberNames` re-supply does not affect BarrowsEnd, but for a different reason than first stated, and `Rebind` is still load-bearing.** **Corrected (Opus review):** it is not "membership is fixed" that makes this safe - party membership actually IS restored from save data (`SaveService.RestoreParty`) each load, it just always round-trips to the same hard-coded ids because `ShellBootstrap.SpawnParty` assigns them by a compile-time constant, not because the save format pins them. The real, stronger reason `memberNames` is safe: **no display name field exists in the save format at all** (`SaveService.CaptureCharacters` only persists id/stats/resources/conditions), so `memberNames` can only ever come from the authored `GateMemberSpec`, never from a load. `hitPointsResource` is safe because only its `.Id` (a compile-time constant) is ever read. **But `Rebind(PartyState, ICharacterRegistry)` is NOT a no-op to skip:** a load genuinely builds a brand-new `GameSession` (`SessionLoadCoordinator`/`RulesetSessionFactory`) and disposes the old one; without calling `Rebind`, `PartyPresenter` keeps reading the discarded `PartyState`/`ICharacterRegistry` forever, and the HUD shows stale pre-load data indefinitely. **A further, real toolkit gap this surfaced:** `PartyView` subscribes to `presenter.Party.Changed` in `Initialize` (`PartyView.cs:53`) and `Rebind` never re-raises or re-subscribes - after a load, the view stays subscribed to the *dead* `PartyState` and never refreshes again from world-driven selection changes. `PartyView.Refresh` is `private`, so the only supported recovery today is calling `Initialize` again, which resubscribes correctly but leaves a dangling handler on the discarded `PartyState` (harmless since that object is garbage after disposal, but worth doing properly). **Fix (toolkit change, Step 0 below): `PartyView` gains a public `Rebind(PartyPresenter)` that unsubscribes from the old presenter's `Party.Changed`, swaps the presenter reference, resubscribes, and refreshes** - cheaper than a full `Initialize` rebuild and leaves no dangling handler.
4. **The gate's shipped `gate-panel-settings.asset` is shared between `Core.unity`'s `ShellPanel` and the standalone `PhaseTwoGate.unity` demo scene - but D-5.1.6 does not touch it.** **Corrected (Opus review):** `PhaseTwoGateSceneAuthor.BuildPanelDocument` only loads-or-creates this asset and assigns it; it sets no theme/scale/sorting order of its own. `BarrowsEndCoreSceneAuthor` simply *stops loading this asset path* once `ShellPanel` is dropped - the `.asset` file itself is untouched, and `PhaseTwoGate.unity` (which never referenced anything `Core.unity`-side) is unaffected. There is nothing to repoint and nothing to re-test in the gate demo scene. **This also means D6's original promise ("5.1 deliberately opts the gate settings into the unified skin") does not actually happen in this task** - the gate asset stays exactly as authored (`ConstantPhysicalSize`, no theme) because `Core.unity` no longer uses it at all. `UiSkinContentTests.GateAndCreatorPanelSettingsAreUntouchedBy50`'s comment ("until 5.1 deliberately opts it in") becomes inaccurate and needs a one-line fix when this lands, not a behaviour change.
5. **The Kenney Adventure pack has no save/load/zoom-specific icons** - only `iconCheck`/`iconCross`/`iconCircle`, `cursorHand/Sword/Gauntlet`. The system menu uses small text buttons, not icon-only round buttons, to avoid inventing icon meanings the art doesn't support.
6. **The wireframe's party status is a horizontal STRIP per member** (name + a wide HP pip-row, stacked vertically as a column of strips), not a column of tall portrait-style cards. **This needs a real toolkit change, not just a skin edit (Opus review, blocker):** `PartyView.BuildLayout` sets `rosterContainer.style.flexDirection = FlexDirection.Row` **inline and unconditionally** (`PartyView.cs:87`, outside every `usePlaceholderStyle` gate) - an inline style beats any USS rule, so editing the skin's `.party-roster` rule to `column` alone is a no-op, exactly the class of bug the gallery's round-1 `Section()` review finding already caught once. **Fix (toolkit change, Step 0 below):** gate that line behind `usePlaceholderStyle` (row only when true), delete the skin's now-redundant `flex-direction: row` rule, and let the skin set `column` when the flag is off. Checked: `PartyViewSkinContractTests` never asserts `flexDirection` on the roster, so this doesn't touch either existing test.
7. **The `hp-bar`'s width is a hard-coded toolkit constant, and the strip reshape breaks it (Opus review, blocker).** `PartyView.HpBarWidth = 120f` is applied as a fixed inline `bar.style.width` and reused to compute the fill (`fill.style.width = HpBarWidth * percent`) - the round-2 gate-review fix for the earlier percentage bug. A skin cannot resize this bar (inline wins again), and a `.party-card` reshaped to a 140px-wide row with a 120px bar plus a name and HP label alongside it overflows exactly like round 2's bug, just from the opposite direction. **Fix (toolkit change, Step 0 below):** replace the fixed constant with a `RegisterCallback<GeometryChangedEvent>` on the bar that recomputes the fill's pixel width from the bar's own *actual* resolved width whenever it changes - removes the hard-coded number entirely instead of moving it, and works regardless of what width the skin or a consumer gives the bar.

### Decisions

- **D-5.2.1 The doll shows the party's currently ACTIVE character, with left/right `be-arrow` buttons to cycle party members.** **Correction (Opus review, blocker): NOT via `PartyPresenter.CycleActiveNext`/`CycleActivePrevious`.** Those cycle over the SELECTED subset (`PartyState.CycleActive` iterates `members.Where(selected.Contains)`), and normal play always leaves exactly one member selected (boot selects `Members[0]`; every HUD card click calls `PartyPresenter.SelectCharacter`, which clears selection down to one) -- with exactly one member selected, cycling is a mathematical no-op: it would compile, raise `Changed`, and never move `ActiveCharacter`. Instead: `DollPresenter` keeps its own index into `party.Members` (not `Selected`) and calls `party.Select(next)` + `party.SetActive(next)` directly on the arrow click.
- **D-5.2.2 Retargeting the preview (on cycle, and on open-after-load) needs an explicit `Unbind()` + `Initialize()` pair, not just a new `SpriteLayerState`.** **Correction (Opus review, blocker):** `SpriteEquipmentBinder.Initialize` (and `SpriteAppearanceBinder.Initialize`) throws `InvalidOperationException` if called again for a different character/inventory/event-bus tuple without an intervening `Unbind()` first -- confirmed by reading the guard directly. Two places hit this: cycling arrows (fixed by D-5.2.1, then immediately throws without this), and re-opening the doll after a load (`GameSession` builds a brand-new `Party`/`Characters`/`Inventory`/`EventBus` every load, so the doll's persistent binders see a different tuple). `Unbind()` leaves the doll's own `SpriteLayerState` target intact, so `Unbind()` -> `Initialize(newCharacter, newRules, newInventory, newEventBus)` re-reconciles onto the same preview state with no second `SetTarget` call needed.
- **D-5.2.3 The preview needs BOTH an appearance binder and an equipment binder, and the state needs the full 7-slot compositor order.** **Correction (Opus review, blocker):** `SpriteEquipmentBinder` alone only paints EQUIPMENT layers -- body/feet/clothes/hair come from `SpriteAppearanceBinder` (`state.ApplyAppearance(character.Appearance, ...)`), which the creator also calls separately. Without it the doll shows gear floating over an empty canvas. The `SpriteLayerState` itself must be built via `SpriteLayerCompositor.DefaultSlots()` (body, feet, clothes, hair, helmet, shield, weapon -- the same order the shipped character prefab and the creator both use), the exact mechanism Task 4.0/4.1 pinned "preview equals world" on -- reusing anything narrower would silently break that equivalence.
- **D-5.2.4 The preview must call `LayeredSpritePreview.Refresh()` explicitly; nothing does this automatically.** **Correction (Opus review, blocker):** `Refresh()` is deliberately explicit with no scheduler (its own doc comment says so) and has exactly one caller in the whole repo -- `CharacterCreatorScreen.Refresh()`, itself driven by the creator's own `Changed` event. `SpriteEquipmentBinder`/`SpriteAppearanceBinder` only bump the `SpriteLayerState`'s `Version`; nothing bridges that to the preview widget. `DollView` must call `preview.Refresh()` itself: immediately after each equip/unequip command returns (the event publish inside `EquipmentService` is synchronous, so the state is already current by the time the call returns), after every retarget (D-5.2.2), and from its own subscription to `ItemEquipped`/`ItemUnequipped` on the event bus (for changes the doll didn't itself cause -- loot, a dialogue `GiveItemAction`; `InventoryView.Subscribe` already does exactly this and is the precedent to copy, `InventoryView.cs:54-58`).
- **D-5.2.5 Ability scores: show the block for every member, reading whatever `StatBlock.GetScore` returns (0 for an absent score), not a placeholder or a protagonist-only special case.** Given finding 5, three of four members will read all-zero today -- this is accepted as a known, visible content gap (not fixed by this task, which owns the UI not the character data) and called out explicitly at the human-check step, not discovered live.
- **D-5.2.6 Equip/unequip interaction, no drag-and-drop:** click a backpack item to select it (a `be-slot--selected` highlight); if it has a `RequiredSlot`, equip it via the same `InventoryPresenter.Equip(instanceId, character, slot)` call `InventoryView` already uses (finding 4), displacing whatever occupied that slot back to the backpack. Click a worn (non-empty) anatomical slot to unequip it back to the backpack (`InventoryPresenter.Unequip`). Matches the project's established KISS preference (no positional/drag inventory anywhere else in the codebase either).
- **D-5.2.7 Modal is `UIToolkitPointerCapture.BeginModal()`/`Dispose()`, not merely `Register`.** **Correction (Opus review, should-fix):** the original plan conflated two different mechanisms in the same class. `Register` alone (what Camp/Store/Dialogue/the creator actually do) makes a panel's own UI Toolkit elements correctly swallow clicks landing ON them -- it does NOT block every other screen position the way "the doll is modal, no world click gets through anywhere while it's open" requires. `BeginModal()` (currently called only by `ConversationController`) is the real mechanism: while `modalDepth > 0`, `IsPointerOverUI` returns true for every position, not just ones over registered UI. Open calls `BeginModal()` and keeps the returned `IDisposable`; Hide/`OnDisable` disposes it. `modalDepth` is static, so a leaked scope (an exception between `BeginModal` and `Dispose`) blocks all world input for the rest of the session -- dispose in a `finally`/`OnDisable`, not just the normal Hide path.
- **D-5.2.8 The doll reads `EquipmentService`/`InventoryPresenter` from `GateSessionServices` (already rebuilt per session), and re-`Rebind`s after a load, matching `HudBootstrap`'s own precedent.** `GateSessionServices.Equipment` already exists and is reconstructed on every `Rebind`; `InventoryPresenter.Rebind(inventory, rulesDatabase, equipmentService)` already exists for exactly this. `HudBootstrap.OnLoadClicked` already rebuilds its `PartyPresenter` the same way after `LoadNow`'s callback -- the doll's `DollPresenter`/binders follow the identical pattern (rebuild/rebind, then D-5.2.2's Unbind+Initialize on the sprite binders), not a separate mechanism.
- **D-5.2.9 Backpack: a wrapping grid of `be-slot`s, one per `InventoryPresenter.GetSharedItems()` entry, in list order** -- no positional data exists to do anything else; `be-scroll` appears only if the party's real item count in Phase 6 content actually overflows the visible grid (verified then, not pre-built against a guess).

### Gate review round 1 (user, 2026-09-25) -- three real bugs found live, fixed same session

You looked at the gallery and reported three problems, all real:

   - **A layout bug in the gallery, not the skin:** `Section()` unconditionally forced `flexDirection: Row` onto whatever content it wrapped, which ran *after* `BuildBars()` had set its own `Column` layout on the same element (a returned `col`, not a new wrapper) -- last-write-wins clobbered it, so all six bar rows laid out side by side and were squeezed by the row's own `width: 200` instead of stacking at their intended 160px. Fixed by deleting the forced override (every `Build*()` method already sets its own correct `flexDirection`).
   - **A real width-resolution bug**, worth keeping in mind for any future bar/pip work: a `Length.Percent` width on `.be-bar__fill` (`position: absolute`) resolved against the fill's own native background-image size (36px, the composite's actual pixel width) instead of the bar's actual layout width (160/120px) -- 25% rendered as ~9px, 50% as an 18x18 square (a "green circle"). ### Gate review round 2 (user, 2026-09-25) -- round 1's own fixes were incomplete; measured this time, not eyeballed

You looked again and reported two of round 1's "fixes" hadn't actually landed: the disabled button was *even less* legible, and the health bars now overflowed their card. Both were measured with a new, real diagnostic (rendered-pixel sampling + a WCAG-style contrast-ratio calculation, and a card/bar layout dump) rather than guessed at a third time, kept afterward as permanent assertions in `SkinGalleryScreenTests`.

1. **Disabled button, root cause found: round 1 never actually removed the dimming.** Measured contrast ratio after round 1's fix: **1.05** (WCAG wants >=4.5 for normal text) -- confirmed numerically, not just by eye. Cause: round 1 deleted `.be-button:disabled`'s OWN `opacity: 0.6` line, but UI Toolkit's **built-in default theme** applies its own `opacity: 0.5` to any disabled control regardless of what this rule does or doesn't set -- removing our rule's opacity never cancelled that default one, so the button kept fading toward the dark screen behind it exactly as before. Fix: explicit `opacity: 1` in `.be-button:disabled` (and `.be-button--round:disabled`) to cancel the built-in default, a much darker tint (`rgb(30, 30, 30)`, tuned by re-measuring after each change -- 120 measured 2.7:1, 70 measured 3.16:1, 30 measured 3.66:1 with a flawed sample point, then 14.46:1 once the sample point itself was fixed, see below), and the light `--be-ink-on-dark` token for the label instead of a dark grey. **A second bug in my own diagnostic, also worth recording:** the first few re-measurements barely moved despite large tint changes because the sample point (40px left of the button's centre) was landing on a pixel of the "DISABLED" label's own glyph, not the background -- moved the sample to just inside the button's left edge, clear of the centred text, and the numbers finally tracked the tint changes correctly.
2. **Health bars overflowing the card, root cause found: the card's declared width was silently shrinking.** A card's `resolvedStyle.width` measured **88px**, not the 140px `.party-card` declares -- the gallery's demo container was a fixed 400px wide, too narrow for 4 non-shrinking 140px cards plus margins, so the roster's flexbox shrank each card by default. The `hp-bar` inside stayed a fixed 120px regardless of its parent's shrunk size, so it overflowed. Fix: `.party-card` gained `flex-shrink: 0` (a party card should never silently shrink -- if its container is too narrow it should overflow the roster, not become illegible), and the gallery's demo container was widened from 400 to 620px so this specific demo doesn't need to invoke that behaviour at all. Re-measured: card width 140px, hp-bar 120px, comfortably inside the card's 124px content width (140 - 8px padding each side).

**Both fixes are now permanent, asserted regression guards, not just log output:** `SkinGalleryScreenTests` gained a real assertion that every card's hp-bar width fits inside its content width, and a real WCAG contrast-ratio assertion (>=4.5:1) on the disabled button's rendered pixels. `UiSkinSpikeTests.S4_B`'s old assertion (`disabled must dim opacity`) was updated to its new, deliberate opposite (`disabled must NOT dim opacity -- tint/colour carry the look instead`), since that old assertion encoded exactly the design round 2 corrected.
