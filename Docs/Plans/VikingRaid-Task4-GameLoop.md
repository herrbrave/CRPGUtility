# Viking Raid -- Task 4: the game loop (design v2: Opus-reviewed; Section 6 SUPERSEDES conflicting text above)

Status: DESIGN v2 -- reviewed by Opus (18 findings: 1 blocker, 6 major, 11 minor; all adopted). Parent plan `VikingRaid-Implementation.md`.

## 1. Goal

Make the scene playable end to end: boot -> four heroes on the start clearing -> click-to-move exploration (formation, camera follow) -> the party reaches an encounter trigger -> it walks to the encounter's stage anchors -> a toolkit tactical fight (turn order HUD, ability bar, click to target, AI goblins) -> win: everyone is healed and revived and the road continues; wipe: banner, then scene reload at the encounter's checkpoint; kill the E4 boss: "Camp destroyed" screen. Non-goals: save/load UI, inventory, dialogue, sound, menus, gamepad.

Inputs we can rely on (already built and tested): `WorldLayout`/`WorldAnchors` (stage points, goblin spawns, triggers, checkpoints), `WorldLayers` masks, the ruleset + 15 NpcDefinitions + brains (`vr-brain-*`), `VetoZeroScoreDecisionProvider`, roster prefabs (on layer `Character`, `ModelActionCues` for hit/down/death glue), `GameDesign` ids, the Arena harness (the proven service wiring), BarrowsEnd's `TacticalCombatSession`/`GateCommandSource`/`EncounterTrigger` (the proven 2D version of the same loop).

## 2. Architecture (all project-local, `Assets/Game/` in `VikingRaid.Game`; the toolkit is NOT changed)

* **`VikingGame`** (MonoBehaviour, the composition root; authored into the scene by `WorldAuthor` on a `Game` object together with `InputSystemCommandSource`, a `UIDocument`+`HudRoot`, `AbilityBarView`, `TurnOrderView`, `PartyView`, `VikingCamera`). `Build()` starts a real `GameSession` from `VikingRaidRulesetProvider` (SRD5 policies), constructs everything below, and is callable by tests with an injected `IPlayerCommandSource`.
* **Spawning.** Heroes and all 14 goblins are spawned through `WorldSpawnService.SpawnNpc` from their `NpcDefinition` (visualPrefab = the roster prefab) at boot, goblins idle on their `goblinSpawns` anchors with stable spawn ids (no pop-in). The heroes join `session.Party`. Encounters before the checkpoint index are not spawned.
* **`VikingCommandSource`**: port of `GateCommandSource` (party-only Select, `CombatMoveOverride`, Interact dropped in combat). Wraps any inner `IPlayerCommandSource` so tests can drive it.
* **Exploration**: `PartyExplorationController` + `PartyMovementService(NavMeshService, SceneSelectableSource)` + `WedgeFormationSolver`, motors registered from each agent; a member that is downed (HP <= 0 or DeathSaves) cannot be moved.
* **`VikingEncounterTrigger`** (added at boot to each anchor trigger box): when a party member's collider enters (and no fight/stage in progress, and the encounter is armed) -> `Stage` -> `StartEncounter`. Disarmed after firing; re-armed on scene reload; ignored while any fight runs (E4's trigger sits in the gate, near E3's goblins).
* **Staging**: on trigger the heroes are ordered to their `partyStage` anchors through their `NavMeshCharacterMotor` (in party order), goblins already stand on their spawn anchors; combat starts when all four are within 0.5 m or after 6 s (stragglers are `Warp`ed to their anchors). This is what makes the fights start from the simulated geometry.
* **`VikingCombatSession`**: adapted from BarrowsEnd's `TacticalCombatSession` with this game's differences: real SRD5 policies from `session.Policies` (attack bonus, AC, saves, resistance, initiative), `EncounterFactionProvider`, `PhysicsLineOfSightProvider(WorldLayers.SightBlocker)` wrapped to eye height 1.4 m, `TurnResourceSet(action, bonus, reaction, movement)` (all already granted by the NpcDefinitions), `CharacterAnimationPresentationHook`, per-combatant brains (`PerCombatantDecisionProvider` over `VetoZeroScoreDecisionProvider(UtilityAIDecisionProvider)`), `AbilityTargetingGate(scheduler, resolution, WorldLayers.Hittable)`, HUD bridge, a `DeathSaveService` built ONCE per session (heroes: `usesDeathSaves`, never die; goblins die outright), `CreatureDied` -> `MarkDefeated` (the controller does it) and `RemoveCombatant`.
* **Down / revive rules (review 9.1.5)**: "down" = HP <= 0. Each tick any hero with HP > 0 and (DeathSaves != null or Unconscious) is cleared (`ConditionRemoved` published so the model stands up). A downed hero's turn rolls its death save and passes. At victory every hero is healed to full and revived. Defeat = all four heroes at HP <= 0 (a downed party cannot be saved: death saves would only prolong it).
* **Defeat/checkpoint**: static `Checkpoint.Index` (reset in `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]`), set to k when encounter k is WON (next fight's checkpoint), 0 at start. Wipe -> "Fallen..." banner for 2.5 s -> `SceneManager.LoadScene`; boot places the party on `checkpointSlots` of encounter k (or the start slots), full HP, encounters < k not spawned, encounter k armed.
* **Victory**: when E4's goblins are all dead -> heal, "Camp destroyed" overlay with a Play Again button (index 0 reload).
* **`VikingCamera`**: perspective follow camera behind the selected hero (yaw along the road, pitch ~42, distance 16, mouse wheel zoom, enabled post-processing), and a tactical mode: on `EncounterStarted` it eases to the arena `cameraTarget` (distance 30, pitch 48) and back on end.
* **HUD**: toolkit `HudRoot` regions: ability bar (BottomRight), turn order (BottomLeft), party roster/HP (TopLeft); a project-local banner label (TopCenter) for "Ambush!", "Victory", "Fallen", feedback lines for rejected targets.
* **FX (phase 2 of the task, after the loop tests are green)**: impact FX at the target on hit, heal FX on Verse/Second Wind, arrows and the shaman bolt as projectiles released at the animation's release frame (bow draw: 0.97 s), the target's hit reaction delayed to the arrival.

## 3. Test plan (PlayMode on the real scene; EditMode for pure rules)

Injected input makes the whole game scriptable: tests supply a fake inner command source and call `Raise(Move/Select)`; combat actions go through the REAL `AbilityTargetingGate` armed through the real ability bar presenter where practical, else `Scheduler.StartAbility`.
1. Boot: a session exists; 4 party members at the start slots on the NavMesh; 14 goblin agents on their spawn anchors with ids; HUD regions exist; scene camera is the VikingCamera.
2. Exploration: a Move command to a road point 20 m ahead moves all four in formation (positions change toward it, stay on the NavMesh); a Select on a goblin is ignored without an exception (party-only select).
3. Trigger: walking the party into E1's trigger starts staging; hero positions reach the stage anchors (< 0.5 m); the encounter then starts (turn order has 7 combatants) from exactly the Task 2 formation.
4. A scripted fight: the Task 2 hero policy driven through the real scheduler wins E1 (seeded) with the goblins played by the real driver; afterwards: all heroes at full HP, no `DeathSaves`, no `condition-unconscious`, trigger disarmed, `Checkpoint.Index == 1`, party can move again.
5. Downed hero: force a hero to 0 HP mid-fight: death save rolls on its turn; healing it clears the state (revive sweep); a goblin never attacks a downed hero while another stands (the Task 2 regression, now live).
6. Defeat: drive all four heroes to 0: banner, then scene reload; the party stands on checkpoint slots of the current encounter at full HP and that trigger is armed.
7. Victory: kill E4's goblins: overlay shown, game state "won".
8. Input arbitration: during combat a ground click moves only the active hero within its movement budget; a click on a goblin with an ability armed attacks; a click on a goblin with none armed does nothing and throws nothing; Interact is dropped.
9. Teardown: two consecutive fights (E1 then E2) leave no orphaned subscriptions/HUD regions (the second fight works; event counts are stable).
Mutation checks: break the revive sweep, the zero-score wrapper, the stage walk, the checkpoint index, the party-only select -> the matching test must fail.

## 4. Risks and what answers them

| Risk | Answer |
|---|---|
| Animation timing (damage lands before the swing) | `ModelActionCues` delay (Task 1) + ability `RecoverSeconds`; verify in a capture sequence; projectiles in phase 2 |
| UI Toolkit panels in batch/PlayMode (PanelSettings, click-through) | author the PanelSettings asset in `WorldAuthor`; tests assert regions exist, not pixels; one capture of the HUD |
| Session-scoped state across scene reload (static flags, event subscriptions) | everything session-scoped is created in `Build()` and torn down in `OnDestroy`; checkpoint index is the only static |
| Staging fails (blocked agent, motor not ready) | 6 s timeout then `Warp`; test 3 asserts the happy path and a mutation breaks it |
| Toolkit APIs unproven in 3D at this scale (`PartyExplorationController` with NavMesh motors, `TacticalPlayerMoveAdapter` on a 374 m mesh) | the tests above exercise exactly those; any toolkit bug found is fixed at the root with a test and flagged |
| Heroes spawned as NPCs (no `CharacterCreator` path) | `NpcDefinition.faction` unused; party membership is `session.Party.AddMember`; death-save/`usesDeathSaves` keyed on party membership |

## 5. Questions for the reviewer

* `TacticalEncounterController` constructor calls `StartCombat` immediately: is calling it after the staging walk correct, and what is the right order for `StartEncounter`, the HUD init and the camera mode so the first frame is consistent?
* Is a scene reload with a static checkpoint index the cheapest correct defeat path, and what breaks on `LoadScene` while a `TacticalEncounterController`/UI bridge/`InputSystemCommandSource` is live?

* Are the tests above vacuous anywhere, and what is missing that will bite in the Task 5 full playthrough?


## 6. Opus review record and v2 decisions (2026-10-05) -- SUPERSEDES Sections 2-5 where they conflict

18 findings (1 blocker, 6 major, 11 minor), all adopted; the toolkit stays unchanged (fixes are project-local).

### 6.1 Blocker and majors
1. **A move that cannot arrive never ends and soft-locks the fight.** `NavMeshCharacterMotor` reports Arrived only within `max(0.1, stoppingDistance)`; `MoveActionExecution` has no timeout; while it runs the AI driver, End Turn and the targeting gate all wait. Melee goblins aim at a point 1.5 m short of their target, so three grunts ordered onto one hero have end points ~0.2 m apart (agent radius 0.35: they can never reach them); a player click 0.3 m beside a goblin has the same problem. Fix: (a) a **move watchdog** in `VikingCombatSession.Tick` -- if the current action is a move and elapsed > budget/speed + 1 s, or speed stays under 0.05 m/s for 0.5 s, `Scheduler.Cancel()` (it settles the distance walked); (b) our own **move handler** replaces `TacticalPlayerMoveAdapter`: sample the click onto the NavMesh (1.5 m), push it out of other combatants' radii, pass NO potential reactors (also removes the stop-start threat-circle stutter, finding 8), show feedback on a rejected click; (c) idle combatants get a lower `avoidancePriority` number than the moving one so they are not shoved. Tests: two grunts ordered onto the same hero, a click 0.3 m from a goblin: each action ends within N seconds.
2. **A hero stabilised at 0 HP (three death-save successes clear `DeathSaves` but leave HP 0 and Unconscious) must not get a turn.** One predicate everywhere: `IsDown = HP <= 0`: turn skip (end the turn even when a death-save roll does nothing), the ability bar for that turn, the move handler and `canMove`, win/defeat checks. The revive sweep clears DeathSaves/Unconscious only when HP > 0 (a heal). EditMode test with a stable hero at 0 HP. (The Arena sweep checked only DeathSaves: fix it and its test too.)
3. **Ending a player turn / stale ability bar.** The toolkit has an End Turn button but `AbilityBarView.Refresh` runs only on turn events, so after a bonus action the buttons stay enabled and a repeat cast is silently rejected. Fix: call `abilityBarView.Refresh()` on every `AbilityResolved` and when the scheduler goes idle; auto-end the turn when the Action is spent AND (the bonus action is spent OR no bonus ability is useful: Second Wind needs HP < max and a use, Verse needs a wounded ally within 8 m and a use, Reckless is never useful after attacking); a hint line "bonus actions before attacking"; hide the bar region on non-player turns (End Turn must not end a goblin's turn); disarm the gate on every `TurnStarted`.
4. **E4's trigger never fires if a hero is already inside it when E3 ends** (`OnTriggerEnter` is one-shot and ignored mid-fight). Fix: while a trigger is armed, and at every fight end, poll `Physics.OverlapBox` on the Character layer (BarrowsEnd learned this, Phase 6 B8).
5. **Staging.** Input must be blocked from the trigger until `StartEncounter` (set `CombatMoveOverride` to a no-op; a click would override the stage order). The walk (17 m + wedge depth at 4 m/s = 4.5-5 s) is close to the 6 s timeout and a one-hero selection leaves the others far behind: `SelectAll` at the trigger and at fight end; timeout 9 s. The staging test must count warps and assert zero and arrival in under 9 s (a warp otherwise masks a broken walk).
6. **Test harness.** (a) `Build()` runs once, from `Start`; tests inject input through a static `VikingGame.CommandSourceFactory` read in `Start` (survives `LoadScene`, reset in `[SetUp]`/`TearDown`); (b) all statics (`Checkpoint.Index`, the factory) are reset in `[SetUp]`; (c) a fake inner source would bypass the click router (hittable mask, collider layers, targeting priority), so tests inject a real `PlayerCommandRouter(new SceneSelectableSource(), fakeCapture, WorldLayers.Hittable)` and drive pointer down/up with `camera.ScreenPointToRay(camera.WorldToScreenPoint(target + 1 m))`; (d) the ability bar is driven headlessly by finding buttons in its region and submitting `NavigationSubmitEvent` (BarrowsEnd's `UiClick.Submit`), waiting 2 frames after the panel builds.
7. **Tests 5/6 must go through the real damage path** (`Execute`/`DamageEffect` raise `CreatureDroppedToZeroHP`; writing HP directly sets no DeathSaves) and test 5 builds the exact farming scene (a downed hero beside a goblin with 0 movement, the others 10 m away) instead of hoping E1 reproduces a bug seen in 77 of 400 E4 fights.

### 6.2 Minors
8. Reactor stutter: solved by 1(b). Clicks on hills/the eroded edge fail path calculation: sample first, show a message. 9. The router always sends `Facing = Vector3.forward`: `VikingCommandSource` rewrites Facing to (destination - party centroid). 10. `PartyView` refreshes only on `Party.Changed`: poll an HP signature and `RefreshNow` (BarrowsEnd `HudBootstrap`). 11. `HudCorner` has no TopCenter: banner on `HudRoot.DocumentRoot` with `PickingMode.Ignore`; dispose any modal pointer capture before `LoadScene` (its depth is static); never use `Time.timeScale` for the banner. 12. `WorldAuthor` must serialise `InputSystemCommandSource.hittableMask = WorldLayers.Hittable` and `raycastCamera` = the game camera (the Task 3 placeholder camera becomes the VikingCamera); the camera's wheel zoom must check the pointer is not over UI. 13. `AbilityTargetingGate` picks the nearest `CharacterAgent` hit, so a hero standing in front of a goblin causes a rejection: accepted for now (flagged), revisit after a live play. 14. Checkpoint index = encounters WON (0..4), spawn at `encounters[Index].checkpointSlots` (Index 4 = victory, never reloaded into); 0 means E1's checkpoint, not the start clearing (the start clearing is only the first boot). 15. `DeathSaveService(canDie: id => !IsParty(id))`: an overkill hit must not kill a hero (`MarkDefeated` would destroy a party member). 16. Tick order: `controller.Tick` -> revive sweep -> downed-turn skip -> pending end turn -> watchdog -> `aiDriver.Tick` -> win/defeat poll; never `EndCombat` from inside a bus handler. 17. Spawn ids include the encounter (`e3-goblin-warrior-a`): `goblin-warrior-a` appears in E2 and E3. 18. Live fights are not deterministic: tests run at `timeScale` 3-4 and assert outcome classes; the victory heal/banner waits until the scheduler is idle plus ~1 s (after the death cue), not the frame of the killing blow.

3. PlayMode `GameLoopTests` (boot, exploration, real-router clicks, staging with zero warps, a scripted fight through the real bar, stable-at-0, farming scene, move stalls, E4 re-entry, defeat reload, victory, two fights after a reload).
4. FX (impact, heal, projectiles at the release frame) once the loop tests are green; HUD capture; mutation checks; results.
