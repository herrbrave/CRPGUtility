# Phase 4 Detailed Design: 2D character creator

> Status: DRAFT v2 (2026-09-20), post-Opus review; awaiting user approval. Child of `Docs/Plans/2D-Campaign-Implementation.md` (Phase 4 / Task 4.1 stub, scope from the GUI handoff's wireframe B, `BarrowsEnd/Docs/Handoff/Barrows-End-GUI-Handoff.md`).
> Nothing here authorizes implementation or committing. The "Review record" at the end lists every Opus finding and its disposition; v2 folds them in directly.

## Goal

A new game opens on a creator screen: a live preview of the assembled layered sprite on the left, `< Category: Value >` cycling rows on the right, Confirm. Confirm produces the player's protagonist (a `CharacterBuildPlan` with rules choices AND appearance), and the shell spawns the party with that character first in the party, selected, wearing the chosen weapon. Every later scene, save and load treats the protagonist like any other character (the save already round-trips appearance, format v3).

Non-goals: the UI re-skin (Phase 5 Task 5.3 is only the USS/texture pass over this structure); customizing the companions; respec or mid-game appearance change (D6); Elf (toolkit gap, see risks); a Name row (see Deviations).

## Deviations from the master plan and the wireframe (flagged)

- **Preview is a UI Toolkit `Image` stack over a real `SpriteLayerState`, not `SpriteLayerCompositor`** (master plan, Task 4.1: "via Task 2.5's `SpriteLayerCompositor`... re-feeds the same compositor used in-world"). Reason in D1.
- **No Race/Background screens** (master plan: "Reuses `CharacterBuildPlan`/`CharacterBuildService` for the Race/Class/Background choices"). The player picks a Class; Race and Background are fixed (D5).
- **Rows are Skin / Hair / Outfit / Weapon / Class**, not the wireframe's Head/Body/Weapon/Class. This is the user's own Gate A answer (`Docs/Plans/2D-Campaign-Phase2-SpritePresentation.md:34, 311`); helmet and shield are equipment, not creator rows.
- **The master plan's "new consumer-side data (an archetype/layer-option catalog)" is half-stale:** `CharacterBuildPlan.Appearance` already exists and `Build` copies it (Task 2.4). What is missing is the curated list of creator choices (D3).
- **No Name row.** `CharacterState` has no name field, `CharacterBuildPlan` has none, the save does not round-trip one (the sample says so, `CharacterCreatorView.cs:232-233`). Adding it is a toolkit + save change that does not belong in a look-and-class creator; recorded as a follow-up.

## What exists (verified in source)

- `CharacterBuildPlan.Appearance` (`SetAppearance/ClearAppearance`, `CharacterBuildPlan.cs:26-38`), copied by `CharacterBuildService.Build` (`:41`). Plan -> `CharacterState.Appearance` -> save -> `SpriteAppearanceBinder` is real.
- Seven `SpriteLayerCatalog` assets, **436** options (body 10, feet 20, clothes 120, hair 80, helmet 36, shield 60, weapon 110), ids `<slot>-<sheet>-<col>-<row>` (permanent), `displayName` still the raw id. `SpriteLayerCatalogValidator` already exists (`Editor/Validation/`).
- `SpriteLayerState.ApplyAppearance(map, ISpriteOptionSource)` is pure; `SpriteCatalogSource` needs only an `IRulesDatabase`. **Both binders already expose `SetTarget(SpriteLayerState)`, documented "for a consumer with no compositor (a UI preview)"** (`SpriteAppearanceBinder.cs:69-74`, `SpriteEquipmentBinder.cs:93-99`). `SpriteEquipmentBinder.Initialize` still needs a character + inventory + event bus (`:58-62`), so a preview applies an item's profile directly: resolve `ItemDefinition.EquipmentVisualProfileId` -> `EquipmentVisualProfile`, then `state.SetEquipment(inventorySlot, profile.SpritePriority, paints, profile.HiddenLayerSlots)` (~10 lines mirroring `SpriteEquipmentBinder.cs:214-219`). No toolkit seam needed. Equipment is keyed by inventory slot (`slot-mainhand`), as the binder does (`:218`).
- Sprite import: `textureType 8`, `spriteMode Multiple`, `filterMode Point`, `isReadable 0`, 16 PPU, no SpriteAtlas. UI Toolkit `Image.sprite` does not need readability; with the default `m_ActiveFilters: 31` non-readable/point textures stay out of the dynamic atlas, so point filtering survives. Caveats: the panel's reference PPU is 100 (size the preview in explicit px), the creator needs its **own** `PanelSettings` (the existing one is the gate's), and UI Toolkit cannot reproduce `SpriteLayerCompositor.TintMultiplier` or the double-sided URP sprite material.
- Rules content: races Human/Dwarf/Elf/Halfling; backgrounds Acolyte/Criminal/Sage/Soldier; classes Barbarian/Cleric/Fighter/Rogue/Wizard. `Build` requires only `plan.IsComplete` (no pending choices) - race/class/background/scores are all optional, but `StatBlock.GetScore` returns **0** for an unset stat, so a creator must set all six. **Level-1 choices are mandatory per class**: Barbarian 1 requirement (2 selections); Fighter 2 (fighting style x1, skills x2); Cleric 2 (skills x2, cantrips x3); Wizard 2 (skills x2, cantrips x3); Rogue 2 (skills x4, expertise x2). Human and the four backgrounds have no choices. Elf's high-elf feature has an unresolvable choice (`options: []`, `filterTag`), so `IsComplete` can never be true.
- **`CharacterBuildService` never grants hit points**: `ClassDefinition.HitDie` is referenced nowhere else in the repo, and no SRD5 feature grants `resource-hp`. `ShellBootstrap.SpawnParty` hand-adds it from `spec.maxHp` (`:150`); `GateSessionServices` (`:33,78,150`) and the party prefab's combat cues key on it.
- **Weapons:** exactly one campaign weapon has a sprite visual profile (`item-short-sword` -> `visual-short-sword`); SRD5 weapons (Longsword etc.) have none, so `SpriteEquipmentBinder.Apply` clears the slot (`SpriteEquipmentBinder.cs:196-204`) and they draw nothing. `ItemDefinition` has no weapon-category field and `ClassDefinition` no weapon proficiencies, so "what this class can wield" is not ruleset data.
- **`ShellBootstrap`:** `Boot` (`:83-124`) always starts a fresh session, loads and activates the starting location (`:102-106`), then `SpawnParty` (`:108`), camera last (`:120`). There is **no boot-time load**: `LoadNow` is reachable only from the `ShellPanel` Load button (`ShellPanel.cs:53`) and tests. `SpawnParty` **ignores `spec.gear`** (unlike `GateBootstrap.SpawnParty`, `:139-150`, which creates `ItemInstance`s and calls `EquipmentService.Equip`): the gear authored on Aldric in `Core.unity:365-368` is never worn (an existing latent defect). `SessionLoadCoordinator.cs:462-468` **throws** if `partyVisualPrefabs` lacks a restored party id; that dictionary is filled only inside `SpawnParty` (`:159`). The authored party is **Aldric, Brenna, Corvin, Dessa** (`Core.unity:356-397`); Garrick/Elara/Silas appear only in the handoff's wireframe A. `SpawnParty` selects `Members[0]` (`:165`).
- No combat/ability UI exists in BarrowsEnd yet (`ShellPanel` = party status + message + Save/Load/Zoom).
- No test in the repo drives a UI Toolkit control with pointer/navigation events (grep for `SendEvent`/`ClickEvent`/`PointerDownEvent` finds nothing); the "real click" in `ShellTests` is reflection into `PlayerCommandRouter.HandlePointerDown/Up` with a hand-built ray (`ShellTests.cs:82-92`).

## Design decisions

**D1. Preview = stacked UI Toolkit `Image` layers driven by a real `SpriteLayerState`.** Considered: (a) a real sprite-wrapper prefab in a preview scene, camera -> `RenderTexture` (the literal in-world path; workable - Play-mode RenderTexture capture is the route `ShellCaptureTests`/`GateCaptureTests` already use), or (b) a pure `SpriteLayerState` painted as one `Image` per slot in a fixed 16x16 box, integer-scaled, point-filtered. Choosing (b) on its merits: one state class and one set of layer/hide/replace rules shared with the world; unit-testable in EditMode with no camera, scene lifecycle or second panel; no preview scene. Cost stated honestly: (a) would exercise the real compositor/URP material but needs a second camera, a preview scene and Play-mode-only verification; (b) does not, which Gate B already proved in-world, and the equivalence test below pins the data. The preview state is built from `SpriteLayerCompositor.DefaultSlots()` so slot order matches the world. **Spike first (start of 4.1):** confirm `Image.sprite` renders a sliced Kenney sprite pixel-crisp under the creator's own `PanelSettings`; fallback is (a).

**D2. Pure model + thin view.** `CharacterCreatorModel` (toolkit, no UI types): holds a `CharacterBuildPlan`, the rows, `Next/Previous(row)` with wraparound, `Randomize(seed)`, `Preview` (the `SpriteLayerState`, via `ApplyAppearance` with a `SpriteCatalogSource` plus the ~10-line item-profile application above), `BuildPlan()`. The view only renders and forwards.

**D3. Curated `CreatorOptionSet`, not raw catalogs.** Reason beyond "436 options are unusable": `BarrowsEndCatalogAuthor` replaces each catalog's whole options list on every re-author (`:87-104`), so curated display names typed into the catalogs would be destroyed on the next authoring run, despite `displayName` being documented as free to change. So curation lives in a separate consumer asset: per slot, an ordered list of catalog option ids + curated names. Catalog ids remain the save contract; the set only references them. Extend the existing `SpriteLayerCatalogValidator` family with a set validator (every referenced id resolves). Curation with the user is Task 4.0.

**D4. Rows: Skin (`layer-body`), Hair (`layer-hair`), Outfit (`layer-clothes`), Weapon, Class.** Skin/Hair/Outfit are appearance. **Weapon is equipment**: the row picks a starting weapon *item* with a sprite visual profile, applied to the preview via `SetEquipment`, so what the preview shows is what the character wields. Because the ruleset has no per-class weapon data and only one profiled weapon, **Task 4.0 also authors a small set of weapon items + visual profiles (3-4, e.g. sword/axe/mace/staff) and a hand-authored per-class weapon table as consumer data** (stated as such - not rules-derived). Weapon-as-appearance is the fallback if 4.0 finds the art does not support it.

**D5. Rules depth: Class is the only rules pick; the rest is consumer data.** Race = Human, Background fixed (one of the four, chosen in 4.0), ability scores = the standard array `{15,14,13,12,10,8}` assigned by a hand-authored per-class priority table, all six set explicitly. The mandatory level-1 choices (2-6 selections per class) are **auto-resolved from a per-class defaults table** (consumer data, validated against each class's real `PendingChoices` by a test so a ruleset change fails loudly). A compact choice step (reusing the sample's picker) is optional polish, not v1; see U2. The standard array constant is copied, not shared: it lives in `Samples~`, which is not compiled with the package.

**D6. Flow: a New Game / Continue step that owns the boot decision, before the location loads.** `ShellBootstrap.Boot` gains a start step at the very top (before line 102: at that point only the session exists, so no rendered town or uninitialized camera sits behind the creator). Outcomes: **New Game** -> creator -> Confirm -> `Boot` continues with the built protagonist; **Continue** (offered only if a save file exists) -> the shell boots and spawns the authored default party through the same single `SpawnParty` path, then immediately `LoadNow`s. Because the protagonist's id and prefab are registered in `partyVisualPrefabs` on *both* paths (the protagonist spec is always one of the spawn inputs), a load never hits the `SessionLoadCoordinator:462-468` throw. This also gives Cancel a meaning: it returns to the New Game/Continue step (U3 resolved). Rejected: a separate `CharacterCreator.unity` with a static carrier (survives domain reload badly, second scene lifecycle to test).

**D7. Protagonist integration.** The protagonist takes party slot 1 (`ba0...01`, replacing Aldric; Brenna/Corvin/Dessa stay), so `SpawnParty`'s `Members[0]` selection selects the new character. It is built by `CharacterBuildService.Build`, then the shell adds what the service does not: **max HP** = class hit-die maximum + CON modifier (consumer-side in the shell; a test asserts non-zero `resource-hp` for every class; promoting HP derivation into `CharacterBuildService` is a toolkit follow-up, not this phase), and **equipment**: the shell gains the `EquipmentService`/`ItemInstance` wiring `GateBootstrap` has (worn before `BindRestoredView`, same order), which also fixes the existing latent bug that every authored `spec.gear` is ignored.

**D8. Input.** The creator is a UI Toolkit `UIDocument` with its own `PanelSettings`; `UIToolkitPointerCapture.Register` keeps the world's click stack quiet (same pattern as `ShellPanel`). Confirm is one-shot.

## Task 4.0 detailed design (2026-09-20, DRAFT v2, post-Opus review; awaiting user approval)

U1-U3 are taken as approved (protagonist only; Class-only with auto-resolved choices; New Game / Continue step). U5 (your curation time) is what this task spends. The Opus findings and their dispositions are listed at the end of this section; v2 folds them in.

### Goal

Everything the creator needs that is **content, not code**: the curated option lists you choose, the starter weapons with real sprite art, and the per-class tables (weapons, ability-score order, level-1 choice defaults). Delivered as data files plus validators, so 4.1 (model) and 4.3 (shell) consume them without further curation. No runtime code, no toolkit change.

### Deviations from Plan v2's 4.0 paragraph (flagged)

- **The contact-sheet generator is a Python/Pillow script, not Unity Editor code.** v2 (following Task 2.4 risk 4) said Editor code with a `File.ReadAllBytes`/`LoadImage` CPU blit because the imported textures are non-readable. The source PNGs are ordinary files, the precedent `BarrowsEnd/Docs/TileCuration/make_overlays.py` already renders review images this way (Pillow 12.2 is installed), it needs no Editor and no compile, and you reviewed its output before. The batch-mode hazards in 2.4 risk 4 do not apply.
- **4.0 emits data files, not the `CreatorOptionSet` asset.** That asset type is a 4.1 deliverable (D3); 4.0 writes `CreatorPicks.json` (ids + curated names) and 4.1's author turns it into the asset. Otherwise 4.0 would depend on 4.1.
- **Class tables are JSON validated by tests**, consumed later by 4.1/4.3 (same pattern as `TileSemantics.json`; shape and runtime loading in 4.0e).
- **Output goes to `BarrowsEnd/Docs/CreatorCuration/`** (beside the script, committed, like `Docs/TileCuration/`), not v2's `BarrowsEnd/ContactSheets/` outside `Assets/`; `Docs/` is already outside `Assets/`, so the `.meta`-churn reason for the old location does not apply.
- **No helmet sheet** (helmet is equipment, D4; only skin, hair, outfit and weapon are creator rows).

### Facts this design rests on (verified this session)

- Sheet `Assets/Art/Source/roguelikeChar_transparent.png`: 16px cells on a 17px pitch (`BarrowsEndSetup.cs:16`); the slicer keeps only non-empty cells, named `<sheet>_<col>_<row>`; option ids are `<slot>-<sheet>-<col>-<row>`. Sheet is 917x203 = 54x12 cells, margin 0; a Pillow crop at `(col*17, row*17)` (rows from the top) reads exactly the cell the option id names (checked against the imported `.meta` rects). **Measured structure (this corrects my first draft, which said "columns are styles, rows are colours"; I re-checked hair and clothes myself):**
  - *Body* cols 0-1 x rows 0-3: only **4 distinct skin tones** (3 brown + 1 green); the two columns have identical silhouettes (col 1 differs by one mouth pixel), so at most 4 meaningfully different skins, one of them a green orc/goblin.
  - *Hair* cols 19-26: shapes repeat with **row mod 4**; rows 0-3, 4-7, 8-11 are three colour bands (brown / blond / grey-white), and within a band the four rows are different styles. **Row 3 of each band is facial hair (beards)**, which would sit on `layer-hair` and cannot coexist with head hair: offer it deliberately or not at all. So about 24 head styles x 3 colours.
  - *Clothes* cols 6-17: shapes repeat with **row mod 5** (rows 0-4 and 5-9 identical shapes, two colourways; rows 10-11 empty): 60 garments x 2 colourways.
  - *Weapons* cols 42-53 are heterogeneous (some columns one weapon in four colours, others several different weapons); judge them by eye. Shield/feet are similar.
  All layers are 16x16 with pivot (0.5,0.5) at 16 PPU on one shared canvas and are pre-positioned inside the cell (weapon a left strip, shield on the right), so a straight alpha composite in draw order is exactly the world's look (verified).
- Catalog blocks (`BarrowsEndCatalogAuthor.Specs`): body cols 0-1 rows 0-3 (+ 2 custom skeleton bodies, sheet `be`, which must **not** be offered to the creator), feet 3-4, clothes 6-17, hair 19-26, helmet 28-31, shield 33-40, weapon 42-53, all rows 0-11.
- Gear is authored in `BarrowsEndGearAuthor.Gear` (`GearSpec`: item id, profile id, slot, layer slot, catalog, option id, hidden slots, priority); idempotent, ids permanent; the author throws if the option is missing. Existing: iron helm, short sword (`weapon-kenney-42-0`), round shield, tunic.
- `ItemDefinition` has no weapon data; a weapon's combat behaviour is not part of this task (no combat UI yet, Phase 6).
- Level-1 choices per class (Opus-verified): Barbarian 1 req/2 picks; Fighter 2 (fighting style x1, skills x2); Cleric 2 (skills x2, cantrips x3); Wizard 2 (skills x2, cantrips x3); Rogue 2 (skills x4, expertise x2). Human and the four backgrounds have no choices.
- **SRD5 already owns `item-longsword`, `item-mace`, `item-handaxe`, `item-shortsword`, `item-dagger`, `item-warhammer`, `item-rapier`, `item-longbow`, `item-shortbow`, `item-shield`** (all `slot-mainhand` except shield). A second definition with any of those ids makes `RulesDatabase.Register` throw (`RulesDatabase.cs:22-26`) and kills every session. The existing author already dodged this (`item-short-sword`, hyphenated). SRD5 weapon assets carry no `equipmentVisualProfileId`, so reusing them would mean editing package content.
- **Equipment beats appearance:** an equipped item's paint has absolute priority over appearance and a hiding item beats everything (`SpriteLayerState.cs:305-317`). The authored Aldric carries iron helm (hides hair), short sword and round shield, and Corvin a tunic. Once 4.3 honours `spec.gear`, starter gear would silently override the creator's hair, weapon and outfit unless the protagonist's starter gear is chosen deliberately (see 4.0d).
- The Unity Editor was not open at drafting time; re-check before any batch run.

### Steps

**4.0a Re-baseline.** Run the four suites (toolkit EditMode + PlayMode, BarrowsEnd EditMode + PlayMode) on the current tree before touching anything, since uncommitted Phase 3 work (fingerprint) is present; record the counts as the Phase 4 baseline. (You may prefer to commit that work first; not required.)

**4.0b Contact-sheet generator** `BarrowsEnd/Docs/CreatorCuration/make_contact_sheets.py` (Python/Pillow; usage in its header; PNG output and a CSV sidecar next to it):
- One PNG per creator slot (skin, hair, outfit, weapon), options drawn at 4x on a neutral background, **composited over a fixed reference character** so each is judged as worn: skins alone; hair over the default body + default outfit; outfits over the default body; weapons over the default body. A straight alpha-composite in `SpriteLayerCompositor.DefaultSlots()` order is exactly what the world draws (verified). Hair beards (row 3 of each colour band) are visibly marked on the sheet.
- Grid labelled by `col` along the top and `row` down the side, like the tile overlays, so a pick is "hair, col 21, row 3"; the CSV maps every cell to its option id.
- A second output, **`assembled.png`**, composites candidate picks (read from `CreatorPicks.json`) into a grid of sample characters so you can judge combinations: helmet hiding hair, weapon alignment, outfit vs skin clash.
- Skips fully empty cells (the slicer's rule) and excludes the `be` skeleton bodies.

**4.0c Your picks (the human step, ~15 min).** You look at the body/hair/clothes/weapon sheets and tell me, per slot, which cells to offer (suggested sizes, rescaled to what the art really has: **skin up to 4**, hair about 8 head styles (beards only if you want them as a choice), outfit about 6, weapons 3) and optionally names ("Auburn Bob"); I write `BarrowsEnd/Assets/Content/Creator/CreatorPicks.json`:
`{ "skin": [{"option":"body-kenney-0-1","name":"Fair"}], "hair": [...], "outfit": [...], "weapons": [{"item":"item-longsword","option":"weapon-kenney-44-2","name":"Longsword"}] }`. Two rounds expected (the sheets, then `assembled.png` to confirm combinations). A pick is one (style, colour) cell.

## Task 4.1 detailed design (2026-09-20, DRAFT v2, post-Opus review; awaiting user approval)

### Goal

### Deviations from Plan v2 (flagged)

- **No `CreatorOptionSet` asset and no validator for one.** v2's D3/4.1 said 4.1 introduces the asset and an author that turns `CreatorPicks.json` into it. Since then 4.0 chose JSON read through a `TextAsset` (Opus finding 4), with `CreatorPicks`/`CreatorClassTable` types in `BarrowsEnd.Content` and validators already written (`CreatorContentTests`). A second, asset form of the same data would be an unneeded copy, so it is cut. - **The preview element ships in 4.1, not 4.2.** The D1 spike must exercise the real element, so 4.1 builds it (about 60 lines); 4.2's view reuses it.
- **A small refactor of committed Task 2.3 code:** the "resolve an item's visual profile into layer paints" logic (`SpriteEquipmentBinder.Apply`, `:192-220`; profile resolution `:196-204`, paints + `SetEquipment` `:214-219`) is extracted into one public static helper used by both the binder and the creator model. Reason: the plan's central promise is "the preview is what the world draws", and two copies of that logic can drift. **Only the pure part moves**: the binder keeps its warn-once `warnedProfiles` set, its `ownedKeys` bookkeeping and its `this` log context. Signature: `public static bool TryResolveSpritePaints(IRulesDatabase rules, DefinitionId itemId, List<LayerPaint> paints, out EquipmentVisualProfile profile)`; `false` means "clear the slot" and the caller inspects `profile` (a non-`Sprite` kind) to decide whether to warn once. Log message text stays identical so the existing `LogAssert` expectations still match. The safety net is the **PlayMode** `SpriteEquipmentBinderTests` (24 tests, notably the no-usable-profile, 3D-profile-warns-once, null-sprite, helmet-hides-hair and `SetTarget` ones), not EditMode; those suites must stay green.
- **`Build()` replaces D2's `BuildPlan()` and creates a FRESH `CharacterBuildPlan` on every call** (D2 said the model "holds a `CharacterBuildPlan`"; it does not). A reused plan would be wrong: `AddPendingChoice` skips any requirement already in `resolvedChoices` (a second `Build()` would surface nothing and silently succeed), and resolved `SelectFeature` selections stay granted (`CharacterBuildService.CollectGrantedFeatureIds`), so switching Fighter to Wizard would leave the Fighting Style on the Wizard. The model holds only row selections; the plan is a product.
- **The plan's "preview state equals the world's" equivalence test moves to 4.3** (it needs a spawned instance and cannot run in toolkit EditMode); 4.1 pins the same property at state level by sharing the binder's helper.
- **Standard array gets one source.** v1 invented `CreatorContent.StandardArray` with no data behind it (the only copy is a private constant in `CreatorContentTests`). It is added to `CreatorClassTable.json` as `standardArray` (and to the `CreatorClassTable` type), and `CreatorContentTests` reads it instead of its literal, so the 4.0 validators and the runtime use the same numbers. This edits committed 4.0 data; flagged.
- **Toolkit type names avoid `BarrowsEnd`'s JSON DTOs** (`CreatorChoiceDefault`, `CreatorClassEntry`, `CreatorPick` already exist in namespace `BarrowsEnd`; the loader lives there and would silently bind the unqualified name to the DTO). Toolkit types use a `Spec` suffix. Also correcting v1: the `BarrowsEnd.Content` asmdef's root namespace is `BarrowsEnd` (`BarrowsEnd.Content` is only the assembly name).
- **`com.unity.modules.uielements` is added to `crpg-toolkit/package.json`** dependencies: `CRPG.Presentation` gains its first UIElements code, and the project's precedent (commit `2911620` added `modules.tilemap` for `SemanticTile`) is to declare the module when runtime code starts using it. Placement of `LayeredSpritePreview` in `CRPG.Presentation` (not `CRPG.UI`) is deliberate: it is a reusable widget over a Presentation type (`SpriteLayerState`), and `CRPG.UI` does not reference `CRPG.Presentation` (putting it there would add an asmdef edge UI -> Presentation instead); note the toolkit has no other `VisualElement` subclass, so this sets a small precedent.

### Facts this rests on (read this session)

- `SpriteLayerState` (`CRPG.Presentation.Sprites`): `ApplyAppearance(map, ISpriteOptionSource)` (replace semantics, bumps `Version` only on a real change), `SetEquipment(key, priority, paints, hiddenSlots)` (equipment paint beats appearance, hide beats all), `ClearEquipment`, `Layers` (effective, draw order), `Version`, `Report`. Constructed from a slot list; `SpriteLayerCompositor.DefaultSlots()` gives the world's.
- `SpriteCatalogSource(IRulesDatabase)` resolves `(layer slot, option id)`; equipment is keyed by the item's inventory slot (`ItemDefinition.EquipmentSlotId`, `slot-mainhand` for every weapon pick).
- `CharacterBuildService.RefreshPendingChoices(plan)` / `Build(plan, id)`; `Build` copies `plan.Appearance`; `ResolveChoice` validates count only. The build sequence (Refresh, resolve defaults, Refresh, `IsComplete`) and the class defaults are already proven per class by `CreatorContentTests`.
- `CRPG.Presentation` references Core, Actors, Inventory only (`CRPG.Presentation.asmdef`), which covers everything the model needs; `UnityEngine.UIElements` is an engine module, so the preview element fits the same assembly. Baselines: toolkit EditMode 978, PlayMode 412 + 3; BarrowsEnd EditMode 79 (1 known stale-bake failure), PlayMode 28.

### Design

**Namespace `CRPG.Presentation.Creator`** (toolkit, `Runtime/Presentation/Creator/`).

**Plain data (no Unity objects; `DefinitionId` everywhere an id appears, so a preview refresh never re-wraps strings):**
- `CreatorOption { DefinitionId Id; string Name }`.
- `CreatorAppearanceRowSpec { DefinitionId LayerSlot; string Title; IReadOnlyList<CreatorOption> Options }` (Skin = `layer-body`, Hair = `layer-hair`, Outfit = `layer-clothes`).
- `CreatorChoiceSpec { string RequirementId; IReadOnlyList<DefinitionId> Options }` (the requirement id is a plain string in the engine's own type).
- `CreatorClassSpec { DefinitionId ClassId; IReadOnlyList<CreatorOption> Weapons; IReadOnlyList<DefinitionId> ScoreOrder; IReadOnlyList<CreatorChoiceSpec> ChoiceDefaults }` (a class's starter weapons are `CreatorOption`s whose Id is the item id).
- `CreatorContent { DefinitionId Race; DefinitionId Background; int Level; IReadOnlyList<int> StandardArray; IReadOnlyList<CreatorAppearanceRowSpec> AppearanceRows; IReadOnlyList<CreatorClassSpec> Classes }`.

**`CreatorRow`** (what a view binds to): `Title`, `Count`, `Index`, `Selected` (`CreatorOption`, default when empty), `Advance(int delta)` (wraps both ways; `Next`/`Previous` = +1/-1; a large delta is what a 120-outfit row's "jump" needs, so 4.2 gets it free), `Select(string id)` (unknown id: ignored, returns false), `Changed` event. An empty row: `Count 0`, `Advance` a no-op, no throw.

**`CharacterCreatorModel(IRulesDatabase rules, CreatorContent content)`:**
- `Rows` in wireframe/user order: one per appearance row, then **Weapon**, then **Class**. Class display names come from `ClassDefinition.DisplayName`; a content class the ruleset does not know is skipped and `Report`ed.
- **Class change rebuilds the Weapon row** from that class's weapons, keeping the current weapon if still offered, else index 0; a class with no weapons gives an empty row (unarmed preview).
- `Preview` (`SpriteLayerState` over `SpriteLayerCompositor.DefaultSlots()`), refreshed on every row change: `ApplyAppearance` with the selected option of each appearance row, plus the weapon through the shared helper (item -> `TryResolveSpritePaints` -> `SetEquipment(item.EquipmentSlotId, ...)`). **The model remembers the last equipment key it set** (as the binder's `ownedKeys` does), so switching to a class with no weapon, or to a weapon whose profile yields no sprite, clears it; the preview is then unarmed. Because equipment beats appearance and the helper is the binder's, a hiding item would hide hair in the preview exactly as in the world (only reachable synthetically: every campaign weapon profile paints only `layer-weapon` and hides nothing).
- `Randomize(int seed)`: one `System.Random`, appearance rows first, then Class, then Weapon (so the weapon draw is over the new class's list); deterministic per seed.
- `Build()` -> `CreatorResult { CharacterBuildPlan Plan; DefinitionId ClassId; DefinitionId WeaponItemId }`. **A new plan every call** (see Deviations). Sequence: new plan; Race/Class/Background from the ruleset (missing -> `InvalidOperationException` naming it); `Level`; ability scores from `ScoreOrder` x `content.StandardArray` (all six set explicitly); `plan.SetAppearance` per appearance row; `RefreshPendingChoices`; then resolve each pending requirement from the class's defaults **iterating a snapshot** (`plan.PendingChoices.ToList()`, because `ResolveChoice` removes from the very list `PendingChoices` exposes) (**missing default, wrong count, or an option not in the requirement's `Options` -> throw**, since `ResolveChoice` checks count only); `RefreshPendingChoices` again; require `IsComplete`. Weapon is not part of `CharacterBuildPlan` (it carries no equipment), so it travels in the result for 4.3 to equip. `Build()` does not register or spawn anything.
- Failure modes degrade or throw with a clear message. The model itself writes nothing to the console: it reports through an `Action<string> Report`, which it also passes to the shared equipment helper and to the `SpriteLayerState` it owns. (The `SpriteCatalogSource` it constructs can still `Debug.LogWarning` for an invalid or duplicated catalog: that is existing behaviour, not the model's.)

**`LayeredSpritePreview : VisualElement`** (`CRPG.Presentation.Creator`): `Bind(SpriteLayerState)`, `Refresh()` (re-applies when `Version` changed; explicit, no scheduler), `Scale` (int >= 1, default 4; pixel size = sprite canvas x Scale so filtering never sees a fractional size; changing `Scale` after `Bind` re-sizes immediately). One `Image` child per state slot, absolute-positioned to fill the square, `scaleMode` set **explicitly** (not left to the default, so a tight-mesh sprite still maps 1:1 into the square), `sprite`/`tintColor` from the effective layer, hidden (`DisplayStyle.None`) when the layer is invisible or has no sprite. No USS dependency. EditMode tests assert the **inline** `style.*` values (there is no panel or layout pass in EditMode, so `resolvedStyle.*` is meaningless there).

**BarrowsEnd side:** `CreatorContentLoader.Build(picksJson, tableJson)` in namespace `BarrowsEnd` (assembly `BarrowsEnd.Content`) maps the 4.0 JSON to `CreatorContent` (Skin/Hair/Outfit rows with the JSON's names and layer slots, per-class weapon `CreatorOption`s named from the weapon picks, table defaults, `Human`/background/level, `standardArray`). It references the toolkit types by their `Spec` names, so there is no clash with the JSON DTOs. `BarrowsEnd.Content.asmdef` gains a `CRPG.Presentation` reference.

### The D1 spike (first, 30 minutes, retires the biggest unknown)

A BarrowsEnd PlayMode test (runs **without** `-nographics`: RenderTexture) builds a `PanelSettings` (`ConstantPixelSize`, `targetTexture` = a 128x128 RenderTexture) and a `UIDocument`, adds a `LayeredSpritePreview` at Scale 4 over a real body sprite plus hair, waits frames, reads the texture back, and asserts against the **source PNG pixels** (read with `File.ReadAllBytes`/`LoadImage`, as `BarrowsEndSetup` does, because the imported sprite is non-readable): every 4x4 block is one flat colour equal to the source pixel (no interpolation, no bleed), and the hair layer sits above the body. It also writes a PNG for you to eyeball. Setup details this review fixed:
- **Assign the runtime theme explicitly.** The project already ships `Assets/UI Toolkit/UnityThemes/UnityDefaultRuntimeTheme.tss` and `gate-panel-settings.asset` uses it; the "themeless" fallback machinery is UnityEditor-only, so relying on it proves nothing about a player. The spike assigns the `.tss` under `#if UNITY_EDITOR` + `AssetDatabase` (the pattern of `TilemapSpikeTests`/`CameraPrefabTests`); 4.2's authored `PanelSettings` asset must have a theme too. Whether a themeless panel renders at all is left unverified and unneeded.
- **Set `dynamicAtlasSettings` explicitly and assert the texture was not atlassed.** My earlier note (and the 4.0-era fact) said non-readable textures stay out of the dynamic atlas; that is backwards: `DynamicAtlasFilters.Readability` excludes *readable* textures, so non-readable ones are eligible. What actually keeps the 917x203 character sheet out is the `Size` filter against `maxSubTextureSize` (64), plus `FilterMode` if active. At 4x an atlassed or bilinear texture would sample inside a texel and produce gradients, which is exactly what the flat-block assertion detects. So the code-created panel sets its filters explicitly, and 4.2's asset must match.
- Project colour space is Gamma (`ProjectSettings.asset` `m_ActiveColorSpace: 0`), so a byte-exact comparison against the PNG is not confounded by a linear conversion.
**Unknowns it settles:** the RenderTexture's y-flip for a panel-rendered target; that `Image.sprite` honours the sprite's rect with the explicit `scaleMode`; that no atlas/filter path blurs it. **Fallback if it fails:** the RenderTexture route (a): the real compositor prefab in a preview scene plus a camera, accepting Play-mode-only verification.
