# Toolkit: NPC services (stores, inns, quests, recruiting)

Status: DESIGN v2 (2026-10-09), Opus-reviewed: Section 5 supersedes anything above it that it contradicts. Goal (the user's): the things a townsperson does besides talk, available to any NPC placed with the location tools, configured in the editor, with Viking Raid's village as the first user: an NPC can run a SHOP, an INN (rest, with a price), give and track QUESTS, and be RECRUITED into the party. Builds on the NPC dialogue runtime (`Docs/Plans/Toolkit-NpcDialogue.md`) and routines.

## 1. What exists (from a survey of the code; verify in review)

- Dialogue actions already exist and call delegates on `DialogueContext`: `OpenStoreAction` (reads `context.Store`), `RequestLongRestAction` (`context.RestService`), `RequestSaveAction`, `StartQuestAction(questKey)`, `RecruitToPartyAction(companionKey)`, `GiveItemAction`, `RecordEventAction` (writes the Timeline; its actor id is `context.NpcId`, which is the PERFORMER). `NpcDialogueOptions` carries `RestServiceFactory`, `CurrencyItemId`, `RequestSave`, `RequestRecruit`, `RequestStartQuest`, but `NpcDialogues.Wire` never sets `adapter.Store`, and nothing supplies the quest/recruit delegates.
- **Stores.** `StoreInventoryState` (runtime-only listings + buy/sell multipliers), `StoreService` (prices = item `BaseValue` x multiplier; currency is an ordinary stackable item in the shared `PartyInventoryState`), `GameSession.GetOrCreateStore(id, seedIfNew)` (stock survives location unload, saved via `session.Stores`), `StoreView`/`StorePresenter` through `ConversationController`. Scene authoring is `StoreContentPoint { StoreId, TalkInteractionAdapter Adapter, seeds }` bound by `LocationInitializer.PrepareStore`: a scene-authored adapter reference, which a spawned NPC's runtime-added adapter can never be. On load, `RestoreStores` only fills stores that already exist, so `GetOrCreateStore` must come first or depleted stock reseeds.
- **Rest.** `RestService.Rest(members, GameEvent.LongRest)` refills resources whose `RestTrigger` matches (SRD hit points are a long-rest resource) and publishes the event. It takes no payment, handles no conditions or downed members, and there is no clock or day concept anywhere.
- **Quests.** `QuestDefinition` (objectives + item rewards), `QuestLog`, `QuestService.StartQuest` (idempotent) / `RefreshProgress` / `ClaimReward` (items only, once). Objective progress ALWAYS comes from the Timeline (`TrackingKey` counted or tested; the objective "type" is a label nothing evaluates), and the quest only refreshes when something calls `RefreshProgress`. In the toolkit only `RecordEventAction` writes the Timeline: kills (`CreatureDied`), talks and pick-ups are not recorded. Barrow's End hand-rolls `RequestStartQuest` (resolve the key as a `DefinitionId` in the rules database, start, refresh all), `RefreshAllActiveQuests` after every interaction, and one-line notifications (`ShellBootstrap` ~189-199, 625-681). `QuestLogPresenter` and `QuestLogView` exist; only TestProject uses them.
- **Recruiting.** Barrow's End never promotes the world NPC: it builds a new `CharacterState` from a fixed roster, registers it, adds it to the party, equips gear, binds a new view, registers its motor with `PartyExplorationController`, and hides the talk-point fixture (`ShellBootstrap.RecruitCompanion` :688-726). No toolkit recruit service exists. The action's `companionKey` is the only identity the callback gets.
- **Load.** `SessionLoadCoordinator` restores NPC records as fresh views and does NOT re-run `LocationInitializer.Prepare`; runtime components (talk adapter, routine runner) are gone and the composition root must run `NpcDialogues.AttachAll` / `NpcRoutines.AttachAll` again. There is no per-NPC state store: "already recruited", "met" must live in Timeline keys, Party, Stores or the spawn record.
- **Viking Raid's village** wires none of this: no save/load at all, no quests, no HUD or inventory UI in that scene, `stores: []`. Its ruleset sits on SRD5, so the 20 SRD items resolve, including `item-gold-piece` (base value 0, usable as the currency id). Village NPC definitions are unarmed and not in the ruleset.

## 2. Decisions

**S1. Stores belong to the spawn point.** `NpcSpawnPoint.Store` (`NpcStoreSpec`: `StoreId` empty = the spawn id, `Listings` of (item, quantity, -1 unlimited), buy and sell multipliers; `Enabled` implied by having listings). `NpcDialogues.AttachAll` (re)wires `adapter.Store = session.GetOrCreateStore(id, seed)` on EVERY call (so it also covers a load, provided the game calls `SaveService.RestoreStores` AFTER `AttachAll`). The shop opens through the dialogue's existing `OpenStoreAction`; a dialogue that opens a store at a spawn point WITHOUT a `Store` is the validator Error it is today, and with one it is fine. Seeds referencing an unknown item are a validator Error (`GetBuyPrice` throws on unknown ids). Starting money is the game's business (Viking Raid grants some in its bootstrap).

**S2. Inns are a price plus a rest, made of existing pieces plus two small ones.** `RestServiceFactory` defaults to the generic `RestService` when the game gives none (it is generic: characters, rules, bus), so `RequestLongRestAction` works out of the box. New: `SpendItemAction { item, quantity }` (removes from the party inventory, no-op if short) and a `BranchNode` mode `PartyHasItem` (item + quantity, evaluated against `context.PartyInventory`) so a dialogue can say "if you have 5 gold: pay, rest; else: come back with coin" with no new node type. The graph editor's branch node view gets the new mode's fields. Reviving downed members, curing conditions and advancing time stay the game's job (`RestServiceFactory` can wrap `RestService`; there is no clock to advance). SAVE at an inn is OUT of scope (Viking Raid has no save pipeline); `RequestSave` stays an optional hook.

**S3. Quests: a tracker that supplies what Barrow's End hand-rolls, plus the Timeline events nothing records.** New `QuestTracker(session)` (CRPG.Gameplay): `Start(string questKey)` (resolves the key as a `DefinitionId` through the rules database, starts it, refreshes), `RefreshAll()`, events `QuestStarted / ObjectiveCompleted / QuestCompleted` forwarded for UI, optional auto-claim of rewards on completion, refresh triggered after every interaction request ends and on a timeline-change tick (so a quest advances without a caller remembering). `NpcDialogueOptions.Quests` (a tracker) supplies `RequestStartQuest`. Recording: `NpcDialogues` records a Timeline event `talked-to:<spawnId>` (actor = the talking party member, never the NPC) when a conversation STARTS, so TalkTo objectives work with no authored action; new `TimelineRecorders.RecordKills(session, spawner)` subscribes `CreatureDied` and records `kill:<npcDefinitionId>` (for kill objectives; opt-in). Both keys are documented constants. The Quest objective "type" stays a label. Viking Raid: a one-corner HUD (gold, a toast line, a quest log toggled with a key via `QuestLogView`) because without it quests are invisible.

**S4. Recruiting turns the spawned NPC itself into a party member, minimally.** `TalkInteractionAdapter.SpawnId` is set by `AttachAll`, and `NpcDialogueOptions.RequestRecruitSpawn(spawnId, companionKey)` is called by `RecruitToPartyAction` (the old `RequestRecruit(key)` still works for Barrow's End). New toolkit `NpcRecruitment.Recruit(spawner, session, spawnId)`: adds the NPC's existing `CharacterState` to the party, removes its routine runner / talk adapter / interactable / conversation facing and any ambient suspension, records Timeline `recruited:<spawnId>`, and raises a `Recruited(agent)` callback for the game (register the motor with the exploration controller, HUD name, move the GameObject to a persistent scene). Because a load re-runs `AttachAll`, both `NpcDialogues.AttachAll` and `NpcRoutines.AttachAll` SKIP a spawn point whose `recruited:<spawnId>` key is in the Timeline. Limitations stated up front: a recruited villager has no combat kit (Viking Raid's combat lives in another scene and uses the four fixed heroes), so in the village it follows the party; moving it across scenes and saving it as a party member is the game's job (the toolkit's scene release logic would otherwise delete it on travel).

**S5. Editor.** The spawn row gets a Store foldout (id, listings, multipliers) next to Dialogue and Routine; validator rules: store listing item unknown or null (Error), a dialogue that opens a store at a spawn point with no store (Error, already there, message improved), `SpendItemAction` or a `PartyHasItem` branch with no item (Error via DialogueValidator), a `StartQuestAction` whose key resolves to no quest in the project (Warning), a `RecruitToPartyAction` (Warning: recruited NPC keeps no combat kit unless the game gives one). `LocationPlacement.AddSpawn` resets `Store`.

**S6. Viking Raid content.** Hild is the alehouse keeper: a dialogue with Buy (store), Rest (5 gold: a `PartyHasItem` branch, `SpendItemAction`, `RequestLongRestAction`, a closing line) and Chat. Orm gives a quest (move the sacks: talk to Orm -> `StartQuestAction`, objective TalkTo Hild, reward a few gold) and the elder is the second TalkTo target / hand-in. A new villager (Sigrun) is recruitable and follows the party. The bootstrap gives the party starting gold, builds the `QuestTracker`, `NpcRecruitment` registration and the village HUD.

## 3. Risks I want checked

- `StoreView` / `StorePresenter` with an arbitrary `PanelSettings` and the plain dialogue style (look, and whether it needs the BE USS).
- Whether `PartyInventoryState`/`StoreService` can find "gold" with the SRD currency item and that `GetBuyPrice` with base value 0 items is sensible (give the shop SRD items with real values).
- `QuestService` built per call vs a long-lived tracker: any stale-session hazard on session swap (`QuestLog` is per session).
- `Timeline` writes from `NpcDialogues` (actor id) and saved keys: the `talked-to:` key must not collide with Barrow's End's keys and must be harmless in games that do not use it.
- Recruit: `Party.AddMember` on a character that is already registered (HUD/camera/`PartyCommandFilter`/`SelectAll`), `PartyExplorationController.RegisterMotor` for a late member, the party formation solver with 5 members, `AmbientSuspension`/runner teardown ordering, `CharacterAgent` faction.
- `BranchNode` change: serialized fields are additive; existing graphs keep Timeline mode; the editor view and `DialogueValidator`.
- A conversation that records `talked-to:` and a quest refresh that happens mid-dialogue.

## 4. Open questions for review

1. Is a spawn-point `Store` the right home (versus an `INpcStoreSource` the game implements)?
2. Is the `PartyHasItem` branch mode the right way to price an inn, or should this be a proper new node type despite the editor work?
3. Should the tracker live in `CRPG.Gameplay` (it needs `QuestService` + `InteractionController` events) and who owns its lifetime across session swaps?
4. Is "recruit = adopt the spawned NPC's own character" right, or should the toolkit support spawning a separate companion (the Barrow's End way) too?
5. Slicing: stores -> inn -> quests -> recruiting, each with tests, mutation checks and a village demonstration. Anything that should come first or be cut?

## 5. Opus review resolutions (2026-10-09; these override Sections 2-4 where they differ)

The Section 1 claims were confirmed (store code is in `CRPG.Inventory`, UI in `CRPG.UI`, hand-off in `ConversationController`; price = `BaseValue` x multiplier rounded away from zero; `NpcDialogues.Wire` never set `Store`; `RestoreStores` skips stores that do not exist yet; `item-gold-piece` resolves in Viking Raid with base value 0). Problems found, resolved as follows.

1. **Recruiting is deferred to the end of the conversation (S4).** `RecruitToPartyAction` runs while the dialogue is still in progress; tearing the NPC's interactable/adapter down then makes `InteractionController` end the request as TargetLost and cancel the conversation (the closing line never shows), and the NPC is still ambient-suspended. The recruit callback therefore only QUEUES; the work (add to party, strip the NPC components, restore `avoidancePriority`, motor registration through the game's `Recruited` callback) runs when the adapter's `ConversationEnded` fires. "Skip in `AttachAll`" uses `Party.IsMember(characterId)` (saved, and a later dismissal is not blocked forever), not a Timeline key; `NpcRoutines.AttachAll` has no session parameter, so it reads `agent.Session.Party`. No `SpawnId` on the adapter: `AttachAll` knows the spawn id and wires `adapter.RequestRecruit = key => options.RequestRecruitSpawn(spawnId, key)` (Barrow's End wires its own and is untouched). The recruit keeps its villager faction unless a new `WorldSpawnService.SetFaction` is used. A recruit's spawn record still has an NPC definition id, so travel release, defeat tombstoning and load restore treat it as an NPC (Viking Raid's village NPC definitions are not in the ruleset, so a load would fail): stated as the game's job; a later `AdoptIntoParty(spawnId)` flag on the spawn service is the proper fix. The game's `Recruited` callback must also add to `VillageBootstrap`'s private party list.
2. **Quests use authored keys, not automatic ones (S3/S6).** `HistoricalCount` (the default) counts events from before the quest started, and nothing records quest start/completion, so the demo uses Barrow's End's working pattern: dialogue nodes `RecordEventAction` authored keys (`orm-sacks-accepted`, `sacks-delivered`), objectives track those keys with `CountSinceActivation`, dialogues branch on the keys, and the tracker additionally records `quest-started:<id>` / `quest-completed:<id>` on the bus events. The automatic `talked-to:` key is CUT (flagged deviation). `RecordKills` is CUT (flagged): `CreatureDied` is only published by the SRD5 death rules, a ruleset without death never raises it, `TacticalEncounterController`'s own handler nulls the spawn record in the same publish, and `CharacterState` has no NPC definition id; if needed later, raise a `SpawnDefeated(spawnId, npcDefinitionId)` event from `WorldSpawnService.MarkDefeated`. There is no "auto-claim" option: `ClaimReward` is private and always runs inside `RefreshProgress` when the quest completes (item rewards only; a reward with no item throws, so a validator rule). The bus already publishes `QuestStarted` / `QuestObjectiveCompleted` / `QuestCompleted` and `QuestLogView` subscribes itself, so the tracker does not forward events; the view does not refresh on count changes, so the HUD calls `Refresh()` after `RefreshAll` and when the log opens. Viking Raid's quest assets must be added to the ruleset provider's `extraContent` (`Start(questKey)` and `QuestLogPresenter` resolve through the rules database and silently skip what does not resolve): the village content author does it, and the "key resolves to no quest" warning says "and register it in the ruleset".
3. **The tracker is per session (open question 3).** `QuestTracker` in `CRPG.Gameplay`, constructed per session (`IDisposable`, re-created on a session swap by the composition root), `Start(key)` / `RefreshAll()` / a `Tick()` that polls `Timeline.AllEvents().Count` (the timeline has no change event) and refreshes on a change; the composition root also calls `RefreshAll` on `InteractionController.RequestEnded`.
4. **No `RestService` wrapping (corrects S2).** `RestService` is a sealed class: a game cannot override it to revive downed members or cure conditions. The extension point is the `GameEvent.LongRest` event it publishes (document it). The village party is always at full health (no combat there), so the inn's rest has no visible effect: the dialogue line and a toast carry it.
5. **Store UI and money.** `StorePresenter.GetSellableItems` lists every shared-inventory item, including the currency (a 0-value gold piece sold for 0 deletes all the gold): exclude `currencyItemId`. `StoreView` hard-codes the Barrow's End panel look (about 2:1 contrast); `plainStyle` is passed to `DialogueView` only: add it to `StoreView` and pass it from `ConversationController`. `OpenStoreView` with a null `context.Store` throws in the presenter: guard (log, skip). `AttachAll` warns when it wires a store and the currency id is invalid (every purchase would say "Not enough gold").
6. **Inventory helpers (Slice 0).** `PartyInventoryState` can only add/remove by instance id and never merges stacks. Add `CountShared(DefinitionId)` and `TryRemoveShared(DefinitionId, int)` (shared inventory only, spanning stacks); `StoreService` uses them instead of its private `TrySpendCurrency`; `SpendItemAction` and the branch check use the same pair. `GiveItemAction` throws on a null item: validator rule.
7. **`BranchNode` gets a separate `BranchSource` field (corrects S2).** `TimelineConditionType` lives in Core and is shared with `ChoiceOption` and quest objectives; it must not learn about inventory. New `BranchSource { Timeline = 0, PartyItemCount }` plus `item` / `quantity` on `BranchNode` (default 0 keeps every existing graph); `Evaluate(ITimeline)` becomes `Evaluate(DialogueContext)` (its only caller is `DialogueRunner`); `BranchNodeView` gets the two fields; `DialogueValidator` reports a null item as the null-action rule does.
8. **Stores are created where stores already are (S1 revised).** The design's "`AttachAll` before `RestoreStores`" ordering is a trap (Barrow's End's order is rebind, then restore). `LocationInitializer.Prepare` and `RebindStoresAndLoot` therefore ALSO `GetOrCreateStore` for spawn points that carry a store spec, and `AttachAll` only assigns `adapter.Store` (it may also create, idempotently, for a game that does not use `LocationInitializer`). Seeds reuse `StoreListingSeed`; multipliers are set INSIDE the seed callback (`GetOrCreateStore` constructs with 1 / 0.5); items the session's rules database cannot resolve are skipped with a warning (`GetBuyPrice` would throw inside the shop UI). The validator, which cannot know the ruleset, checks for a null item, a 0-value listing (free), and duplicate explicit store ids including against `StoreContentPoint` ids (they share `session.Stores`). An empty `StoreId` defaults to the spawn id. `NpcSpawnPoint.Store` is `= new()` with `Listings = new()`; `LocationPlacement.AddSpawn` and `VillageSceneAuthor` reset it.
9. **Minor.** Fix the `DialogueContext` doc comment on `NpcId` (it is the performer). The HUD's UIDocument must register with `UIToolkitPointerCapture` or clicks go through to the world. The recruitable villager is named Ragna (Sigrun is too close to the hero Sigrid). The inn price is one constant in the authoring script. Hild's stock from the SRD items: healing potion 50, explorer's pack 10, dagger 2, handaxe 5, shield 10, leather armor 10; the party starts with about 80 gold so purchases matter next to a 5 gold inn.

**Slices (each: tests, mutation checks, village demonstration):** 0 prerequisites (inventory helpers, store UI fixes, validator null-item rules) -> 1 stores -> 2 inn (`BranchSource`, `SpendItemAction`, default `RestService`) -> 3 quests (authored keys, tracker, HUD) -> 4 recruiting (last, riskiest).

## 6. As built (2026-10-09)

All five slices built and verified (see the test totals in the hand-off message): stores, inn, quests and recruiting each work end to end on the real Viking Raid village, driven by real clicks (`VillageDialogueTests`, 12 tests), plus toolkit unit/integration suites and mutation checks.

**Slice 0, prerequisites.** `PartyInventoryState.CountShared` / `TryRemoveShared` (all or nothing, across stacks, shared inventory only); `StoreService` uses them (and exposes `CurrencyItemId`); `StorePresenter` no longer offers the party's money for sale; `StoreView` gets a `plainStyle`; `ConversationController` skips an Open Store action when no store is wired (with a warning) and passes `plainStyle` to the shop; `DialogueView.Driven` plus `ConversationController` now open the shop when the player's step REACHES an Open Store action in the middle of a conversation (before, only a graph that started with it worked: this was a latent toolkit bug found when Hild's menu offered the shop); validator rules for a give-item action with no item.

**Slice 1, stores.** `NpcSpawnPoint.Store` (`NpcStoreSpec`: id defaulting to the spawn id, `StoreListingSeed`s, buy and sell multipliers); `NpcStores.Ensure` (idempotent by id, multipliers set inside the seed, unresolvable items skipped with a warning); created by `LocationInitializer.Prepare` and `RebindStoresAndLoot` (so a load's `RestoreStores` finds the store: tested with a real capture/restore) and bound to the NPC's adapter by `NpcDialogues.AttachAll` on every call; a warning when a shop has no currency id; editor: Store field on the spawn row, `AddSpawn` resets it, validator rules (null item, free item, sold-out stock, duplicate ids including store talk points, a shop nobody can reach, an Open Store action with no shop).

**Slice 2, inn.** `BranchNode.Source = PartyItemCount` (+ item, quantity; `Evaluate(DialogueContext)`), `SpendItemAction`, a default generic `RestService` in `NpcDialogues.Wire` (the `GameEvent.LongRest` event is the extension point; `RestService` is sealed), `BranchNodeView` fields, validator rules. Hild's inn: the dialogue branches on 5 gold, spends it, rests, and a HUD toast carries the effect (the village party is always at full health, so a rest changes nothing visible otherwise).

**Slice 3, quests.** `QuestTracker` (per session; `Start(key)`, `RefreshAll`, `Tick`, records `quest-started:<id>` / `quest-completed:<id>`), `NpcDialogueOptions.Quests`, `QuestValidator`, validator rules for `StartQuestAction`. Viking Raid: the errand "Word for Hild" (Orm gives it, Hild's extra menu option appears only once it is accepted, Orm pays out 15 gold; objectives count authored keys `CountSinceActivation`), the quest registered in the ruleset's `extraContent` (and `GameContentAuthor` now keeps village content when it rewrites that list), and `VillageHud`: gold, a toast line, the toolkit quest log on J.

**Slice 4, recruiting.** `NpcRecruitment` (`Queue(spawnId)` waits for the conversation to END, then the NPC's own character joins the party, its routine / talk adapter / interactable / conversation facing are stripped, its avoidance priority is restored, a game callback registers the motor); `NpcDialogueOptions.RequestRecruitSpawn(spawnId, key)`; `NpcDialogues.AttachAll` and `NpcRoutines.AttachAll` skip party members; `WorldSpawnService.SetFaction`; `NpcRoutineRunner.Detach`. Viking Raid: Ragna, a new villager, joins and then follows the party's orders (she is registered with the exploration controller and the village's party list).

**Deviations (all flagged in Section 5 or here).** No `talked-to:` and no `RecordKills` recording. Starting gold is a bootstrap constant. Ragna's spot is chosen by an editor visibility test (eight camera directions) because the first spot was in a gully the camera cannot see, so a click on her walked the party instead of talking (the base test fixture's "would the click land" check compares FLAT distances and passed it). The test fixture's `BringPartyNear` now holds the villager still and, if the camera cannot see her, brings her into the open.

**Findings.** (1) `OpenStoreAction` only ever worked at the START of a graph (the controller consumed the request in its constructor and after the view completed, never after a mid-conversation step): fixed by `DialogueView.Driven`. (2) The store screen sold the party's gold for 0 and deleted it. (3) A recruit's spawn record still carries its NPC definition id (travel release, defeat tombstoning and load restore treat it as an NPC; Viking Raid's village NPC definitions are not in the ruleset so a load would fail anyway, moot while the village has no save). (4) The quest log view does not refresh on objective counts: the HUD refreshes it when opened and on completion. (5) NUnit reuses one fixture instance across tests: reset instance fields in `SetUp`.

**Not done / limitations.**
- No save/load in the Viking Raid village (so nothing here is saved; the toolkit side is designed for it: stores are created before `RestoreStores`, `AttachAll` re-wires, party membership is the recruit truth).
- A rest only refills resources: reviving a downed hero or curing a condition is the game's job through `GameEvent.LongRest`.
- A recruited villager has no combat kit: in the village she follows; Viking Raid's combat lives in another scene with the four fixed heroes. Travelling or loading with a recruit needs the game to move and restore her as a party member (a later `WorldSpawnService.AdoptIntoParty` is the proper fix).
- Quest objective ORDER cannot be expressed (the quest is a set of objectives): the demo gets ordering from dialogue branches.
- Quest rewards are items only; there is no experience or reputation.
- A person has not yet used any of this in the Editor window (the spawn row's Store field, the shop and quest log panels were checked by tests and captures only).
