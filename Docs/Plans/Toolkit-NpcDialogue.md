# Toolkit: talking to a placed NPC (NPC dialogue runtime)

Status: DESIGN v2 (2026-10-09), Opus-reviewed: Section 5 supersedes anything above it that it contradicts. Goal (the user's): place an NPC in the scene, give it a dialogue in the editor, and in play click it, have the party walk up, and hold the conversation, with no per-game wiring code beyond a PanelSettings reference. Viking Raid's village is the first user. Out of scope: quests/stores/recruiting for village NPCs (the existing DialogueContext hooks stay game-supplied and optional), NPC-initiated conversations, barks, portraits.

## 1. What exists (verify in review)

- `NpcDefinition.DialogueId` is a bare `DefinitionId`; nothing turns it into a conversation (`NpcSpawnService` documents that as the composition root's job).
- Conversation machinery exists and works: `WorldInteractable` (needs an explicit anchor + range, resolves exactly one sibling `IInteractionAdapter` in `Awake`), `TalkInteractionAdapter` (`[SerializeField] dialogue`, `[SerializeField] panelSettings`, session dependencies as public settable properties, `IsAvailable = dialogue != null && !conversationOpen`), `ConversationController` (builds its own UIDocument + `DialogueView`/`StoreView`, modal pointer capture), `InteractionController(+Behaviour)`. Barrow's End wires it by hand: static "talk point" fixtures in the scene, `ShellBootstrap.WireTalkAdapters` pushes the session dependencies in. TestProject's AdventureSlice does the same.
- `PlayerCommandRouter.ResolveClick`: a hit whose collider has a `CharacterAgent` in its parents ALWAYS resolves as Select, never Interact ("interactable targets are static world objects, not characters"), so a spawned NPC cannot be talked to by clicking it.
- `InteractionController.TickApproaching` ends the approach only when the performer's motor reports `Arrived` (or Blocked/Invalid/Cancelled); then it re-checks the horizontal distance to `InteractionPoint` against `InteractionRange`.
- The Place-NPC quick panel and the spawn-row buttons (`LocationNpcAccess`) assign/create/open a `DialogueDefinition` and store only its id on the shared `NpcDefinition.DialogueId`. Nothing registers that asset anywhere a runtime can find it: Viking Raid's village NPC definitions are not in the ruleset's `extraContent`, and BarrowsEnd's dialogues are referenced directly by the talk-point adapters, never resolved by id.
- Routines (just built): `GameSession.Ambient` suspends an NPC from the moment an interaction request targeting it is accepted (`InteractionController.SuspendAmbient` takes the target's `GetComponentInParent<CharacterAgent>()`).

## 2. Decisions

**D1. The dialogue lives on the spawn point.** `NpcSpawnPoint.Dialogue` (a direct `DialogueDefinition` reference, null = this NPC does not talk), authored in the spawn row and by the quick panel. Why: no registration step (a dialogue created in the editor works immediately), and "this NPC, in this place, says this" is the designer's model for a town. Fallback when the spawn point's reference is null: resolve `NpcDefinition.DialogueId` through `session.RulesDatabase.TryResolve<DialogueDefinition>` (works for games that register their dialogues, costs nothing otherwise). The panel/drawer Dialogue buttons switch from writing `NpcDefinition.DialogueId` to writing the spawn point's reference; the id path stays for games that use it.

**D2. Clicking a talkable NPC is an Interact.** New `WorldInteractable.TakesClickOverSelection` (serialized bool, default false). `PlayerCommandRouter.ResolveClick`: a clicked character whose parents also carry a configured `WorldInteractable` with that flag resolves as Interact; every other case is unchanged (a party member or a plain NPC is still Select; existing tests keep passing).

**D3. The approach to a character completes in range.** New `WorldInteractable.CompleteApproachInRange` (default false). `InteractionController.TickApproaching`: when set and the performer is within `InteractionRange` of the interaction point, begin the arrival sequence now (stop the performer, turn, execute) instead of waiting for the motor to say `Arrived`. Why: the interaction point of an NPC is the NPC itself (its own transform is passed as the explicit anchor), which the performer's agent can never reach exactly: it would press against the NPC until the 15 s approach timeout.

**D4. `TalkInteractionAdapter` becomes configurable from code.** Public `Dialogue` and `PanelSettings` properties (the serialized fields stay as the authoring path), and `ConversationStarted` / `ConversationEnded` events carrying the performer id. No behaviour change when unused.

**D5. `NpcDialogues` (new, `CRPG.Gameplay.Interactions`).** `AttachAll(ILocationContent content, WorldSpawnService spawner, GameSession session, NpcDialogueOptions options)`, idempotent and keyed by spawn id exactly like `NpcRoutines.AttachAll` (call it after the NPCs exist, after `LocationInitializer.Prepare`, after a load): for each spawn point with a resolvable dialogue whose live agent has no `WorldInteractable` yet, add `WorldInteractable` (anchor = the NPC's own transform, `InteractionRange` from the options, both new flags on) and `TalkInteractionAdapter` to the NPC root (the collider the router hits is on the root's hierarchy; `GetComponentInParent` from it must find the interactable, so a child object will not do) with the GameObject deactivated around the `AddComponent`/`Configure` calls (the interactable's `Awake` demands its anchor), then wire the adapter's session dependencies. Session dependency wiring is the part BE hand-rolls in `WireTalkAdapters`; it is promoted here as `NpcDialogueOptions` + `TalkAdapterWiring.Wire(adapter, session, options)`: skill-check rule (`DefaultSkillCheckRule` is SRD5-specific, so the options carry an `ISkillCheckRule` factory; null = none), `RestService` factory, currency item id, `RequestSave` / `RequestRecruit` / `RequestStartQuest` delegates, PanelSettings. While a conversation is open the NPC turns to the speaker (`FacingPriority.Interaction` on its `FacingController`, cleared when it ends), via the adapter events.

**D6. Editor.** The spawn row gets a Dialogue object field (DialogueDefinition) beside the NPC and Anchor fields; `LocationNpcAccess` gains spawn-point-level `AssignDialogue / CreateDialogue / OpenDialogue` (new asset `dlg-<spawnId>` beside the NPC asset, assigned to the spawn point). Validator: an NPC whose dialogue is assigned but whose graph has no start node or does not validate is an Error (reuse `DialogueValidator`); a `DialogueId` on the definition that resolves to nothing and no spawn point dialogue is a Warning ("this NPC will not talk"); an NPC with a dialogue but a body without a collider is a Warning (nothing to click); two spawn points sharing one `DialogueDefinition` asset is fine (a shared "villager" dialogue) and is not flagged.

**D7. Viking Raid.** `VillageBootstrap` gets a `PanelSettings` reference (the existing `HudPanelSettings.asset`) and calls `NpcDialogues.AttachAll` after `NpcRoutines.AttachAll`; a small authoring step creates short dialogues for Orm, Hild and the elder (line, choice, end) and assigns them to their spawn points; PlayMode test: click an NPC, the party walks up, the `DialogueView` appears, advancing reaches the end, the NPC's routine resumes, the party is not left in a modal state.

## 3. Risks I want checked

- Toggling `SetActive(false/true)` on a live NPC root to satisfy `WorldInteractable.Awake` (OnDisable/OnEnable of `CharacterAgent`, `NavMeshAgent`, `FacingController`, `CharacterPlayableAnimator`, `NpcRoutineRunner`). Alternative: change `WorldInteractable` so `Configure` after `Awake` is valid.
- `NavMeshAgent` avoidance: the performer walks toward an NPC standing still (a suspended NPC restores its original priority 50, equal to the party's).
- Router change: any caller or test that relies on "a character is never Interact".
- A conversation open when the location is torn down or the session ends (ConversationController owns a UIDocument).
- Save/restore: spawn-point dialogue is authored data, nothing new to save; `AttachAll` after load recreates the interactables.
- Two `IInteractionAdapter`s on one object (the NPC already has a store/loot adapter in some game): `WorldInteractable` treats more than one as unconfigured.
- PanelSettings theme: `DialogueView` styles itself with `be-panel` USS class names (Barrow's End) and inline styles; does it look acceptable without the BE stylesheet?

## 4. Open questions for review

1. Is the spawn point the right home for the dialogue reference, versus resolving everything through the rules database?
2. D3 as an InteractionController flag, or should the NPC interactable instead expose an approach point that is always on the NavMesh near the NPC?
3. Is deactivating the NPC around `AddComponent` acceptable, or should `WorldInteractable` be made configurable after `Awake`?
4. Anything in the suspension/facing interplay (routine facing `Ambient` vs conversation facing `Interaction`, the performer's `Interaction` facing) that breaks?

## 5. Opus review resolutions (2026-10-09; these override Sections 2-3 where they differ)

The Section 1 claims were verified (nuance: `TickApproaching` also ends on the 15 s timeout; `IsConfigured` is evaluated live, so `Configure` after `Awake` already works for the anchor, as `TileDoor` does). The villager prefab has a `CapsuleCollider` on the root, layer 11 (Character), which is in `WorldLayers.Hittable` and in the village router's mask.

1. **No SetActive toggling (replaces the D5 mechanism).** It would activate NPC views that `LocationInitializer.Prepare` deliberately leaves inactive, trip the documented stale `NavMeshAgent` position after a SetActive cycle, make `NpcRoutineRunner.OnDisable` abandon the routine step, and reset the Animator. Instead `WorldInteractable` becomes configurable after `Awake`: `Configure` looks the adapter up again whenever `Adapter` is null, and the missing-anchor `LogError` moves from `Awake` to `Start` (skipped once configured). No test asserts on the Awake log. `NpcDialogues` adds the `WorldInteractable` first (explicit, so `[RequireComponent]` on the adapter finds it), then the adapter, then calls `Configure`.
2. **A conversation that fails to start must not lock anything.** `TalkInteractionAdapter.BeginExecute` sets `conversationOpen` only after the `ConversationController` is built (and resets it on failure); `ConversationController`'s constructor disposes the modal scope if building the view throws (it called `BeginModal()` before `AdvancePresentation()`); `NpcDialogues` refuses a null `PanelSettings` with an error; `DialogueRunner` throws on a bad start node, so the validator reports it.
3. **Conversation events fire on every end.** `ConversationStarted` / `ConversationEnded` (performer id) fire on complete AND on cancel (`Execution.Cancel` skips `onFinished`; cancels happen on a superseding request, Esc and scene unload). The NPC's `Interaction` facing is cleared there, with Unity-null checks (the NPC may already be destroyed at teardown).
4. **`LocationPlacement.AddSpawn` resets `Dialogue`** next to `ResetRoutine` (the inserted element is a copy of the previous one; the inspector's own list "+" does the same, which is why a shared-asset Info note is added to the validator).
5. **Validator.** Deep-only (rename `deepRoutineChecks` to `deepChecks`): the DialogueValidator run, prefab collider check. A spawn-point dialogue with no nodes is a Warning ("empty dialogue"), not a red Error, so a freshly created one is not red at once; `DialogueValidator` Errors map to Error, its Warnings to Warning. "`DialogueId` on the definition but no spawn-point dialogue" is a Warning that it only works if the ruleset registers the asset (checking asset existence would pass for Orm, whose `dlg-village-orm` exists but is not in `extraContent`); Viking Raid's authoring step migrates it onto the spawn point. `DialogueValidator` gains: a null node entry and an `ActionNode` with a null action are Errors (Orm's stub dialogue has one); an `OpenStoreAction` in a spawn-point dialogue is an Error (no store is wired, `StorePresenter` would get null).
6. **"Idempotent" means re-wire, not skip.** `AttachAll` always (re)wires the session dependencies of every talkable NPC's adapter (a same-scene session swap with surviving views would otherwise leave them stale, which is why Barrow's End re-wires every session); only the `AddComponent` step happens once. An NPC root that already has another `IInteractionAdapter` is skipped with a warning (`WorldInteractable` supports exactly one).
7. **Ids.** The router emits `interactable.EntityId` (not the agent's: `FindTarget` searches `WorldInteractable.AllLive`) and requires `isActiveAndEnabled && IsConfigured && TakesClickOverSelection`. Ambient suspension already uses the NPC's `CharacterAgent.EntityId`, which matches the runner. Pre-existing and deliberately NOT changed: `TalkInteractionAdapter` passes the PERFORMER as `DialogueContext.NpcId` (the context documents it as "who the party is talking to"; `RecordEventAction` and the check performer consume it): Barrow's End depends on it. The conversation events carry both ids so a game can tell them apart.
8. **`DialogueView` styling.** Inline styles (mid-grey fill, dark-brown text) beat any theme; Barrow's End reads well only because its USS paints a wood panel over it. Judge the Viking Raid dialogue on a capture and, if poor, add a light-text default that Barrow's End opts out of (precedent: `creatorScreen.UsePlaceholderStyle`).
9. **D3 details.** The in-range check runs BEFORE the motor-status switch, so it works whatever the motor reports; `Stop()` keeps the request id, so recapturing `OwnedMotionRequestId` causes no false `Superseded`; `InteractionRange` is clamped to at least 1.0 m (two agent radii are 0.7 m) and the options default to 1.8 m, so the performer stops short and the avoidance-pushing risk goes away.
10. **Router.** Existing router tests keep passing (the flag defaults to false); drag-select is untouched; `PartyCommandFilter` still drops Interact during combat. Known edge, documented: a flagged NPC that JOINS the party can no longer be selected by clicking (the router has no party knowledge).
11. **Resume delay.** After a conversation (and any suspension) the routine re-planned immediately, so the NPC walked off the instant the box closed. `AmbientRoutineMachine` waits `ResumeDelaySeconds` (1.5 s) after a suspension ends.

Answers: (Q1) spawn point + rules-database fallback, validator checks registration; (Q2) D3 stays an InteractionController flag; (Q3) make `WorldInteractable` configurable after `Awake`; (Q4) facing tiers compose (Interaction 2 beats Ambient 1 beats Motion 0; the performer and NPC use separate controllers), plus items 3 and 11.

## 6. As built (2026-10-09)

Verified: toolkit EditMode and PlayMode suites for the new/changed code green (new: `NpcDialoguesTests` 14, `LocationDialogueEditorTests` 14, `NpcDialoguePlayTests` 4, router +3, interaction +3, machine +1), Viking Raid `VillageDialogueTests` 5/5 on the real village (a real click, the party walks up, the panel opens, the NPC holds still and turns to the speaker, finishing releases the NPC, the modal lease and the routine). 21 mutants, all killed.

**What exists.** Runtime: `NpcSpawnPoint.Dialogue`; `NpcDialogues.AttachAll(content, spawner, session, NpcDialogueOptions)` (+ `ResolveDialogue`, `Wire`, `NpcConversationFacing`); `WorldInteractable.TakesClickOverSelection` / `CompleteApproachInRange` / `ConfigureForCharacter` (configurable after `Awake`; the missing-anchor error moved to `Start`; range clamped to at least `MinCharacterRange` 1 m); `PlayerCommandRouter` resolves a flagged talkable character as Interact with the interactable's id; `InteractionController` completes an in-range approach for a flagged target; `TalkInteractionAdapter` gets `Dialogue`, `PanelSettings`, `PlainStyle`, `ConversationStarted` / `ConversationEnded` (every ending), and no longer locks the NPC when a conversation fails to start; `ConversationController` releases its modal lease if the view cannot be built, takes `plainStyle`; `DialogueView` gets a self-contained dark `plainStyle` (the default look only reads well under Barrow's End's wood-panel USS); `AmbientRoutineMachine` waits `ResumeDelaySeconds` (1.5 s) after a suspension. Editor: a Dialogue field in the spawn row, the quick panel and the Dialogue button author the spawn point's dialogue (`LocationNpcAccess` spawn-level assign/create/open; `dlg-<spawnId>` beside the NPC asset), `AddSpawn` resets `Dialogue`, validator rules (empty dialogue = Warning, DialogueId without a spawn dialogue = Warning, graph errors and a store action = Error, body without a collider = Warning; deep checks only), `DialogueValidator` reports a null node entry and an action node with no action; `deepRoutineChecks` renamed `deepChecks`. Viking Raid: `VillageBootstrap` gets `dialoguePanelSettings` (the existing HUD panel settings) and calls `NpcDialogues.AttachAll`; `Viking Raid/Village/3. Author NPC Dialogues` (`VillageDialogueAuthor`) writes the villagers' short dialogues and wires the panel (Orm's empty `dlg-village-orm` stub is filled in place); `VikingRaid.PlayModeTests` references `CRPG.Dialogue` (any assembly that reads `NpcSpawnPoint.Dialogue` needs it).

**Deviation.** Not doing: moving `DialogueContext.NpcId` to the NPC's id (the adapter passes the PERFORMER; Barrow's End depends on it). Left as a documented pre-existing inconsistency; the conversation events carry the performer id.

**Findings.** `PlayerCommandRouter` never resolved a click on a character as Interact (by design); the opt-in flag is the smallest change. The pre-existing `InteractionLifecycleTests.FullLifecycleApproachTurnExecuteCompletesAndReleasesFacing` failed on a clean checkout (it computed the "opposite" destination from the performer's offset to the anchor, which is mostly vertical when the performer stops within centimetres of it; the destination ended metres above the ground); fixed by flattening the vector. A stash of the whole working tree to run a test on the committed state worked cleanly (`git stash push -u`, then `pop`).

**Not done / limitations.**
- Quests, stores, recruiting and rests for village NPCs: the options carry the hooks, the village supplies none; a dialogue that opens a store is an Error.
- A flagged NPC that JOINS the party can no longer be selected by clicking (the router has no party knowledge).
- Nothing starts a conversation by itself (no barks, no NPC-initiated talk).
- A person has not yet clicked a villager in the Editor; the panel look, the spawn row's Dialogue field and the quick panel's new Dialogue handling are checked by tests and a capture only.
- `DialogueView`'s plain style is a placeholder look (no portraits, no typewriter text).
