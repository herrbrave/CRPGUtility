# Toolkit: location tools (scene and NPC placement) — design v1

Status: DESIGN v1 (2026-10-08), NOT reviewed, NOT built. Requested by the user ("Yes let's jump into Scene and NPC placement tooling"); the standing goal (memory: `project_crpg_viking_village`) is in-editor configuration of scenes with named NPCs, so a CRPG is built by placing content in scenes instead of scripting it. Dogfood: `VikingRaid/Assets/Scenes/VikingVillage.unity` (a 3D NavMesh scene; the 2D `BarrowsEnd` scenes author their NPCs by code and use a grid, see Section 6).

## 1. What exists

- `CRPG.Gameplay.Scenes.LocationContent` (a MonoBehaviour, one per location scene): `spawnPoints` (`NpcSpawnPoint { SpawnId, Definition, Anchor }`), `stores` (`StoreContentPoint`), `lootContainers` (`LootContentPoint`), `hasCameraBounds/cameraBoundsXZ`. Read ONLY by `LocationInitializer` (fresh `SpawnNpc` vs restore `BindRestoredView` by `SpawnId`).
- Authoring today is raw Inspector list editing plus an `Anchor` transform the author must create and position by hand; `VillageSceneAuthor` does it by code. No validation: a duplicate or empty `SpawnId`, a missing anchor/definition/prefab, an anchor off the NavMesh or unreachable from where the party arrives are silent until runtime.
- `NpcDefinitionEditor` already hosts an extension hook (`INpcAppearanceEditor`, discovered with `TypeCache`) and the toolkit has `ValidationResult/ValidationSeverity` (`CRPG.Editor.Validation`), `PackageValidatorWindow` (project assets only, no scenes).

## 2. The tools (toolkit, `crpg-toolkit/Editor/Location/`, assembly `CRPG.Editor`)

1. **`LocationPlacement`** (pure static API, the tested core): `AddSpawn(location, definition, position, rotation, spawnId?)` creates the anchor (a child of the location's `NPCs` root, named `Anchor_<id>`, created when missing) and the list entry in ONE Undo group and returns the id; `RemoveSpawn(location, index, deleteAnchor)`; `NextSpawnId(location, definition)` (`<definition id without "npc-"> `, then `-2`, `-3` ... unique within the location); `Snap(surface, point)`; `FaceToward(point, target)`.
2. **`LocationValidator`** (pure, testable): `Validate(location, surface, otherLocations) -> List<ValidationResult>` (existing type: severity, asset path, field, message, fix). Rules: Error: empty `SpawnId`; duplicate `SpawnId` (in this location and among `otherLocations` = the other LocationContent in the open scenes); `Definition` missing; `Definition` has no `VisualPrefab`; `Anchor` missing; `Anchor` not a scene object of the same scene as the location (a prefab asset or another scene); anchor not reachable from the reference point (path incomplete). Warning: anchor off the walkable surface (farther than 0.5 m from a snap point); two anchors closer than 0.8 m; anchor outside the camera bounds when set; store/loot id empty or duplicate, adapter missing. Info is not a severity today (not added).
3. **`ILocationSurface`** (editor interface): `TrySnap(point, radius, out snapped)`, `CanReach(from, to)`. Default `NavMeshLocationSurface` (`NavMesh.SamplePosition`, `NavMesh.CalculatePath` complete). The abstraction exists because the toolkit has TWO navigation backends (`INavMeshService`: NavMesh and the 2D grid); a grid surface is a later implementation, discovered through `TypeCache` like `INpcAppearanceEditor` (Section 6).
4. **`LocationContentEditor`** (custom inspector of `LocationContent`, UI Toolkit): a summary line; a table of NPC rows (status icon from the validator, `SpawnId` text, `Definition` object field, `Anchor` object field, buttons Select / Frame / Snap / Remove); buttons Place NPC (enters place mode), Add empty row, Validate (results listed in the inspector, a click selects the offending anchor or the location); the stores, loot and camera-bounds fields keep their default property drawers below.
5. **Scene-view tool** (`LocationSceneTool`, `SceneView.duringSceneGui` active while a `LocationContent` is selected): draws every spawn as a wire capsule (height from the definition's prefab renderer bounds, 1.8 m default) with a label `<SpawnId> (<DisplayName>)` and a facing arrow, red when the validator reports an Error for it, yellow for a Warning; the selected row gets position and rotation handles (Undo, position snapped to the surface when "Snap" is on). **Place mode**: pick an `NpcDefinition` (object field in the inspector, remembered in `SessionState`), a ghost capsule follows the mouse (`HandleUtility.GUIPointToWorldRay`, `Physics.Raycast` against the scene colliders, snapped with the surface; green when snapped and reachable, red otherwise); LMB places via `LocationPlacement.AddSpawn` (facing toward the reference point), Shift keeps placing, Esc or RMB cancels. A model ghost (the dressed NPC) is a project concern: the base prefab shows every body variant until the appearance is applied at runtime, so the toolkit draws capsules and offers a hook later (`INpcGhostBuilder`, not in v1).
6. **Menu**: `CRPG Toolkit/Location/Validate Open Locations` (all LocationContent in the open scenes; results to the console and the `PackageValidatorWindow` style list).

## 3. Runtime change (small, additive)

`LocationContent` gains an optional `Transform partyStart` (public `PartyStart`, documented as the origin for the editor's reachability check; the game may use it too). `ILocationContent` is NOT changed. CHANGELOG entry. Existing scenes keep working (null = no reachability check, noted as a Warning "no party start: reachability not checked").

## 4. Tests (tests first, toolkit `Tests/Editor`, real Unity runs)

`LocationPlacementTests`: AddSpawn creates the anchor under `NPCs`, the entry, a unique id (`-2`, `-3`), ONE undo step reverts both, the anchor takes the position and rotation, RemoveSpawn with and without deleting the anchor, an id the user typed is kept, snapping uses the surface. `LocationValidatorTests` (fake `ILocationSurface` plus ONE real NavMesh built in the test with `NavMeshBuilder`): each rule fires exactly once for its own defect and not for a clean location, duplicate ids across two locations, an anchor in another scene or a prefab asset, unreachable island, the camera bounds rule, a missing party start warning. `LocationContentEditorTests`: the element lists one row per spawn point with the right status, Remove and Add work through the serialized object and Undo, Validate fills the result list. The scene-view drawing and place mode are not unit-testable: a headless `SceneView` capture probe plus a manual pass by the user. VikingRaid: a PlayMode test runs the validator on the loaded village (`VillageSceneTests`) and expects no Error. Mutation checks on the validator rules and the placement.

## 5. Phasing

Slice 1: `LocationPlacement`, `LocationValidator`, `ILocationSurface`, the `partyStart` field, the inspector, the menu, tests. Slice 2: the scene-view tool (gizmos, handles, place mode). Slice 3 (only if wanted): store and loot placement, camera-bounds handles, `Fit to walkable`, the grid surface, the dressed ghost hook. Not in scope: modular piece painting (the village is a kit of 1,000+ prefab pieces), NPC schedules and dialogue/quest authoring.

## 6. Questions for the review

(a) Is the right home the toolkit (`CRPG.Editor`) with a small `LocationContent` addition, or a project-side tool? What breaks for the 2D scenes (`BarrowsEnd`: `LocationContent` authored by code, grid walkability, no NavMesh)? (b) Does `NavMesh.CalculatePath` / `SamplePosition` work in edit mode and in EditMode tests without baking in a scene (build NavMeshData in the test)? Which toolkit API should `NavMeshLocationSurface` reuse instead? (c) Is "anchor in the same scene as the location" the right ownership rule, and what does `LocationInitializer` do with an anchor whose scene is unloaded? (d) `SpawnId` must be unique across the whole save's world, not only the open scenes: is an all-scenes check feasible (opening 26 MB scenes), or should the rule stay "open scenes" plus a project-level id registry? (e) Undo with `SerializedObject` arrays plus created GameObjects: pitfalls (`Undo.RegisterCreatedObjectUndo`, group collapse, prefab instances). (f) UI Toolkit inspector for a `[CustomEditor]` on a MonoBehaviour with `List<T>` of nested serializable classes: the cleanest way to keep the default drawers for stores/loot. (g) Scene-view place mode in 6000.6 (`EditorTool` vs `duringSceneGui`, `HandleUtility.AddDefaultControl`, hot control, raycast in edit mode needs `Physics.SyncTransforms`, colliders only). (h) What is missing: validation of the NPC's own content (dialogue id exists, faction exists), `NpcSpawnPoint` for companions/party, facing; ids stability when an NPC is renamed (saves refer to `SpawnId`); effort and the smallest useful slice.

## 7. Opus review and design v2 (2026-10-08)

Verified by the reviewer and by me: BarrowsEnd's six location scenes DO carry a `LocationContent`, but every one has `spawnPoints: []` (its NPCs are talk points placed by `LocationAuthoringKit.AddTalkPoint`), so a `[CustomEditor(typeof(LocationContent))]` would take over all of their inspectors for nothing; `VillageBootstrap.SpawnLocationNpcs` spawns directly (skipping a defective entry with a warning) and never goes through `LocationInitializer.Prepare`, which THROWS on a null anchor (and rolls the whole location back); a duplicate `SpawnId` is not loud but silent corruption (the second entry takes the restore path and orphans the first view); `partyStart` would duplicate `VillageBootstrap.partyStart` and the toolkit's own `SceneTravelDestination`.

**Changes.**
1. **No `ILocationSurface`**: the editor tool uses the toolkit's `INavMeshService` (`NavMeshService` for 3D; the grid backend `GridPathfindingService` is plain C# and can be given `WalkabilityGridProvider.FindInScene(scene).Grid` later, chosen by whether the scene has a grid provider, not through `TypeCache`).
2. **No `partyStart` on `LocationContent`, no runtime change.** The validator takes optional `reachabilityOrigins` (the toolkit menu passes the scene's `SceneTravelDestination` transforms; Viking Raid's menu passes `PartyStart`). With none given, reachability is not checked and the summary says so.
3. **No custom inspector for `LocationContent`**: a UI Toolkit `PropertyDrawer` for `NpcSpawnPoint` (status icon, Select / Frame / Snap buttons) keeps the default list (reorder, multi-edit, Undo) and the default drawers for stores, loot and bounds, and touches no 2D scene's inspector.
4. **Place mode is an `[EditorTool("Place NPC", typeof(LocationContent))]`** (on only while a LocationContent is selected, off in play mode and prefab stages) with a small IMGUI panel (definition, layer mask, hint), `RaycastAll` taking the first hit that snaps onto the walkable surface (a package cannot know the project's layers; the village puts roofs on the Obstacle layer), `Physics.SyncTransforms` once on entering, `HandleUtility.AddDefaultControl`, the picked definition remembered by GUID in `SessionState`. A `[DrawGizmo]` draws label and facing arrow per spawn with only cheap checks for colour (no `CalculatePath` per frame).
5. **Severities from the runtime behaviour**: Error: empty `SpawnId`; duplicate `SpawnId` (this location and the other open locations: it silently corrupts); `Definition` missing or without a `VisualPrefab`; `Anchor` missing (throws in `LocationInitializer`); anchor persistent (a prefab asset dragged into the field spawns at the prefab's root) or in another scene; empty or duplicate store/loot id (they would silently share persisted state). Warning: anchor more than 0.5 m off the walkable surface; unreachable from an origin; two anchors closer than 0.8 m; outside the camera bounds; a store/loot adapter missing; a `SpawnId` with a reserved prefix (`hero-`). `ValidationResult` gains an additive optional `Context` (UnityEngine.Object) so a result can select its object.
6. **Anchor parent rule**: the common parent of the existing anchors; else a sibling named `NPCs` next to the location's host (the village: `CRPG/NPCs`); else a child of the location. `AddSpawn` is one Undo group (`RegisterCreatedObjectUndo`, `Undo.SetTransformParent`, `SerializedObject` insert with all three fields set, `CollapseUndoOperations`), `RemoveSpawn` does not delete an anchor another entry shares.
7. **Ids are permanent**: `NextSpawnId` never changes an existing id; renaming or swapping the definition is the author's explicit choice and the drawer warns (renaming orphans the saved record and can revive a dead NPC).
8. **Tests**: validator with a FAKE `INavMeshService` (its three methods) plus an attempt at one real NavMesh through the RUNTIME `NavMeshBuilder.BuildNavMeshData` (the classic editor builder does nothing once `com.unity.ai.navigation` is installed; if the runtime route is not provable in EditMode the real-NavMesh check is run as a one-shot dogfood on the village instead); `LocationPlacementTests` with Undo; the drawer builds. Not a PlayMode test (VikingRaid's PlayMode assembly cannot reference the editor assembly). The dogfood: a Viking Raid menu validates the village and I run it once in batch.
9. **Cut from slice 1**: store/loot placement, camera-bounds handles, the project-wide id text scan (a menu in slice 2, with reserved prefixes), the dressed-ghost hook, dialogue/faction checks (`NpcDefinition.DialogueId` is not read by the runtime and no faction asset type exists), companions (they never use spawn points).

## 8. BUILT: slice 1 + the scene tool (2026-10-08)

Files (toolkit, `crpg-toolkit/Editor/Location/`): `LocationPlacement`, `LocationValidator`, `NpcSpawnPointDrawer`, `LocationGizmos`, `PlaceNpcTool`, `LocationMenu`; `ValidationResult.Context` (additive); CHANGELOG entry; Viking Raid `Assets/Editor/Village/VillageLocationTools.cs` (menu + the `Dogfood` batch method). Tests (`crpg-toolkit/Tests/Editor`, run in `TestProject`): `LocationPlacementTests` (8: anchor under a sibling `NPCs` root, ids `-2`/`-3`, other locations and the reserved prefix, typed ids, the common-parent rule, a host with no parent, ONE undo step and redo, remove with/without the anchor and a shared anchor), `LocationValidatorTests` (16: every rule fires for its own defect and nothing else, a clean location has no findings, results carry their object, no navigation service skips only the surface rules), `LocationToolsTests` (5: the drawer, the walkable-ray rule with a roof above the ground and a layer mask, the picked definition in `SessionState`, the open-locations command with two locations and an arrival point, the gizmo height). Full toolkit EditMode: 1141 tests, 1140 passed, 1 pre-existing skip (a fixture that needs a graphics device).

**Dogfood on the real village** (`VillageLocationTools.Dogfood`, batch, nothing saved): the scene as authored validates with 0 findings (3 spawn points, `CRPG/PartyStart` as the origin); the place-mode ray from above the party start crosses seven colliders (Ground tiles, two Obstacle-layer hill pieces) and returns the first walkable point (0.83, -0.46, 49.69); `AddSpawn` of `village-hild` gave `village-hild-2`, 0 findings, one undo restores 3 spawn points and 3 anchors.

**Deviations from the design v1 (all from the Opus review, Section 7)**: no `ILocationSurface` (uses `INavMeshService`), no `partyStart` field (arrival points come from `SceneTravelDestination`s or the caller), a property drawer instead of a custom inspector (BarrowsEnd's six scenes carry an empty `LocationContent`), no PlayMode test (VikingRaid's PlayMode assembly cannot reference editor code; the dogfood replaces it), no store/loot placement, camera-bounds handles, project-wide id scan or dressed ghost (slice 2 candidates).

**Not verified (needs a person at the editor)**: the interactive behaviour of the `Place NPC` tool in the Scene view (toolbar entry, ghost, click, Shift, R, Esc, the panel), the drawer's look in the real Inspector and the gizmo drawing. The pieces under them (placement, validation, the ray rule, the drawer's elements) are tested. To try: open `VikingVillage.unity`, run `CRPG Toolkit/Location/Place NPC Tool` (or pick `Place NPC` in the Scene view Tools overlay, custom tools list), choose an NPC definition in the panel and click on the ground. **Fix after the first hands-on try (2026-10-08):** the menu command threw `InvalidOperationException: The current selection does not contain any objects editable by the component tool` because `PlaceNpcTool` was a COMPONENT tool (`[EditorTool(.., typeof(LocationContent))]`), which Unity only lets you activate while the Inspector holds that component's editor. It is now a GLOBAL tool that places into `PlaceNpcTool.ResolveLocation()` (the selected object's LocationContent, else the first one in its scene, else any open one; the panel names the target), the menu catches a failed activation and says where to pick the tool, and two regression tests (the menu never throws for any selection and the tool really becomes active; the target resolution) fail on the old declaration (verified).

**Visibility pass after the second hands-on try (2026-10-08):** "it is tough to see where you have placed one in the Scene view". The 1.8 m wire capsule vanished in a 360 m village and buildings hid it. `LocationGizmos.DrawNpc` now keeps a minimum SCREEN size at any zoom (`HandleUtility.GetHandleSize`): a ground ring, a facing arrow and a beacon (a line up from the head to a downward cone) scale with distance; everything is drawn twice (faint where a building hides it, solid where visible) so it shows through walls; a see-through filled column and disc; the label sits on a dark plate; a newly placed NPC pulses with expanding rings for 3 s (`LocationGizmos.Flash`) and the tool selects the new anchor (Unity's move handles appear) and pings it. Compiles and the 31 location tests still pass; the drawing itself is only checkable by eye (Gizmos must be on in the Scene view).

## 9. Access to a placed NPC (2026-10-08, after "capsule is fine as long as we can easily access the npc for adding dialogs and what not")

`LocationNpcAccess` (editor, tested) and `NpcQuickPanel` (Scene view) give a direct path from a marker to what an author edits next. **Click an NPC's beacon** (an invisible `Handles.Button` on the cone; off in play mode and while the Place NPC tool is active) to select its anchor; while an anchor is selected a panel (top right) shows `Name [spawn-id]` and: **Open NPC** (selects the `NpcDefinition` asset: its inspector has the appearance creator, stats and the rest), **Frame**, **Remove** (spawn point and anchor, one undo step), a **Dialogue** object field (assigning writes the dialogue's id into `NpcDefinition.dialogueId`, Undo-able), **Create dialogue and open graph** / **Open dialogue graph** (a new empty `dlg-<npc>` `DialogueDefinition` is created beside the NPC asset with a unique readable id and assigned; an NPC that already has one gets it back, never a second asset), and a warning when the stored id has no asset. The inspector row (`NpcSpawnPointDrawer`) got the same two shortcuts: **NPC** and **Dialogue**. Tests: `LocationNpcAccessTests` (7: anchor to spawn row, the selected anchor is the selected spawn, open selects the asset, assign stores the id and resolve finds the asset again, assign is one undo step, create makes the asset beside the NPC with a readable unique id and never duplicates, a dangling id is reported), plus the drawer's new buttons and the NPC button's handler; mutation checks on the helper. The IMGUI panel and the beacon clicks are only checkable by eye.

**What this does NOT do (important):** the toolkit does not turn `NpcDefinition.DialogueId` into a conversation. `NpcSpawnService` documents that as left to the game, and a spawned NPC has no `WorldInteractable` / `TalkInteractionAdapter` (the adapter holds a `DialogueDefinition` and needs the session wired into it by a composition root, as BarrowsEnd's `ShellBootstrap` does at about line 548). Viking Raid's village has no interaction wiring at all yet (no `InteractionController`). So today the panel AUTHORS the link (NPC to dialogue asset to the graph editor) but clicking an NPC in play mode will not start it. The next piece is the runtime half: on spawn, give an NPC that has a dialogue a `WorldInteractable` + `TalkInteractionAdapter` bound to it and wire the village's session into it.
