# 2D Campaign: exploration UX follow-ups (plan v2, Opus-reviewed, findings folded in; user-approved)

Raised by the user during Phase 5's Gate E playthrough (2026-09-28), after Phase 5 (UI re-skin) had already closed. Not a Phase 5 task (these are exploration-input/world-feedback gaps, not UI re-skin) and not Phase 6 (that needs story/content input the user hasn't given yet) -- a short, standalone task list before Phase 6 starts.

**Goal.** Three real things: (1) a visual for drag-select, which already computes a correct rectangle and hit-tests correctly but is never drawn; (2) real multi-select for BarrowsEnd's own exploration control (currently collapsed to exactly one member by design, `GateCommandSource.OnSelect`'s own `// exactly one` -- the user explicitly chose to lift this rather than ship a box that visually surrounds three members while only highlighting one); (3) a destination marker for movement clicks, which currently fire with a real world-space point that nothing ever renders.

**Non-goals.** A path-preview line; per-member (as opposed to per-click) markers (the user explicitly chose the raw click point over wiring a new resolved-destination signal from `PartyExplorationController`); anything about ability/combat targeting (no combat UI exists yet); changing `PlayerCommandRouter`'s own selection/movement resolution logic, which already works correctly.

### Source facts (verify-first; corrected against the Opus review, v1 -> v2)

1. **`PlayerCommandRouter` already computes a real drag-select `Rect` and hit-tests correctly** (`ResolveDragSelect`, `PlayerCommandRouter.cs:145-173`); `HandlePointerMove` already tracks `exceededThreshold`/`currentScreenPosition` continuously (`:83-90`); none of this is exposed live. Confirmed, not assumed.
2. **`PlayerCommandRouter`'s ground-click tier already fires `Move` with the real world-space click point** (`hit.point`, `:142`) -- sufficient for a raw-click marker with no new `PlayerCommandRouter` API (per the user's own choice on marker accuracy).
3. **Blocker (Opus review, B1): `CRPG.UI` cannot reference `InputSystemCommandSource`/`PlayerCommandRouter` at all -- an assembly cycle, not just bad style.** `CRPG.InputSystem.asmdef` and `CRPG.Gameplay.asmdef` both already reference `CRPG.UI`; the reverse reference this plan's v1 assumed would cycle. **Fix (D1 below): a new interface in `CRPG.Core`** (which everything already references), implemented by both `PlayerCommandRouter` and `InputSystemCommandSource`.
4. **Blocker (B2): a MonoBehaviour in `CRPG.UI`/`CRPG.Presentation` cannot serialize a field of a type from `CRPG.InputSystem`, and Unity cannot serialize an interface field either** -- D5's original "just wire a SerializeField in the scene author" has no valid field type. **Fix: wire it in RUNTIME CODE from a BarrowsEnd composition root that already holds the real reference**, matching this whole project's own established composition-root pattern (`DollBootstrap` reading `bootstrap.Services.Equipment` directly, `HudBootstrap` reading `bootstrap.Services.Session`) rather than a scene-authored cross-assembly reference.
5. **Blocker (B3): firing the live drag-box event unconditionally on `exceededThreshold` would show a selection box during a modal (the paper doll, a conversation), over the HUD, or mid scene-transition** -- confirmed both real modals call `UIToolkitPointerCapture.BeginModal()` (`DollView.cs`, `ConversationController.cs`). **Fix (D1): gate on `exceededThreshold && !gestureSuppressed`, and re-check suppression on every move (not just at press time), firing the "ended" event if a modal opens mid-drag** (mirroring `HandlePointerUp`'s own existing "modal opened mid-gesture" re-check, `PlayerCommandRouter.cs:94-96,103`).
6. **Blocker (B4), the reason this is v2: `GateCommandSource.OnSelect` (`GateCommandSource.cs:47-58`) deliberately collapses every `SelectCommand` -- including a real multi-hit drag-select -- down to exactly one member** (`// exactly one`, forced `SelectionMode.Replace`). Confirmed via source, and confirmed no test hard-asserts this specific behavior (a plain text/name search found no test referencing `GateCommandSource` at all). **User's decision: lift this** -- forward every party-member hit from the real command, with its real `SelectionMode`, instead of truncating to one. `PartyState`/`PartyExplorationController`/`WedgeFormationSolver` already fully support a real multi-member selection+move today (confirmed: `PartyState.SelectMany`, the formation solver fanning one move command out per selected member) -- `GateCommandSource` was the only thing throwing this away, not a missing capability elsewhere.
7. **Blocker (B5): `HudRoot.CreateRegion` cannot host a full-screen overlay, and a naive attempt would swallow every world click.** `CreateRegion`'s own region element defaults to `PickingMode.Position` (not `Ignore`) and is registered with `UIToolkitPointerCapture` via the HUD's document -- stretching it full-screen would make `IsPointerOverUI` true everywhere, suppressing every world gesture including the drag's own release. **Fix (D2): a sibling component on the SAME `Hud` GameObject, adding its OWN `PickingMode.Ignore` element directly to `GetComponent<UIDocument>().rootVisualElement`** (bypassing `CreateRegion` entirely) -- matches how `HudRoot`'s own root is already set to `Ignore`. Call `BringToFront()` on show, since `HudBootstrap` adds its own regions later (in `Update`), so the overlay would otherwise be an earlier, under-drawn child.
8. **Blocker (B6): no reusable "synthetic drag through a real `InputSystemCommandSource`" test helper exists.** `PointerCommandTests.cs` constructs a bare `PlayerCommandRouter` directly with fakes -- no UI, no real input device. **Fix: the new interface (finding 3) makes this a non-issue** -- tests construct a `PlayerCommandRouter` directly (matching that file's own existing pattern) and hand it to `DragSelectionOverlay` through the interface; no Input System device needed.
9. **Should-fix (S1): the coordinate conversion needs both rect corners converted, then min/max taken -- not a single top-left point.** `UIToolkitPointerCapture`'s conversion (`Screen.height - y` then `RuntimePanelUtils.ScreenToPanel`) is inline, not a helper -- extract it (an internal static) rather than duplicate it by hand. For this project's actual panel setup (`ConstantPixelSize`, scale 1, no rotation) the two approaches agree numerically, but converting both corners is the version that stays correct if that ever changes.
10. **Should-fix (S2, already resolved by the user's own choice): raw click point, not a resolved/snapped destination** -- `PartyMovementService` can snap to a different cell, displace, or fail (Unreachable), and `PartyExplorationController.HandleMove` early-outs on nothing selected, so the marker can occasionally sit a little off from where a character actually stops. Accepted explicitly, not silently assumed.
11. **Should-fix (S3): the marker's sprite must be rotated (`Euler(90,0,0)`, matching the project's own flat-ground-visual convention, `BarrowsEndLocationAuthor.cs:225-226`) since a default `SpriteRenderer` lies edge-on to the pitch-90 camera and would be invisible.** Sorting: `SpriteSortingContract.GroundLayer` (a floor-decal layer, ABOVE the Ground tilemap's order 0), not `WorldLayer` -- `WorldLayer` is for characters/props and sorts by depth-Z bands the Objects tilemap already occupies at a flat order 0; a marker there could draw underneath every Objects-tilemap tile. `|world Z| <= 256` is not the relevant constraint here (that's about depth-sorting bands on `WorldLayer`, which the marker isn't on).
12. **Should-fix (S4): a naive "deactivate the GameObject to hide, drive the fade with a Coroutine on that object" pattern breaks** -- `StartCoroutine` throws on a re-enabled-then-restarted inactive object unless carefully sequenced, and a NEW `Move` command superseding an in-flight fade needs its OLD coroutine explicitly stopped, not just overwritten. **Fix: a single, always-active marker instance with an `Update`-driven timer** toggling visibility/alpha directly, not a coroutine -- simpler, no lifecycle trap, and makes "pooled vs. per-click instantiate" moot (there's only ever one).
13. **Should-fix (S4, continued): the marker must hide during a scene travel/session load**, or it lingers into the next location -- gate it on the same `TransitionGate.IsBusy`/session-swap signals other world-facing systems already respect.
14. **Should-fix (S5): `DragBoxEnded` must fire before `HandlePointerUp`'s own early returns** (the suppression check, `:103`; `ResolveDragSelect`'s `camera == null` guard, `:147`), and ALSO from `InputSystemCommandSource.OnClick`'s existing early return when `ActiveCamera == null` (`:120-121`, which currently drops the release phase entirely) -- otherwise a stuck-visible box is reachable. The overlay itself also hides on its own disable/detach as a last-resort safety net.
15. **Verified correct (Opus review): `Action<Rect>` firing per pointer-move callback (not per frame) with no boxing/allocation is fine perf-wise** (a struct delegate invoke, `Rect.MinMaxRect` allocates nothing) -- confirmed, not assumed to be a non-issue.
16. **Verified correct: no `ClickMarker`/`MoveMarker`/`Reticle`/`GroundMarker`/similar class exists anywhere in the repo today** (a real, case-insensitive search, not just the plan's own claim).

### Decisions

- **D1 `PlayerCommandRouter` gains a new interface, `IDragSelectionFeedback` (or similar name), defined in `CRPG.Core`:** `event Action<Rect> DragBoxChanged` (fired from `HandlePointerMove`, gated on `exceededThreshold && !gestureSuppressed` -- re-evaluating suppression live, not just the press-time snapshot -- with the same Rect helper `ResolveDragSelect` already uses, factored out into a shared private method) and `event Action DragBoxEnded` (fired from every path that ends or invalidates a gesture: `HandlePointerUp`'s normal completion AND its early-suppression return, `ResolveDragSelect`'s `camera == null` guard, and a modal opening mid-drag). `PlayerCommandRouter` implements this interface directly; `InputSystemCommandSource` implements it too, forwarding via the same pass-through-property pattern already used for `Select`/`Move`/`Interact`/`Cancel`, PLUS its own `OnClick`'s `ActiveCamera == null` early return now also ends any in-flight drag box first. Kept off `IPlayerCommandSource` deliberately (not every input scheme has a screen-space drag gesture to visualize).
- **D2 `DragSelectionOverlay` (`CRPG.UI`) takes `IDragSelectionFeedback` (never a concrete type), and attaches directly to `HudRoot`'s own `UIDocument.rootVisualElement`** (a sibling addition, `PickingMode.Ignore`, NOT a `CreateRegion` region) -- per finding 7. Converts the live `Rect` via the extracted/shared conversion helper (finding 9), both corners then min/max. `BringToFront()` on show.
- **D3 Wiring is RUNTIME CODE, not a scene-authored `SerializeField`** (finding 4/B2) -- a small new BarrowsEnd composition-root step (folded into `HudBootstrap.Build()`, which already holds `bootstrap` and builds against the same `Hud` GameObject) passes the real `InputSystemCommandSource` reference (already held by `ShellBootstrap`) to the overlay through the interface.
- **D4 `GateCommandSource.OnSelect` is fixed to forward every real party-member hit, with the real `SelectionMode`, instead of truncating to one** (finding 6/D4, the user's explicit choice) -- `PartyState`/`PartyExplorationController`/`WedgeFormationSolver` already handle a real multi-member selection and formation-move correctly; this was the only place discarding it.
- **D5 `MoveDestinationMarker` (a new `CRPG.Presentation` component) subscribes to the EXISTING `Move` event** (no new `PlayerCommandRouter` API -- finding 2/10) and shows at the raw `MoveCommand.Destination` (the user's explicit choice on marker accuracy). A single always-active instance, `Update`-driven show/fade timer (finding 12, no coroutine), superseded (not stacked) by a newer `Move`. Sprite rotated `Euler(90,0,0)`, drawn on `SpriteSortingContract.GroundLayer` above the Ground tilemap (finding 11). Hidden during a scene-transition/session-load (finding 13).
- **D6 Marker art: check the Kenney game-asset library first; fall back to a simple procedural shape (a plain ring/circle) if nothing fits** -- judged live, not guessed, matching this whole project's established visual-polish pattern.
- **D7 BarrowsEnd wiring:** `MoveDestinationMarker` added as a child of the existing `Input`/world-root GameObject in `Core.unity` (subscribes to `IPlayerCommandSource.Move`, which is already reachable in `CRPG.Core` -- no interface-cycle issue here); `DragSelectionOverlay` wired per D3. The gate scene (`PhaseTwoGateSceneAuthor`) deliberately gets neither (finding S7) -- it's a separate debug scene, not the real campaign flow.

### Task breakdown (tests first, per file)

1. **`CRPG.Core`:** the new `IDragSelectionFeedback` interface (D1).
2. **`PlayerCommandRouter`:** implements it; `DragBoxChanged`/`DragBoxEnded` per D1's exact gating. PlayMode tests (matching `PointerCommandTests.cs`'s own existing direct-construction style, per B6's fix): a drag past the threshold fires `DragBoxChanged` with the correct rect on each subsequent move and stops firing (fires `Ended` instead) if a modal/suppression condition becomes true mid-drag; release always fires `DragBoxEnded` exactly once per active gesture (including the suppressed-at-press-time path and the `camera == null` path); a plain click (never exceeding the threshold) never fires either event.

6. **`MoveDestinationMarker`** (`CRPG.Presentation`, D5): subscribes to `Move`, shows/positions/fades per D5. PlayMode tests: a `Move` command shows the marker at the destination; a second `Move` before the first's timer elapses repositions/restarts rather than stacking; it hides itself once its timer elapses with no external cleanup needed; it hides during a scene-transition/session-load signal.

### Results (implemented 2026-09-27/28)

All 7 task-breakdown items implemented, tests-first, per the reviewed v2 plan.

1. **`IDragSelectionFeedback`** (`crpg-toolkit/Runtime/Core/Commands/IDragSelectionFeedback.cs`): `DragBoxChanged`/`DragBoxEnded`, as designed.
2. **`PlayerCommandRouter`** implements it: `HandlePointerMove` re-checks suppression live (not just the press-time snapshot) and fires `DragBoxChanged`/toggles `dragBoxShown`; `EndDragBoxIfShown()` is called from `HandlePointerDown` (defensive, a stale unshown box from a gesture that never got an Up), `HandlePointerUp` (unconditionally, before its own suppression check -- covers the normal path, the suppressed-at-release path, and `ResolveDragSelect`'s own `camera == null` guard, since that guard runs strictly after), and a new `AbortGesture()` (for a release that can't be resolved at all). `ComputeDragRect()` factored out of `ResolveDragSelect` and reused by the drag-box events. 8 new PlayMode tests in `PointerCommandTests.cs`.
   - **Bug found and fixed during verification**: two of the new tests asserted `Rect.Contains(downScreenPos)`/`(midScreenPos)` -- `Rect.Contains`'s max bound is exclusive, and one of those two points is by construction the rect's own max corner on at least one axis, so the assertion was flaky-by-construction (failed once, seed-dependent). Fixed by asserting the rect's min/max bounds directly against `Mathf.Min`/`Mathf.Max` of the two screen points instead of relying on containment at an exact corner.
3. **`InputSystemCommandSource`** implements `IDragSelectionFeedback` via pass-through properties (same shape as `Select`/`Move`/`Interact`/`Cancel`); `OnClick`'s `ActiveCamera == null` branch now calls `Router.AbortGesture()` on `context.canceled` instead of silently dropping the release. New `InputSystemCommandSourceTests.cs` (real Input System `Mouse` device via `InputTestFixture`, matching `CameraInputTests.cs`'s own precedent): pass-through forwarding, and the camera-goes-null-mid-drag abort path.
4. **`GateCommandSource.OnSelect`** now forwards every matching party member with the real `SelectionMode` (was: exactly one, forced `Replace`). New `BarrowsEnd/Assets/Tests/Editor/GateCommandSourceTests.cs` (3 tests): multi-hit forwarding, hostile-NPC-only silently dropped, Move/Interact/Cancel pass through unchanged.
5. **`DragSelectionOverlay`** (`crpg-toolkit/Runtime/UI/DragSelectionOverlay.cs`): a `PickingMode.Ignore` sibling element added directly to `HudRoot.DocumentRoot` (new public property, bypassing `CreateRegion` per B5). `UIToolkitPointerCapture`'s screen->panel conversion extracted to a public static `ScreenToPanelPoint` (per S1) and reused for both rect corners. 2 new PlayMode tests in `DragSelectionOverlayTests.cs`: shows/hides across a real drag against a real `PanelSettings` (`ConstantPixelSize`, scale 1); hides immediately if a modal begins mid-drag.
