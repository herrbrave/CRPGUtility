# NPC appearance creator, family 2: Sidekick goblins

Status: DESIGN v2 (2026-10-06): spike done, Opus-reviewed (Section 8 supersedes Sections 2/4/5 where they differ), NOT built, awaiting the user. Builds on the finished Viking creator (`Docs/Plans/VikingRaid-NpcAppearance.md`, Sections 12-14). Decision by the user: Sidekick HUMANS are out (the Starter pack has no Viking outfits and the Viking Sidekick pack costs $200); goblins first, same structure as the Viking creator ("a fairly rigid structure with a few categories to rotate through"), edited from the `NpcDefinition` inspector with the live 3D preview.

## 1. Goal

A goblin NPC is authored as data (`NpcDefinition.appearance`: (slot, option) id pairs, copied onto `CharacterState.Appearance` at spawn, saved and restored by the toolkit), dressed at spawn from one shared goblin base prefab, and edited with `< Title: Value >` rows on a few tabs with a live preview. Same data path, same binder, same inspector as the Viking creator; the catalog is a second asset.

## 2. Facts (verified 2026-10-06; spike code `Assets/Editor/Appearance/SidekickGoblinSpike.cs`, sheets `VikingRaid_Logs/spikes/appearance_goblin_*.png`, `goblin_report.txt`)

- The prebuilt Sidekick prefabs (`GoblinSpecies_01`, `GoblinFighter_01`) are ONE combined skinned mesh each (thousands of duplicated bones): not usable as a master. The raw per-region part FBXs are: `Resources/Meshes/Species/Goblins/SK_GOBL_BASE_{NN}_{region}_GO01.fbx` (97 files) and `Resources/Meshes/Outfits/GoblinFighters/SK_GOBL_FIGT_{NN}_{region}_GO01.fbx` (330 files = 10 sets x 33 regions). Every part is a skinned mesh on one shared skeleton of named bones (`root pelvis spine_01.. head neck_01 jaw hand_l ...`, 93 transforms in `GoblinSpecies_01`).
- Regions (the 2-digit prefix orders them): 01 HEAD, 02 HAIR, 03/04 EBRL/R (brows), 05/06 EYEL/R, 07/08 EARL/R, 09 FCHR (facial hair), 10 TORS, 11/12 AUPL/R (upper arm), 13/14 ALWL/R (lower arm), 15/16 HNDL/R, 17 HIPS, 18/19 LEGL/R, 20/21 FOTL/R, 22 AHED (head attachment), 23 AFAC (face attachment), 24 ABAC (back), 25-28 AHPF/B/L/R (hip attachments), 29/30 ASHL/R (shoulders), 31/32 AEBL/R (elbows), 33/34 AKNL/R (knees), 35 NOSE, 36 TETH, 37 TONG, 38 WRAP.
- BASE species: ONE body (TORS..FOTR each have only variant 01), 10 "species" variants of HAIR, EBRL/R, EARL/R, FCHR, NOSE, TETH (NOSE 10), ONE HEAD, EYEL/R, TONG. Rendering species N's face parts on the base body gives 10 clearly different goblins (long hair, buns, topknots, tusks, ear shapes).
- FIGT sets 01..10: each set carries ALL regions from 02 to 36 except HEAD/EYE/TONG/WRAP, including its own HAIR/EBR/EAR/FCHR/NOSE/TETH.
- Assembling whole sets (face parts from the set) and MIXED sets (set 2 torso and arms + set 7 legs and feet + set 4 head attachments + set 5 shoulders) both render correctly; the mixed goblins (skull mask, spiked armour, hide) look intended. Parts of different sets do not clash.
- Colour: ONE Sidekick shader-graph material per character (`_ColorMap` texture, `_SkinColor`/`_SkinColorAmount`, dirt/dark/eyeliner amounts). The 5 `GoblinSpecies_0N` and 5 `GoblinFighter_0N` colour maps share one UV layout: any map on any part combination renders as that palette (species maps: dark grey-green skin; fighter maps: olive skin with different outfit colours). So "Look" is a choice of 10 whole-character colour maps; the part meshes' own materials are placeholders (`Lit`).
- Blend shapes: body parts have 4 (`defaultBuff`, `defaultHeavy`, `defaultSkinny`, `masculineFeminine`), HEAD has 72 (mostly facial animation) plus the same 4. Not yet rendered for goblins (to verify in the build).
- Bones: of 427 parts, 109 (against the species skeleton; 82 against `GoblinFighter_01`) have bones missing from the skeleton; every one is a per-part dynamic-chain bone named `{region}_dyn_NN_NN_{c|l|r}x{n}` (hair, ears, belts, back, facial hair). They exist in the part's own FBX hierarchy. (CORRECTED in Section 8: the names are generic, e.g. `hair_dyn_01_01_c`, shared across many parts, and the species-01 master prefab itself carries `hair_dyn_01_01..03_k`; the spike's "renders look right" claim is RETRACTED: it bound by name and fell back to an ancestor, which is wrong for any vertex weighted to a dyn bone.)
- The existing project prefabs for goblins (`Goblin_Grunt_*`, `Goblin_Warrior_*`, from `CharacterRosterAuthor`) stay as they are (combat roster); the creator is for NPC definitions.

## 3. Structure: 4 tabs, 12 rows

| Tab | Row (slot id) | Required | Options |
|---|---|---|---|
| **Face** | `face` | yes | species 01..10: HEAD(01), EYEL/R(01), TONG(01) + EBRL/R, EARL/R, NOSE, TETH of species N |
| | `hair` | no | species HAIR 01..10 + fighter-set HAIR 01..10 (20) |
| | `facialhair` | no | species FCHR 01..10 + set FCHR 01..10 (20) |
| **Outfit** | `torso` | yes | Bare (base 01) or fighter set 01..10: TORS, AUPL/R, ALWL/R, HNDL/R (an outfit's top half, arms and hands) |
| | `legs` | yes | Bare or set 01..10: HIPS, LEGL/R, FOTL/R |
| | `helm` | no | set 01..10: AHED + AFAC |
| **Gear** | `shoulders` | no | set 01..10: ASHL/R |
| | `back` | no | set 01..10: ABAC |
| | `belt` | no | set 01..10: AHPF/B/L/R |
| | `joints` | no | set 01..10: AEBL/R + AKNL/R |
| **Colour** | `look` | yes | the 10 colour maps (5 species + 5 fighter) |
| | `build` | yes | Default / Buff / Heavy / Skinny / Masculine / Feminine (blend shape weights on all body and head parts) |

That is 12 rows on 4 tabs. Ids are stable strings derived from the part names (`face-goblin-03`, `torso-set-05`, `helm-set-02`, `look-fighter-03`, `build-heavy`); the catalog is the only place they map to meshes.

## 4. Changes to the existing system

The master of a goblin has NO baked meshes: the base master prefab is the skeleton only. Everything is attached by the applier, so there is no `ToggleChild` for goblins and every slot is "attach".

1. **Catalog** (`ModelAppearanceCatalog`, additive fields, the Viking catalog keeps working): a family label; `paletteScope` (`FamilyMaterials` = today's behaviour, `AllRenderers` = every renderer of the character, used by the goblins); `previewIdleClip` (the preview's idle pose, replacing the preview's hard-coded Hero profile path). Options gain `parts` (a list of `{prefab, bone-binding}` entries; `AttachRigged` already binds one renderer) via a new kind `AttachParts` (a SET: all its parts are bound, marked with the slot id so the slot can be replaced as a unit), and a new kind `BlendShapes` (`{name, weight}` pairs).
2. **Applier**: `AttachParts` binds every part's skinned renderers to the master skeleton BY BONE NAME. A bone the master lacks is handled per part: the part's own transform for that bone (its dynamic-chain bone) is moved under the master's counterpart of its parent with the same local pose when the parent exists (exact bind pose), else the renderer is rejected as today (a half-bound mesh is worse than none). After all slots: apply the palette (scope), then the blend shapes: first reset every blend shape the catalog names to 0 on every renderer, then set the chosen option's weights. Idempotent, total, and "Resolve" unchanged. Existing Viking tests unchanged.
3. **Binder**: unchanged (catalog reference; self-binds; `Refresh`).
4. **Inspector** (`INpcAppearanceEditor`): the Viking-specific handler becomes generic: `Handles` is true for no prefab or any prefab with a `ModelAppearanceBinder`; the catalog comes from the binder on the NPC's prefab (not from a hard-coded author call); the no-prefab offer shows one button per family (Viking base, Goblin base). The preview loads the catalog's master and `previewIdleClip`.
5. **Author**: `GoblinCatalogAuthor` builds `Assets/Appearance/GoblinAppearanceCatalog.asset` from the part folders (throws listing every missing file, asserts unique ids, region coverage per row, the 10 colour maps), saves `GoblinMaster.prefab` (the `GoblinSpecies_01` prefab with its combined mesh removed, so skeleton + Animator avatar) and the base prefab `GoblinNpcBase.prefab` via the same wrapper path as `CharacterRosterAuthor` (goblin animation profile, `ModelActionCues`, the Sidekick yaw correction (18, 34) already measured, binder + catalog).
6. **Seeds**: a few goblin NPC definitions can be seeded by an author the way the villagers are (written once).

## 5. Tests (tests first, real Unity runs)

- EditMode catalog: 12 rows on 4 tabs; every part file exists and loads as a skinned mesh; ids unique; each required row has a default; each slot's option lists every region it owns; the 10 colour maps load; `GoblinMaster` has no skinned renderers and keeps the Animator avatar.
- EditMode applier on the real goblin master: face N shows exactly one SMR per face region; a mixed outfit has exactly one SMR per region (no leftover bare part under a set; switching torso set replaces, never duplicates); None removes a set; palette applies to EVERY renderer including late-attached parts; blend-shape reset then set (switching Buff to Skinny leaves no residual weight); all bones of every attached renderer belong to the master skeleton (the dyn-bone chains moved under it); every option of every row applies with zero warnings; idempotence; the Viking tests still pass.
- EditMode inspector: the generic handler gives the goblin rows for a goblin-base NPC and the Viking rows for a Viking-base NPC; no-prefab offers both; foreign slot entries survive a goblin write.
- PlayMode: a goblin NPC spawned through `WorldSpawnService` in the village scene is dressed from its definition; a restored view is dressed from the saved STATE; the goblin idles/moves with the goblin profile and the yaw fix.
- Contact sheets per row (the existing probe extended) reviewed by eye, as for the Vikings; a mutation pass on the new applier paths.

## 6. Risks and what is deliberately not done

- **Draw cost**: a dressed goblin is up to ~36 skinned renderers (11 face + 12 body + 13 attachments), no batching across skinned meshes. Fine for the village; a combat with 8 goblins is ~290 renderers. A mesh MERGE step (concatenate parts into one skinned mesh at spawn, blend shapes preserved by weight baking or dropped) is the known fix and is NOT part of this design; measure first (the Frame Debugger / profiler on the real goblin encounter) and decide.
- Dynamic bones do not move (no physics): hair and belts are static. Acceptable.
- Sidekick humans, the Sidekick Character Tool and the combined prefabs are out of scope. The Starter package stays imported (unused).
- Part pivots/scale: all parts share the skeleton's bind pose so no per-part pose is stored (unlike the Viking attachments).

## 8. Review resolutions (Opus, read-only, 2026-10-06; every point below checked against the source; surprising ones re-verified by me)

**Facts corrected**
1. Dyn-bone names: the "x10" in `goblin_report.txt` is a COUNT (the spike prints `name + "x" + count`); real names are `hair_dyn_01_01_c`, `ahpr_dyn_01_01_02_r`, `hair_dyn_01_01_k` (suffix c/l/r/k, 2-3 indices) and are GENERIC: many parts use the same name. The report lists only the top 25 of the 109/82, which also include `hips_`, `tors_`, `ahed_` chains.
2. The `GoblinSpecies_01` prefab itself contains `hair_dyn_01_01..03_k` (verified by grep), so "skeleton + avatar" is not clean: binding by name silently binds other parts' same-named chains to species 01's rest pose. The spike did exactly this (species faces 2, 4, 7 show no visible ears: consistent with collapsed ear chains). Everything was rendered in T-pose with the Animator off; nothing about animation was tested.
3. Blend shape names are region-prefixed (`TORSBlends.defaultBuff`, `HEADBlends.defaultBuff`, `HAIRBlends.*`); a plain `defaultBuff` matches nothing. Shapes also exist on hair; attachments unknown. `masculineFeminine` direction/range unverified. BASE has a `38WRAP` part the design drops (deliberate: decided below). Header said 11 rows, there are 12.

**Design changes (accepted)**
- B1. **Dyn chains are the part's own, never looked up by name.** `*_dyn_*` transforms are excluded from the master's name map. For each part clone, a dyn chain is moved (top-most missing ancestor only) under the master bone that is its parent in the part's hierarchy, keeping its LOCAL pose, and is marked with a `ModelAppearancePart` (slot id) so `RemoveParts` removes it with the part and the next Apply never sees it. The master's own `hair_dyn_*_k` transforms are stripped when `GoblinMaster` is authored. Local pose = the bind pose is verified by test (B3), not assumed.
- B2. `AttachParts` does not use `MasterMeshes`/`master.transform.parent`; the parts' parent is the avatar Animator's transform (stored explicitly: catalog `rigRoot` bone/path or found by `Animator`).
- B3. **Test that every bound bone matches its bind**: for each attached renderer and each bone i, `bone[i].localToWorld` at rest ≈ `inverse(bindposes[i])` relative to the renderer root (tolerance), plus every bone belongs to the master hierarchy; and an ANIMATED contact sheet (idle sampled, as the preview already does) in addition to the T-pose sheets. The T-pose-only evidence is retracted.
- B4. **Blend shapes**: matched by the suffix after the `.` through `GetBlendShapeIndex`, skipped when -1 (never call `SetBlendShapeWeight` with an unchecked index); applied to EVERY part renderer that has the shape (body, head, hair, set parts); before applying, reset to 0 every shape the catalog names. Verify `masculineFeminine` range by rendering 0/50/100 first. Heavy/Buff may clip shoulder/joint pads that lack the shape: check on the sheets.
- S1. Catalog fields for the preview: `headBone` (`Head` for Viking, `head` for goblins; today `ModelAppearancePreview` hard-codes `"Head"` and falls back silently) and `headTab` (today `tab == "Head"`); `previewIdleClip` with a null fallback to today\x27s hero-profile idle so the Viking preview keeps its pose. The probe\x27s `"Hips"` lookup is made family-aware.
- S2. `CharacterRosterAuthor` gets per-entry catalog, animation profile and yaw (today `RunVillagers` always uses the hero profile, `AppearanceBase` always the Viking catalog, and the Sidekick yaw (18, 34) keys on the model path containing `SidekickCharacters`: a `GoblinMaster.prefab` saved elsewhere would silently get (20, 31)). The goblin base build lives in `CharacterRosterAuthor` (Assembly-CSharp-Editor; `BuildPrefab` is private and the Appearance.Editor asmdef cannot call it); `GoblinMaster`/`GoblinNpcBase` live OUTSIDE `Assets/Characters/Prefabs` (`RosterPrefabTests` asserts every prefab there is armed).
- S3. `paletteScope = AllRenderers` is scoped to renderers marked as appearance parts (not every renderer under the root, which would repaint weapons/equipment visuals).
- S4. **Family switching**: when the NPC\x27s `visualPrefab` changes, or a base-prefab button is clicked, `appearance` entries are pruned/rewritten against the new catalog; slots of any KNOWN family catalog that the new family does not have are dropped (a registry of the project\x27s family catalogs tells another family\x27s slots from genuinely foreign ones). Shared slot ids (`face`, `hair`, `look`, `shoulders`) with different option ids fall back to defaults with a warning today; ids that cannot map are removed on the switch.
- S5. Serialization safety: new `ModelAppearanceKind` values are APPENDED (stored as int), `paletteScope` 0 = `FamilyMaterials`; a test loads the EXISTING `ModelAppearanceCatalog.asset` and asserts unchanged behaviour. The generic inspector handler is exercised by openly UPDATED inspector tests (they hard-code `VikingNpcAppearanceEditor`, `use-base-prefab`, the tabs), not "unchanged".
- Part clones keep stripping Animators/colliders (the part FBXs import as humanoid with an avatar: `ModelYawCorrection` takes the FIRST Animator with an avatar), keep the root layer.
- N1. Decide WRAP: dropped (no part rows use it). `GoblinNpcBase` saves a default-dressed set so the prefab is visible in Scene/Prefab view (otherwise it is an invisible skeleton at edit time). Part clones may be cached later (each Apply clones ~36 whole FBX hierarchies of ~90 transforms; acceptable for the inspector and spawn, measure before caching).

**Draw cost**: deferring the mesh merge is defensible (one shared material: the SRP Batcher removes most setup cost; combat goblins stay on the roster prefabs; meshes are readable so a merge can be a final Apply step). It only becomes hard if dyn bones were de-duplicated by name: so each part keeps its own chain transforms (B1).

**Runtime components**: nothing needs a renderer at Awake (`CharacterView.BindModel` takes the Animator, `ModelYawCorrection` the first avatar Animator, `ModelActionCues`/`AnimationPhaseOffset` look up `CharacterPlayableAnimator`, the collider is the spec capsule, culling is AlwaysAnimate). The real breakage was in the applier (B2).

## 9. As built (2026-10-06)

Status: BUILT. Design v2 Section 8 was followed; what the build added or corrected is below.

**Files**: `Assets/Appearance/ModelAppearanceCatalog.cs` (new kinds `AttachParts`, `BlendShapes` appended; `ModelPaletteScope`; catalog `Family`, `PaletteScope`, `HeadTab`, `HeadBone`, `PreviewIdleClip`; option `parts`, `blendShapes`), `ModelAppearanceApplier.cs` (`AttachPartSet`, `BindPart`, `RestPose`, blend shapes, palette scope, "slot already shows it" skip), `Assets/Editor/AppearanceCreator/` (`GoblinCatalogAuthor` -> `Assets/Appearance/Goblin/{GoblinMaster.prefab, GoblinAppearanceCatalog.asset}`, `ModelAppearanceFamilies`, the creator classes renamed `ModelAppearanceCreator{Editor,Element,Model}`, `BindPoseAudit`, probe methods), `CharacterRosterAuthor` (per-entry catalog / yaw / baked look; menu `Viking Raid/Appearance/Author Goblin Base Prefab` -> `Assets/Characters/Npcs/GoblinNpcBase.prefab`, outside the combat roster folder). Catalog: 12 rows, 137 options.

**What the build found (beyond the review)**
1. **Outfit parts rest their attachment SOCKETS differently from the species master.** `BindPoseAudit` (every weighted bone of every part: master rest vs part bind pose): the core skeleton matches to 0.00 cm, but `elbowAttach_*` is off by 37 cm, `backAttach` 7.6, `shoulderAttach_*` 5.8, `hipAttach*` 1-2, `kneeAttach_*` 0.2, `thumb_02_*` 8.9 (set 07 hands) and `prop_r` 159 cm (2 hand parts); the dynamic chains hanging under those sockets inherit the offset. Without correction the pads float. Fix: where a weighted bone's rest differs from the part's bind pose (> 4 mm / 0.02), the part brings a **bind bone** (`<bone>_bind`, marked as a part) under the master bone at exactly the bind pose; dynamic chain tops keep their authored pose. After the fix every weighted bone is within 2 mm.
2. **Rest poses must come from the master PREFAB ASSET, not the live transforms.** First version derived them from the live skeleton: fine on an unposed skeleton, but dressing an ALREADY ANIMATED character (the preview after its first pose, a binder `Refresh`) froze every bind bone in the T-pose (baked hand 1.2 m from its bone). Found by a contact sheet where a second dressing stayed T-posed; `RestPose` now reads bone matrices relative to the rig root from the asset. Regression test `PartsAttachedToAnAlreadyPosedSkeletonStillFollowTheBones`.
3. **Probes must run across editor update ticks.** Inside one synchronous method a skinned mesh with blend shapes is not re-deformed (builds looked identical, 0 pixels differ); across `EditorApplication.update` ticks they differ by thousands of pixels. `AppearancePreviewProbe` sample and contact-sheet methods are tick-driven (run with graphics, without `-quit`). (This also means the earlier Viking contact sheets were synchronous; the Viking meshes are plain skinned meshes and rendered correctly.)
4. A humanoid `SampleAnimation` rotates the model root (already handled for Vikings); `AnimationClip` humanoid idle from the goblin profile poses the Sidekick rig correctly (the hunched stance; Synty's own assembled goblin as a control matched).
5. `GetInstanceID()` is obsolete in this Unity (6000.6): compare references.
6. Blend shapes work and are visible: buff max delta 8.6 cm, heavy 16 cm, skinny 3.4 cm, masculineFeminine 4.1 cm on the torso; the `Build` row offers Default / Buff / Heavy / Skinny / Feminine. `Masculine` is NOT offered: the range/direction of `masculineFeminine` was not verified (weight 100 = the feminine end is an assumption read off the name).

**Tests (all green)**: EditMode `GoblinAppearanceTests` (18: structure, completeness, skeleton-only master, region coverage, species faces, mixed outfits, every weighted bone's skin matrix equals its renderer matrix and lies in the master's hierarchy, dyn chains owned and removed with the part, a master that still carries dynamic bones is not matched by name, posed attach, palette scope, blend shapes by suffix with no residual, idempotence keeps the same objects, clones stripped, every option applies with no warning (a `LogCapture` helper: `LogAssert` only fails on errors), randomizer, Viking catalog keeps its settings), `ModelAppearanceCreatorTests` (family-neutral inspector: goblin rows/tabs, per-family base-prefab buttons, family switch prunes the old family's entries but keeps foreign and unknown ones), PlayMode `VillageGoblinTests` (3, real village scene: a goblin spawned through `WorldSpawnService` is dressed, one renderer per region, follows its animation; `Refresh` re-dresses a live animated goblin; a restored view is dressed from the saved STATE). VikingRaid EditMode 144, all Viking tests unchanged in behaviour.

**Deliberate non-goals / open**: mesh merge (a dressed goblin is up to ~36 skinned renderers; measure on a real encounter first); `WRAP` part unused; `Masculine` build; Sidekick humans (out by decision); dynamic bones do not move (no physics); the combat roster goblins are unchanged.
